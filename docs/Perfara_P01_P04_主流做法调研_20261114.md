## 二、P-01：SmallJank 的主流做法

### 2.1 一手证据链（按时间顺序）

| 时间 | 来源 | 原文 | 是否给阈值 |
|---|---|---|---|
| 2021-04 | PerfDog 官方《Jank卡顿及stutter卡顿率说明》(`article_detail?id=10162`) | Jank：`>前三帧平均耗时2倍` **且** `>两帧电影帧耗时(1000ms/24*2≈83.33ms)`；BigJank：同上且 `>125ms` | ✅ 只有这两档，**没有 SmallJank** |
| 2022-05-13 | WeTest 官方发布说明 (`wetest.qq.com/labs/584`) | 「发布微小卡顿 **SmallJank**，**在 Jank 基础上对细微的卡顿进行捕捉**」 | ❌ 无数值 |
| 现行 | PerfDog 客户端说明书 (`article_detail?id=10089`) | `SmallJank(微小卡顿，在Jank基础上对细微的卡顿进行捕捉)`、`TinyJank(极小卡顿，在高帧率情况下对极小的卡顿进行捕捉)` | ❌ 无数值 |

**结论**：PerfDog 一共四档命名（TinyJank / SmallJank / Jank / BigJank），但**只公开了 Jank 与 BigJank 的数值**。SmallJank 与 TinyJank 至今只有语义描述，没有公式。所以「取得官方 SmallJank 公式」这条路**走不通**，不是我没找到。

### 2.2 必须澄清的一条假证据（重要）

调研过程中，对 `id=10089` 的一次网页渲染摘要里出现了这样一段：

> 「3. 同时满足两条件，则认为是一次严重卡顿 **SmallJank**. ②当前帧耗时>一帧电影帧耗时(1000ms/24=41.66ms)」

看起来很完美——正好补上缺失的阈值，还符合 1×/2×/3× 电影帧的递进规律。**但它是假的**，理由三条：

1. **权威原文（`id=10162`）的「PerfDog Jank计算方法」只有 2 条**，没有第 3 条；该文是 PerfDog 卡顿口径的定稿文档，2021-04 更新后再未改动这一节。
2. 用 `"一帧电影帧耗时"` 这个精确短语做全网检索，**没有任何独立来源**把它与 SmallJank 关联；所有转载 PerfDog 卡顿公式的文章都只有 83.33 / 125 两个数。
3. 那段文字自身有硬伤——把 SmallJank 写成「一次**严重**卡顿」，而 SmallJank 按定义是**轻微**卡顿。

**所以：`41.66ms` 不能作为「PerfDog 官方 SmallJank 阈值」写进代码注释。** 它可以作为**推荐值**，但必须标注为「按 PerfDog 自身电影帧算术推导」，不能标成官方口径。

> 这条记录保留在文档里，是因为下一次有人搜到同样的摘要时，会再次被它误导。

### 2.3 主流工具的分档对照

| 工具 | 分档方式 | 相对条件 | 绝对门槛 |
|---|---|---|---|
| **PerfDog** | Jank / BigJank（公开）；SmallJank / TinyJank（仅命名） | `> 前三帧均值 × 2` | 83.33 / 125（公开） |
| **Android Vitals**（Google 官方） | 不叫 Jank，按帧耗时分类 | — | 慢帧 `16–700ms`、冻结帧 `700ms–5s`、ANR `>5s` |
| **AndroidX JankStats** | 单档：帧耗时 > 期望帧时长即 jank | 期望帧时长来自 `FrameMetrics`/`expectedDuration` | 无固定毫秒值，**随刷新率变化** |
| **项目现状** | Tiny / Small / Jank / Big 四档 | Tiny 用 `1.5×baseline`，其余用 `2×baseline` | 25 / **84** / 83.33 / 125（60Hz 时） |

可以看出主流有两种范式：

- **固定毫秒门槛**（PerfDog、Android Vitals）——跨设备可比，但对高刷设备不敏感；
- **随刷新率浮动的期望帧时长**（AndroidX JankStats）——贴合「掉了几帧」的物理含义，但跨设备不可比。

项目现在是**混用**：Jank/BigJank 走 PerfDog 的固定门槛，TinyJank 走 JankStats 的相对倍数，SmallJank 走了一个与两者都不兼容的固定值 84。这才是 P-01 的根因——不是数字错了 1ms，是**三档用了三套基准**。

### 2.4 推荐档梯（已按此落地）

> **落地状态**：✅ 已实施。`adb.js:1489-1493` 新增 `MOVIE_FRAME_X1/X2/X3_MS`，
> `:1679/1680/1688`（直方图通道）与 `:1786/1790/1792`（framestats 通道）统一档梯，
> `SCHEMA_VERSION` 4 → 5。`round2_fixes_test` 30 → 38 项覆盖「0.5~200ms 全档枚举单调 0 违例」。

保持 PerfDog 的「同一相对条件 + 不同绝对门槛」结构，让四档真正单调递增：

```js
const baseline = Math.max(vsyncMs || 0, p50 || 0);

// 相对条件统一为 2×baseline（PerfDog 原义）；绝对门槛按电影帧 1/2/3 倍递进
const tinyMs  = baseline * 1.5;                                  // 自定，PerfDog 未公布
const smallMs = Math.max(2 * baseline, MOVIE_FRAME_X1_MS);       // 41.67 —— 1 帧电影帧
const jankMs  = Math.max(2 * baseline, MOVIE_FRAME_X2_MS);       // 83.33 —— 2 帧电影帧
const bigMs   = Math.max(2 * baseline, MOVIE_FRAME_X3_MS);       // 125   —— 3 帧电影帧
```

**为什么这样改是对的**：

1. **单调不减恒成立**：`tinyMs = 1.5×baseline < 2×baseline ≤ smallMs ≤ jankMs ≤ bigMs`，任何 baseline 下 Tiny 都严格小于 Small，不会再出现「极小卡顿比微小卡顿还宽松」。

   顺带修掉两处现存倒挂（已用脚本枚举 baseline 0.5–200ms 验证）：
   - **Small ⊂ Jank**：帧率 ≥ 约 24fps（`baseline ≤ 41.67ms`）时 `jankMs` 被绝对门槛钉在 83.34，而 `smallMs = 84`，SmallJank 严格成为 Jank 的子集——这就是 P-01 本体。**这个 bug 在正常帧率下 100% 触发**；只有帧率掉到约 23.8fps 以下（`baseline > 42ms`，`jankMs = 2×baseline > 84`）时 `smallMs` 才重新低于 `jankMs`，方向「碰巧」正确。换句话说，它恰好在最该区分轻微卡顿的场景里失效。
   - **Tiny > Small**：`tinyMs = 1.5×baseline` 不设上限，`baseline > 56.5ms`（帧率低于约 17.7fps）时 `tinyMs > 84 = smallMs`，「极小卡顿」反而比「微小卡顿」更宽松。

   **需要如实说明的一点**：新档梯是「单调不减」而非「严格递增」。当 `2×baseline ≥ 83.33`（帧率 ≤ 约 24fps）时 Small 与 Jank 合并到同一门槛，`≥ 125`（帧率 ≤ 约 16fps）时 Jank 与 BigJank 也合并。这是 PerfDog `max(2×基线, 固定门槛)` 公式的**固有性质**——它自己的 Jank/BigJank 在低帧率下同样会合并——不是本次改动引入的缺陷，但注释里应写明。
2. **与 PerfDog 的算术同源**：41.67 / 83.33 / 125 正是电影帧的 1/2/3 倍，PerfDog 公开的两档（2×、3×）完全吻合，只补了它没公开的第 1 倍。
3. **`SmallJank ⊃ Jank` 成立**，符合「在 Jank 基础上对更细微的卡顿进行捕捉」——SmallJank 变成 Jank 的超集，而不是子集。

**需要同步改的**：

- `MOVIE_FRAME_X1_MS = 1000 / 24` 新增常量，与现有 `X2/X3` 放一起；
- `SMALL_JANK_MS = 84`（`adb.js:1715`）删除，改用同一套计算；
- 注释里把「PerfDog 口径」限定到 Jank/BigJank 两档，SmallJank 标注「门槛按电影帧 1 倍推导，PerfDog 未公开具体值」。

> ⚠️ 这会改变已发布指标的数值 → 必须 `SCHEMA_VERSION: '4' → '5'`。

### 2.5 顺带修正 Q-01

原报告把 `TinyJank` 标为「疑似项目自造、PerfDog 无此指标」。**这个判断错了**：PerfDog 客户端说明书里明确有 `TinyJank(极小卡顿，在高帧率情况下对极小的卡顿进行捕捉)`。所以：

- **命名**是 PerfDog 的，项目注释「PerfDog 口径，逐级递进」在**命名层面成立**；
- **阈值**（`1.5×baseline`）是项目自定的，PerfDog 未公布 —— 注释应只说命名来源，不要暗示阈值也是官方值。

Q-01 由「存疑」改判为「命名已核实、阈值自定」。

## 三、P-04：刷新率档位的主流做法

### 3.1 Android 官方立场：不要猜，去问设备

`developer.android.google.cn/games/optimize/display-refresh-rate-change` 原文：

> 使用方法 **`Display.getSupportedModes()`** 确定设备是否支持 90Hz、120Hz 或其他刷新频率。**如果设备仅支持 60Hz，则无法超出此限制。**

> 您的游戏应**检测当前设备支持的最大显示刷新率**（例如 60Hz、90Hz 或 120Hz），并相应地限制 FPS 设置。

官方给的是**枚举设备实际 mode** 的路径，没有任何「常见刷新率列表」可供硬编码。原因很直接：面板档位是厂商定的，Android 不承诺集合。

同一篇还提到 **Android 15 起游戏默认锁 60Hz**，需应用显式请求高刷——这意味着「设备峰值刷新率」与「本场实际刷新率」可能不同，两者都要能区分。

### 3.2 市场实况：档位集合远不止 7 个，且有非 30 倍数

| 刷新率 | 实际机型（举例） | 证据强度 |
|---|---|---|
| 60 / 90 / 120 | 主流全价位 | 一手（Android 官方文档点名） |
| 144 | 红魔 10 Pro+ 等游戏手机 | 二手（媒体评测） |
| 165 | REDMI K100、ROG Phone 9（系统设置上限） | 一手（ROG 规格页）+ 二手 |
| **185** | ROG Phone 9（Game Genie）、REDMI K100 Pro Max、荣耀 WIN | 一手（`rog.asus.com` 规格页：`Max to 165Hz in system setting / 185Hz in Game Genie`） |
| 240 | 红魔 8S Pro / 8S Pro+ / 12 Pro+ | 二手 |
| 1–120 可变 | LTPO 屏（ROG Phone 9：`LTPO 1~120Hz`） | 一手（ROG 规格页） |

两个反直觉的点：

- **`45` 不是面板刷新率**。手机面板没有 45Hz 这一档；45 是常见的**帧率上限**（游戏画质选项），被误当成刷新率塞进了报告端的表。这一条是纯粹的错配。
- **`100` 没找到手机采用证据**。它更常见于显示器/电视。作为超集保留无害，但不该被当作「必须支持的档位」来论证。

`185` 尤其说明问题：它既不是 30 的倍数也不是 60 的倍数，任何 `Math.ceil(p95/30)*30` 形式的兜底都会把它算错（185 → 210）。

### 3.3 项目链路现状：权威值采到了，但被丢了

采集端（`collector.js:366-375`）已经实现了两路探测，还带 provenance：

```js
const rr = await ADB.getDeviceRefreshRate(this.deviceId);
this._displayProfile = (rr && rr.hz != null)
  ? { refreshRateHz: rr.hz, source: rr.source } : null;   // source: dumpsys-display | settings-system
```

`adb.js:2219-2242` 的实现也符合官方立场——先 `dumpsys display` 取 `mPeakRefreshRate`，取不到再 `settings get system peak_refresh_rate`，都失败才返回 null。注释写得也对：

> 目标帧率的唯一可信来源是设备自报的峰值刷新率，而不是 FPS 序列 P95。锁 30fps 的应用会把 P95 推成 30，但屏幕其实是 120Hz —— 用推断值当目标会把「主动限帧」误判成「达标」。

这段注释把问题说得很清楚。然后：

```
collector.js:473   displayProfile: this._displayProfile,     ← 写进 payload 了
perf.html          grep "displayProfile" → 0 条             ← 报告端从没读
perf.html          grep "refreshRateHz"  → 0 条
```

**整条权威路径在报告侧是死的**。报告仍然只走 `fpsTargetOf()` → P95 → `snapFpsTarget()` 的 7 档表。也就是说，设计意图（用设备值）和实际行为（用推断值）完全相反，而注释描述的正是「不该这么做」的那一种。

### 3.4 主流做法对照

| 工具/平台 | 目标帧率来源 |
|---|---|
| Android 官方建议 | `Display.getSupportedModes()` / 当前 mode 的 `refreshRate` |
| PerfDog | 按设备刷新率归一（高刷设备自动识别，不靠被测应用帧率反推） |
| AndroidX JankStats | `FrameMetrics` 的 `expectedDuration`（即 vsync 周期） |
| **项目现状** | 被测应用自己的 FPS 序列 P95 → 吸附到 7 档表 |

只有项目这一种是**从结果反推目标**，逻辑上是循环论证：应用锁 30fps，P95=30，目标就被判成 30，达帧率 100%，「主动限帧」被记成满分。

### 3.5 推荐修法（按优先级）

> **落地状态**：✅ **已全部实施**（S-01 补齐了当时只做到 2/6 的部分）。
> 第 1 步：`perf.html:deviceTargetHz()` 现读 `data.loading.targetHz`，回退 `target` 前
> 必须校验 `targetSource === 'device-peak-refresh-rate'`，来源不可信一律返回 `null`
> 交本地吸附——不再把推断值当设备值。
> 第 2 / 3 / 4 步：5 份生产副本（`fps-loading.js`、`adb.js`、`perf.html` 两处、
> `library.html`、`backend/utils.py`）已统一为同一张 11 档表 + `ceil(p95)` 兜底。
> 第 5 步：`parsePeakRefreshRate` 上界已放宽到 480。
> 同步断言见 `perf_param_audit_test.js` ⑧~⑩；完整修复记录见
> `Perfara_全项目扫描报告_20261114_r5.md` 第四节。
>
> 以下为当时（修复前）的分析，保留用于说明成因。

1. **首选：报告端读 `displayProfile.refreshRateHz`**。有值就直接当目标帧率，并在报告里标注来源（`dumpsys-display` / `settings-system`）。这一步就能消掉绝大多数误判，且不改任何采集逻辑。
2. **回退：复用采集端的 `REFRESH_RATES` 常量**，不要再维护第二份表。两处同源，`45` 自然消失。
3. **补 `185`**：真实存在且非 30 倍数，当前表必错。
4. **修兜底公式**：`Math.ceil(p95 / 30) * 30` 会把 24fps 视频判成 30、185Hz 判成 210。改为「吸附到档位表中不小于 `p95 × 0.97` 的最小档，都不满足则取 `p95` 向上取整」。
5. **放宽 `parsePeakRefreshRate` 的上界**：现在是 `hz >= 24 && hz <= 240`，360Hz 屏会被判非法而丢弃。建议上界放到 480 或改为「只校验正数且 < 1000」。
6. **区分「峰值」与「本场」**：`peak_refresh_rate` 是设备上限，若系统因省电/热节流降到 60Hz，用峰值当目标会把正常降频算成不达标。理想做法是同时记录当前 mode，报告中两者都给。

> 第 1、2 步只改报告展示口径，但会改变「达帧率」的数值 → 同样需要 `SCHEMA_VERSION` 递增。

## 六、未采纳的说法及原因

| 说法 | 为什么不用 |
|---|---|
| 「SmallJank = 41.66ms，PerfDog 官方」 | 无法在任何独立来源复现；权威原文该节只有 2 条。**41.67ms 只作为推导值推荐，不作为官方口径引用** |
| 「SmallJank 是 Jank 的子集」 | 与「捕捉更细微卡顿」的语义直接矛盾 |
| 「刷新率档位固定为 7 档」 | 官方明确要求枚举设备 mode；市面已有 185Hz 这类非 30 倍数档位 |
| 「45Hz 是常见刷新率」 | 未找到任何手机面板采用；它是帧率上限而非刷新率 |
