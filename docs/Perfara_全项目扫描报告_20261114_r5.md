**为什么 #3 比 #2 优先级更高（架空链路）**：

```
collector.js:369   ADB.getDeviceRefreshRate() 失败 / iOS / PC → _displayProfile = null
        ↓
reports-data-js.js:333  analyseLoading(..., deviceHz=null)  → fromDevice=false
        ↓
fps-loading.js:53       旧 7 档表推出 target（不是设备值）
        ↓
reports-data-js.js:448  data.loading = { target, targetSource, targetHz, ... }
                        targetSource='fps-p95-inferred'，targetHz=null
        ↓
perf.html:2255 deviceTargetHz()  读 data.loading.target，只看「有没有值」，不看 targetSource
        ↓
perf.html:2273 fpsTargetOfSeries() / :2280 fpsTargetOf()   if (dev != null) return dev;   ← 两个入口都直接返回
        ↓
perf.html:2245 snapFpsTarget()（新 11 档表）  在这条链路上执行不到
```

`targetSource` 明明已经写进 data.js（`reports-data-js.js:449`），`targetHz`（仅设备值时非空，`fps-loading.js:160`）也在，但 `deviceTargetHz()` 偏偏读了**语义最模糊**的 `target`。

**影响范围要说准**：有 `displayProfile` 时 `target` 就是设备值，结果是**正确**的——此时 `snapFpsTarget` 不执行也无所谓。真正出错的只有「拿不到设备刷新率」的报告：iOS、PC、历史报告、以及 Android 上 `getDeviceRefreshRate` 探针失败的情况（`collector.js:374` 的 `catch` 会静默置 null）。

**实测复现**（`fps-loading.analyseLoading` 真跑，无设备值 → 走推断）：

| 场景 | `loading.target`（旧表） | perf.html 新表应得 | 达帧率误差 |
|---|---|---|---|
| 100 Hz 屏稳定 99 fps | **120** | 100 | 99% → **82.5%**（−16.5pp） |
| 185 Hz 屏稳定 180 fps | **180** | 185 | 97.3% → **100%**（−2.7pp） |
| 24 fps 视频 | **30** | 24 | 100% → **80%**（−20pp） |
| 48 fps 视频 | **60** | 48 | 100% → **80%**（−20pp） |
| 60 Hz 稳定 59 fps | 60 | 60 | 一致 |

这正是 P-04 当初要解决的问题（「100Hz 机型 / 24·48fps 视频的达帧率被系统性拉低」），**在无设备值的路径上症状原样保留，只是换了个位置发生**。

**另一处同源矛盾**：#4 评分区（`perf.html:3176`）用旧表，且**不受 `displayProfile` 影响**——即使有设备值也照样按 7 档吸附。于是同一份报告里 KPI 卡的目标帧率（走设备值或 `fpsTargetOfSeries`）与评分用的目标帧率可能不是同一个数。同理 #5 报告库对比页、#6 Web 版后端也是恒旧表。

**修法（三步，都很小）**：
1. `fps-loading.js:53` 换 11 档表 + 新兜底（`Math.ceil(p95)`）；
2. `perf.html:2255` `deviceTargetHz()` 改读 `data.loading.targetHz`（该字段只在设备值存在时非空，语义精确），或加 `targetSource === 'device-peak-refresh-rate'` 判断；
3. `perf.html:3176` / `library.html:1762` / `backend/utils.py:195` 三处换 11 档。

**改数值吗**：改。第 1、3 步会改变已发布报告的达帧率与综合得分 → 按 `metric-schema.js:24-27` 的铁律需 `SCHEMA_VERSION` 5 → 6。第 2 步单独做不改数值（只是把「误用推断值」改回「无设备值则吸附」），但它会让 #2 的新表第一次真正生效，所以实际上也改数值。

### S-02（P2）TinyJank 两条通道基准不一致：一个用 p50，一个用 avgMs

| 通道 | 位置 | TinyJank 阈值（修复前 → 修复后） |
|---|---|---|
| 直方图（`dumpsys gfxinfo` timestats） | `adb.js:1682` | `max(vsyncMs, **p50**) * 1.5`（未变） |
| 逐帧（`framestats`） | `adb.js:1777` | `max(vsyncMs, **avgMs**) * 1.5` → `max(vsyncMs, **ftP50All**) * 1.5` |

而 `adb.js:1806-1808` 的注释自己写着：

> 注意 `TINY_JANK_MS` 用的 `avgMs` 是均值基准（长帧会抬高均值），**不能拿来当锚** —— 那正是已修掉的「自我遮蔽」：用 P50 而不是 avgMs。

注释在批评的正是它上面 35 行处正在运行的代码。同一函数里 deadline 已经改用 `ftP50Anchor`（`:1808`），只有 TinyJank 漏了。

**实测复现**（同一份帧序列，两条通道分别算）：

| 场景 | avg | p50 | 逐帧阈值 | 直方图阈值 | TinyJank（逐帧 / 直方图） |
|---|---|---|---|---|---|
| 200×16.67ms + 40×40ms 抖动 + 10×300ms 长卡 | 31.74 | 16.67 | 47.60 | 25.01 | **10 / 50** |
| 同上，长卡增到 40×400ms | 74.76 | 16.67 | 112.15 | 25.01 | **40 / 80** |

第二行暴露了「自我遮蔽」：卡顿从 10 帧增到 40 帧，`avgMs` 被抬高到 74.76，阈值跟着涨到 112 ms，40 ms 的抖动帧全部不再计入 TinyJank——**越卡越测不出来**。

**修法**：`adb.js:1771` 的 `avgMs` 换成 `ftP50Anchor` 的 p50（需要把该变量提前计算）。**改数值**，需 `SCHEMA_VERSION` 5 → 6。
→ **已按此修法落地**，修复后上表两行分别为 **50 / 50** 与 **80 / 80**，见第四节。

**说明（避免过度归因）**：同一复现里 Jank/SmallJank/BigJank 也出现 2 vs 10 的差异，但那是**设计使然**——`adb.js:1657-1660` 已写明「直方图无法还原逐帧前三帧均值，因此用分布中位数做近似」。这条不算缺陷，只有 TinyJank 的基准不一致算。

### 8.1 S-04：白名单怎么改的

`tools/make_release_zip.py` 里原来是：

```python
PRUNE_FLAT_DIRS = {
    'collector/resources/reports/': ('.xlsx', '.xls'),   # ← 黑名单，新产物类型挡不住
}
```

改成：

```python
REPORTS_ALLOW = {'perf.html', 'library.html', 'echarts.min.js'}

if rel.startswith(REPORTS_DIR):
    tail = rel[len(REPORTS_DIR):]
    if '/' not in tail and tail not in REPORTS_ALLOW:
        return 'S-04 报告目录非白名单文件'
```

配套两件事：

- **可见**：命中的文件在打包日志里打 `⚠ 报告目录剔除（不在白名单）: <文件>`。
  静默剔除比漏剔更危险——将来有人往这个目录加交付资源，会以为「打包脚本会自动带上」。
- **可校验**：新增 `check_reports_assets()`，白名单文件少一个就 `SystemExit`。
  白名单的风险方向是「名字写错 → 把交付资源一起挡掉 → 用户打开报告页 404」，
  所以必须在打包前确认这三个文件真的在。

行为测试 `perfara/tests/deep/package_whitelist_test.py`（17 PASS / 0 FAIL）直接调
`pruned()`，覆盖：3 个交付资源保留、`.xlsx/.xls/data.js/data.json/perf2.html` 剔除、
以及 `diagnostics.json` / `trough_export.csv` / `shot_01.png` 这些**尚未存在但将来可能新增**
的产物类型也必须默认剔除——这正是黑名单漏掉的那一类。

  `require('electron')`，纯 node 下用桩顶一下），保证 `samples` / `durationSec` / `kpi` 自洽。

结果 35 PASS / 0 FAIL，且跑完 `history/` 回到原来的 2 份报告。

**`dedupe_metrics` / `shared_report` 的「无 JS 报错」过严**。真机套件跑过之后，
报告引用的低谷截图被清掉，页面留下 3 条 `Failed to load resource: net::ERR_FILE_NOT_FOUND`，
两个用例必红。这是测试数据漂移，不是代码缺陷 —— 截图是可选产物，用户清掉 `shots/`
之后报告仍要能看。改法是把两类错误分开收集：

```js
page.on('pageerror', e => errs.push(e.message));                 // 真 JS 异常

check('无 JS 报错', errs.length === 0);
check('无缺失资源（低谷截图除外）', missRes.filter(u => !/\/shots\//i.test(u)).length === 0);
```

这样既不误报，也仍然抓得住 `echarts.min.js` / `data.js` 缺失。

### 8.6 顺带发现：非标档位的目标帧率会被抬到上一档（未改，待决策）

`loading_algo_consistency.py` 的 B20 原本断言 `snap_fps_target(200) == 210`——那是 S-01
**之前**的规则（`ceil(p95/30)*30`）。S-01 之后实测两侧都是 **240**：

| p95 | 结果 | 说明 |
| --- | --- | --- |
| 180 | 185 | 0.97 容差内向下贴档 ✅ |
| 190 | 185 | 同上 ✅ |
| **200** | **240** | 200 不是规范档位，下一档是 240，容差规则允许「档位高出 20%」 |
| 240 | 240 | ✅ |
| 250 | 250 | 超过最高档才走 `ceil(p95)` ✅ |

**JS 与 Python 两侧结果逐项一致**（各跑 19 个取值比对），所以 S-01 的「5 份副本同源」
仍然成立，B20 只是一条没跟着改的旧断言。已把它改成断言当前规则，并补了
190 / 200 / 240 / 250 四个边界（32 PASS / 0 FAIL）。

**但这暴露一个口径问题**：200Hz 这类非标面板的 target 会被抬到 240，
`fpsReach = 实测 / target` 因此偏低约 17%，用户看到的是「一直没达到目标帧率」。

**没有当场改**，因为它属于派生算法变更，按规矩要递增 `SCHEMA_VERSION`（6 → 7），
而今天已经因 S-01/S-02 从 5 跳到 6，再跳一次会把报告库切成三段。
建议的改法是给「向上贴档」加一个上界：

```js
for (const c of REFRESH_RATES) {
  if (c >= p95 * 0.97 && c <= p95 * 1.10) return c;   // 只贴「略高于实测」的档
}
return Math.ceil(p95);                                 // 200 → 200，而不是 240
```

对现有全部用例无影响（180→185、119→120、190→185、240→240、250→250 都不变），
只影响 p95 落在 187~218 的非标面板。**要不要做，等确认**——一旦改，`SCHEMA_VERSION`
要升到 7，历史报告的目标帧率/达成率会与新报告不可直接比较。
