## 二、新发现（3 项，均有真机数据佐证）

### D-01 非自愿上下文切换**永远采不到**：正则用了不存在的内核字段名（P1）

**代码**（`_client_src/app/src/adb.js:1062-1063`）：

```js
const ctx  = st.match(/^voluntary_ctxt_switches:\s+(\d+)/m);
const ctxNV = st.match(/^voluntary_ctxt_switches_nonvoluntary:\s+(\d+)/m);  // ← 字段名不存在
```

**内核一手证据**（`torvalds/linux` → `fs/proc/array.c:400-401`）：

```c
seq_put_decimal_ull(m, "voluntary_ctxt_switches:\t", p->nvcsw);
seq_put_decimal_ull(m, "\nnonvoluntary_ctxt_switches:\t", p->nivcsw);
```

字段名是 **`nonvoluntary_ctxt_switches`**，不是 `voluntary_ctxt_switches_nonvoluntary`。`/proc/<pid>/status` 里永远不会出现后者，所以 `ctxNV` 恒为 `null`。

**真机佐证**（`_client_src/app/reports/history/20261114-165625-Android_<设备>.js`）：

```
lite -> {'threads': 80, 'swapMB': 54, 'ctxVoluntary': 185131, 'ctxNonvoluntary': None}
lite -> {'threads': 80, 'swapMB': 54, 'ctxVoluntary': 185144, 'ctxNonvoluntary': None}
```

`ctxVoluntary` 正常递增，`ctxNonvoluntary` 全程 `null`——同一份 `/proc/<pid>/status` 里两个相邻字段，一个能读一个读不到，只可能是正则问题。

**为什么一直没被发现**：测试把这个错误字段名当成了断言。

`perfara/tests/accuracy_fixes_test.js:143-145`：

```js
check('FIX-07.3 自愿/非自愿上下文切换解析存在',
  src.indexOf('voluntary_ctxt_switches') > 0
  && src.indexOf('voluntary_ctxt_switches_nonvoluntary') > 0, true);
```

这是「源码字符串嗅探」型断言——只要源码里有这串字符就通过，**与它是否是正确的内核字段名无关**。缺陷因此被测试固化。

**影响**：`mem.ctxNonvoluntary` 在 `metric-schema.js:120-122` 里登记为「非自愿切换速率高 = CPU 争抢」，报告和 Excel 都有这一列，但永远是空的。用户会以为「没发生 CPU 争抢」，而实际是「没测」。

**修复**：

```js
const ctxNV = st.match(/^nonvoluntary_ctxt_switches:\s+(\d+)/m);
```

并把测试改为**用真实 `/proc/<pid>/status` 样本**断言解析结果，而不是嗅探源码字符串。

### D-02 full 通道把四个已读到的字段主动置空，依据不成立（P1）

**代码链路**：

1. `adb.js:1108-1110` —— full 通道的命令**确实读了** `/proc/<pid>/status`：
   ```js
   + 'echo "---PROCSTATUS---"; '
   + (pid ? `cat /proc/${pid}/status 2>/dev/null` : 'true');
   ```
2. `adb.js:1119-1123` —— 解析出来了，但**只取两个字段**：
   ```js
   const lite = parseMemLite(mi, st);
   base.rss = lite.rss;
   base.hwm = lite.hwm;
   return base;            // threads / swapMB / ctxVoluntary / ctxNonvoluntary 被丢弃
   ```
3. `collector.js:551-557` —— 再显式置空，并给出理由：
   ```js
   // FIX-07：dumpsys meminfo 没有 /proc/<pid>/status 的字段 —— 写 null
   return Object.assign({}, full, {
     threads: null, swapMB: null, ctxVoluntary: null, ctxNonvoluntary: null,
     src: 'full',
   });
   ```

**问题在于第 3 步的注释与事实相反**：那条命令里 `cat /proc/<pid>/status` 明明在，数据已经拿到手，只是第 2 步没往外传。

**真机佐证**（同一份报告）：

```
lite -> {'threads': 80, 'swapMB': 54, 'ctxVoluntary': 185131}
full -> {'threads': None, 'swapMB': None, 'ctxVoluntary': None}
```

**影响**：

- `MEM_FULL_REFRESH_MS = 5000`（`collector.js:67`），1Hz 采样下**每 5 拍有 1 拍**这四项为 `null`；
- `mem.threads` / `mem.swapMB` / `mem.ctxVoluntary` 覆盖率被打成约 80%，provenance 会报 `partial`，用户看到「采集期间换了通道」的提示，但真实原因是主动置空；
- 上下文切换是**累计值、由报告层取差**（`metric-schema.js:117-122`）。中间插一个 `null`，取差窗口就被打断，速率曲线出现规律性断点。

**修复**：`getMemInfo` 把四个字段一并带出，`collector._collectMem` 去掉那段置空（改为透传，读不到自然还是 `null`）。改动只影响「有没有值」，不改任何数值语义。

### D-03 GPU 利用率标成「应用口径」，实际是整机口径（P2，但会误导归因）

**代码**（`metric-schema.js:105`）：

```js
{ key: 'gpu', label: 'GPU 利用率', unit: '%', group: 'gpu', scope: 'app',
```

**采集实现**（`adb.js:2779-2803`）全部是**设备级 sysfs 节点**：

```
/sys/class/kgsl/kgsl-3d0/gpu_busy_percentage     ← Adreno 整卡忙
/sys/class/kgsl/kgsl-3d0/gpubusy                 ← 整卡累计 busy/total
/sys/class/misc/mali0/device/utilization         ← Mali 整卡
/proc/mtd_mali/utilization、/proc/ged/hal/gpu_utilization ...
```

没有任何一个是按进程/按 UID 的。**项目自己也知道**——`adb.js:1142` 的 preflight 注释写得很清楚：

> `gpu` —— GPU 负载（**已满载说明有别的应用占着 GPU，测到的是别人的负载**）

**影响**：`buildProvenance` 会把这一项报成 `scope: 'app'`（应用口径），报告里呈现为「本应用的 GPU 利用率」。实测时若后台有相机/游戏在跑，用户会把别人的负载当成自己的，归因直接跑偏。这与网络那项的处理不一致——网络在回退整机口径时会明确降级为 `degraded` 并提示，GPU 却没有。

**修复**：`scope` 改为 `'device'`。改后 `expected` 与实际一致，不会误触发 `degraded`；已确认**没有测试锁住这个值**（`metric_schema_test.js` 只断言覆盖率与质量评级）。

## 三、已核实正确（4 项，本轮新增一手对照）

### V-01 1% Low 算法与 CapFrameX **逐行等价** ✅

**项目实现**（`perf.html:2511-2517`，`reports-data-js.js:394-400` 两处完全一致）：

```js
const ftList = moving.map(v => 1000 / v).sort((a, b) => b - a);   // 帧耗时降序
const k = Math.max(1, Math.round(ftList.length * 0.01));
const worstFt = ftList.slice(0, k).reduce((a, b) => a + b, 0) / k;
oneLow = 1000 / worstFt;
```

**CapFrameX 实现**（`CXWorld/CapFrameX` → `FrametimeStatisticProvider.cs:384-387`）：

```csharp
case EMetric.OnePercentLowAverage:
    metricValue = 1000 / GetPercentageHighAverageSequence(sequence, 1 - 0.01);
// GetPercentageHighAverageSequence (L316-325):
//   var quantile = GetPQuantileSequence(sequence, pQuantile);
//   var subSequenceLow = sequence.Where(element => element >= quantile);
//   return subSequenceLow.Average();
```

即 `1000 / mean(frametimes ≥ P99(frametimes))`——**先对帧耗时取最差 1% 求平均，最后取倒数**，与项目完全一致。关键点在于「对帧耗时求平均」而不是「对 FPS 求平均」（两者是调和平均 vs 算术平均，结果不同），项目选对了。

**CapFrameX 还把三种东西分成了独立指标**（`Contracts/EMetric.cs`），这一点值得项目参考：

| CapFrameX 指标 | 含义 | 项目对应 |
|---|---|---|
| `P1` = "1% percentile" | **FPS 序列**的第 1 百分位 | 无 |
| `OnePercentLowAverage` = "1% low average" | 最差 1% 帧耗时的均值再取倒数 | ✅ 就是项目的 1%Low |
| `OnePercentLowIntegral` = "1% low integral" | 按时间积分口径 | 无 |

也就是说项目的 1%Low **不是** P1，命名上应避免混用。

**遗留局限**（r1 已记录，本轮再次确认根因）：CapFrameX 的输入是**逐帧**帧耗时，项目用的是 **1Hz 采样点**的 FPS 反算。一个 300ms 的单帧卡顿在 1 秒均值里会被稀释，这是「采样点口径」的固有限制，不是算法错误。

### V-02 PSS 解析与 AOSP `getTotalPss()` 一致 ✅

**AOSP 定义**（`platform_frameworks_base` → `core/java/android/os/Debug.java:399-404`）：

```java
/** Return total PSS memory usage in kB. */
public int getTotalPss() {
    return dalvikPss + nativePss + otherPss + getTotalSwappedOutPss();
}
```

**项目解析**（`adb.js:1007-1010`）：

```js
const totalMatch = text.match(/^\s*TOTAL\s+(\d+)/m)
  || text.match(/(?:^|\s)TOTAL\s+PSS:\s*(\d+)/);
```

取 `dumpsys meminfo` 的 `TOTAL` 行**第一个数字**（PSS 列），而不是行内最后一个。注释解释了原因：「取行内最后一个会拿到 SWAP PSS（差数百倍）」。这个处理是对的——`TOTAL` 行的列序是 `Pss Total | Private Dirty | Private Clean | SwapPss Dirty | Rss Total | ...`，取最后一个会拿到 Heap Free 或 Rss，取错列会差一个数量级。

单位换算 `/1024`（KB→MB）也正确。

> 一处细微差异，不构成错误：`getTotalPss()` 含 `SwappedOutPss`，而 `dumpsys meminfo` 的 `TOTAL` 行把 `SwapPss Dirty` 放在单独一列。所以项目的「总 PSS」与 Java API 的 `getTotalPss()` 可能差一个 swap 分量。两者都是通行解读，但若要严格对齐 API，可加 `SwapPss` 列。**建议仅在口径表注明，不必改数值**。

### V-03 「机身温度」不会拿结温冒充 ✅

`adb.js:2640-2651` 的选择链是 `battery → skin → body → board → die`，且 die 分支**返回 `main = null`**：

```js
// 只有芯片结温可读时不编造「机身温度」：返回 null，交给下一级（电池）兜底，
// 否则又会复现「手摸不热却 60 多度」。结温仍在 cpu/gpu 字段里完整保留。
else { main = null; source = 'die'; }
```

这意味着 `tempSource = 'die'` 时 `temperature` 必然是 `null`，不会被 `buildProvenance` 计为已测。设计正确——避免了 Android 上最常见的「把 SoC 结温当机身温度」错误（两者可差 20°C 以上）。

### V-04 进程 CPU 按单核百分比 ✅（r1 已核，本轮仅确认未被破坏）

`calcCpuPct` 分母用 `totalDelta / coreCount`，单核跑满 = 100%，N 核可到 N×100，与 `top` / PerfDog / psutil 同口径，且有测试锁定「不被 100 截断」。

## 四、跨工具命名陷阱（不是缺陷，但会导致对比出错）

### T-01 项目的 `ftP95` ≠ CapFrameX 的 `P95`

- 项目 `ftP95` = **帧耗时**的第 95 百分位（越大越差）；
- CapFrameX `P95` = **FPS 序列**的第 95 百分位（越大越好），实现见 `FrametimeStatisticProvider.cs:361-363`：
  ```csharp
  case EMetric.P95: metricValue = GetPQuantileSequence(fps, 0.95); break;
  ```

同名不同义，且方向相反。跨工具对数据时极易得出相反结论。建议在口径表把项目这列写成「帧耗时 P95（越大越差）」。

### T-02 `jankyRatio` ≠ Android 的「Janky frames」

项目是「帧耗时 > 2×deadline 的帧占比」，`dumpsys gfxinfo` 的 Janky frames 是另一套判定（约 >16ms 或 missed vsync）。r1 已记录，本轮确认仍存在。

### T-03 百分位实现是 nearest-rank，与 NumPy 默认不同

`metric-schema.js:329-333` 与 `adb.js:1545` 都用 `i = ceil(p·n) − 1`（nearest-rank / R-1）。NumPy `percentile` 默认是线性插值（R-7）。大样本下差异很小，但**同一份数据用两套工具算 P95 会有零点几毫秒的差**。不是错误，但跨工具核对时要预期这个偏差。

> 未能确认 CapFrameX 的 `Quantile` 扩展用哪种分位变体（`LinqExtensions.cs` / `CollectionExtensions.cs` 均未命中，仓库内未定位到定义文件）。这不影响 V-01 的结论——`OnePercentLowAverage` 的「取最差 1% 求均值」结构已确认，分位变体只影响边界元素个数。

## 八、一句话总结

本轮最有价值的三个发现都不在「数值算错」，而在**「数据采到了却被丢掉」**：一个正则写错让非自愿上下文切换永远为空，一段依据错误的置空让四个字段每 5 拍丢一次，一个 scope 标签把整机 GPU 负载说成应用负载。三者都不会让报告报错，只会让用户**安静地得出错误结论**——这也是这类工具最难自查的一类缺陷。
