|---|---|---|
| **Q-01** | `TinyJank` 是否 PerfDog 口径 | **命名已核实**：PerfDog 客户端说明书确有 `TinyJank(极小卡顿，在高帧率情况下对极小的卡顿进行捕捉)`；但 PerfDog **未公布阈值**，项目的 `1.5×baseline` 属自定，注释应只说命名来源 |

> `MsRenderPresentLatency` = “The time between the Present() call and when GPU work for this frame completed”。
> 此前的「存疑」来自 presentmon.org 二手文章的转述失真（该文把 `MsUntilRenderComplete` 的「帧起点」口径套到了 `MsUntilDisplayed` 上），而 `MsUntilRenderComplete` 在该官方文档中根本不存在。详见 4.2。

### 2.4 口径局限（不是错误，但会误读）

- **1% Low 的粒度**：项目用 1Hz 采样点的 FPS 反算帧耗时，取最差 1% 的**采样点**。业界标准的 1% Low 是取最差 1% 的**帧**。一个 300ms 的单帧卡顿，在 1 秒均值里会被稀释成 55fps 左右，而逐帧口径会直接掉到 3.3fps。**当前实现会系统性低估单次长卡顿的严重度**。framestats 通道其实拿得到逐帧数据，有条件做逐帧 1% Low。
- **`jankRate` ≠ PerfDog 的 Stutter**：项目 `jankRate = 卡顿帧数 ÷ 总帧数`（帧数比）；PerfDog 的「卡顿率 Stutter」是 `Σ卡顿时长 ÷ 总时长`（时长比）。项目另有 `stutter` 指标且口径正确，但两个名字很接近，报告里应避免都叫「卡顿率」。
- **`jankyRatio` 与 Android 的「Janky frames」同名不同义**：项目是「帧耗时 > 2×deadline 的帧占比」，`dumpsys gfxinfo` 的 Janky frames 是另一套判定（约 >16ms）。跨工具对数据时容易对不上。

## 三、需修正项详解

### P-01 `SmallJank` 阈值方向反了（P1）

**现状**（两条通道都是）：

```js
// adb.js:1659  analyseHistogram（timestats 通道）
const jankMs  = Math.max(2 * baseline, MOVIE_FRAME_X2_MS);  // ≥ 83.33
const smallMs = 84;                                          // ≥ 84
// adb.js:1715  calcJankFramestats（framestats 通道）
const SMALL_JANK_MS = 84;
```

于是判定条件变成 `SmallJank(≥84ms) ⊂ Jank(≥83.33ms)`——**每一帧 SmallJank 都同时是 Jank**，而 `SmallJank` 反而是「更严重的那一半」。

**权威口径**（腾讯 WeTest 官方发布说明，2022-05，PerfDog V7.1）：

> 【创新发布】发布微小卡顿 **SmallJank**，**在 Jank 基础上对细微的卡顿进行捕捉**

同一版本还发布了「稳帧指数 Smooth」。也就是说 SmallJank 的语义是「Jank 抓不到的那些更细的卡顿」，阈值必须**低于** Jank，二者应互斥或包含关系相反。

**补验（2026-11-14 17:40，全网检索）**：PerfDog 的卡顿口径定稿文档《Jank卡顿及stutter卡顿率说明》（`article_detail?id=10162`）中，「PerfDog Jank计算方法」**只有 2 条**——Jank（`>前三帧均值×2` 且 `>1000/24×2≈83.33ms`）与 BigJank（同上且 `>125ms`）。**SmallJank 与 TinyJank 至今只有语义描述，从未公布毫秒阈值**。因此「取得官方公式再按其实现」这条路不存在。

> ⚠️ 检索中出现过一条「SmallJank 第 3 条：>一帧电影帧 41.66ms」的网页摘要，经核为**渲染摘要臆造**：权威原文无此条，精确短语全网无独立来源，且该摘要把 SmallJank 写成「严重卡顿」与定义自相矛盾。**41.67ms 只能作为推导值，不能标注为官方口径。**

**影响**：`SmallJank` 这一列在报告和 Excel 里都在，用户会把它当成「轻微卡顿」，实际读到的是「84ms 以上的重度卡顿数」，结论方向相反。更严重的是：整数直方图桶下 `jankMs = 83.34` 与 `smallMs = 84` 落到同一个桶边界，**SmallJank 实际就是 Jank 的复制品**，两列数值恒等。

**建议**：把三档统一到同一相对条件，只让绝对门槛递进（电影帧 1/2/3 倍）：

```js
const tinyMs  = baseline * 1.5;                              // 自定，PerfDog 未公布
const smallMs = Math.max(2 * baseline, MOVIE_FRAME_X1_MS);   // 41.67 —— 1 帧电影帧
const jankMs  = Math.max(2 * baseline, MOVIE_FRAME_X2_MS);   // 83.33 —— 2 帧电影帧
const bigMs   = Math.max(2 * baseline, MOVIE_FRAME_X3_MS);   // 125   —— 3 帧电影帧
```

这样 `SmallJank ⊃ Jank` 成立（符合「捕捉更细微卡顿」），且四档单调不减。顺带修掉第二处倒挂：`tinyMs = 1.5×baseline` 不设上限，当 `baseline > 56.5ms`（帧率低于约 17.7fps）时会超过固定的 `smallMs = 84`，「极小卡顿」反而比「微小卡顿」更宽松。

> 需如实说明：新档梯是「单调不减」而非「严格递增」。`2×baseline ≥ 83.33`（帧率 ≤ 约 24fps）时 Small 与 Jank 合并，`≥ 125`（≤ 约 16fps）时 Jank 与 BigJank 合并——这是 PerfDog `max(2×基线, 固定门槛)` 公式的固有性质，其自身的 Jank/BigJank 在低帧率下同样会合并。

> 我没有直接改，因为这会改变一个已发布指标的定义，必须配 `SCHEMA_VERSION` 递增。完整调研见 `docs/Perfara_P01_P04_主流做法调研_20261114.md`。

### P-02 PC 进程 CPU 被截断在 100%（P1）

**现状**：

```python
# collect_pc_perf.py:411-414
"cpu": {
    "sysCpu":  round(min(100.0, float(sys_cpu)), 1),   # 整机，0~100，截断正确
    "procCpu": round(min(100.0, float(proc_cpu)), 1),  # ← 进程，不该截断
},
```

**对照 Android 侧**（`adb.js:845-861`）：

```
 *   procCpu = 进程占用，**按单核百分比**（单核跑满 = 100，N 核可到 N×100）
```

并且有测试明确锁定「不被 100 截断」：

```js
// perfara/tests/realdevice/perf_source_audit_test.js:39
check('8 核双核跑满 → 200%，不被 100 截断', cpu(0, 200, 800, 600, 8).procCpu === 200, ...);
```

**影响**：8 核机器上，一个吃满 6 核的游戏在 PC 报告里显示 **100%**，实际是 **600%**，CPU 瓶颈会被完全掩盖；且同一指标在 Android 与 PC 报告之间不可比。

**建议补丁**：

```python
"procCpu": round(float(proc_cpu), 1),   # 进程 CPU 按单核百分比，可 >100（与 Android 一致）
```

改完必须重跑 `tools/compile_pc_collector.py` 重新生成 `Scripts/collect_pc_perf.pyc`，否则运行期仍加载旧字节码。

### P-03 Android「上下文切换」曲线恒为空（P1）

**现状**：Android 模板里有这条曲线（`perf.html:1109`，标题「上下文切换 (次/s)」），归一化读的是：

```js
cswitch: it.cswitch ?? null,   // perf.html:1983 的 series 也读 d.cswitch
```

但**整个 Android 采集链路从不产出 `cswitch`**：

- `_client_src/app/src/` 下只有 `ios-collector.js:101` 出现过这个字段名；
- 真机采样点的实际字段清单里也没有 `cswitch`（见 `perfara/tests/_run_out/realdevice_*.log`）。

**而数据其实是采到的**，只是名字不同。口径表写得很清楚：

```js
// metric-schema.js:111-116
{ key: 'mem.ctxVoluntary',    ... note: '累计值（等 IO / 锁时主动让出）；速率由报告层取差' },
{ key: 'mem.ctxNonvoluntary', ... note: '累计值；非自愿切换速率高 = CPU 争抢' },
```

指标说明（`perf.html:786-788`）也写的是「取进程自愿 / 非自愿上下文切换计数在采样间隔内的差值」。

**结论**：数据采集、口径定义、UI 三样都在，唯独**报告层没有做那个「取差」**，于是曲线永远是空的，解读里的「上下文切换」条目也永远不出现。

**建议补丁**（Android 归一化内，按相邻采样点求速率）：

```js
// 在 Android 的 perf.map 之前维护上一拍
let _prevCtx = null, _prevCtxTs = null;
// map 内：
const ctxNow = (mem.ctxVoluntary != null && mem.ctxNonvoluntary != null)
  ? mem.ctxVoluntary + mem.ctxNonvoluntary : null;
let cswitch = null;
if (ctxNow != null && _prevCtx != null && it.timestamp > _prevCtxTs) {
  const dtSec = (it.timestamp - _prevCtxTs) / 1000;
  if (dtSec > 0) cswitch = Math.max(0, (ctxNow - _prevCtx) / dtSec);
}
if (ctxNow != null) { _prevCtx = ctxNow; _prevCtxTs = it.timestamp; }
// 返回对象里：cswitch,
```

> 与既有约定一致：首拍写 `null`（无基线），计数器回绕时 `Math.max(0, …)` 不报负数。

### P-04 刷新率档位表两处不一致（P1）

**现状**：

```js
// 采集端 adb.js:1472
const REFRESH_RATES = [24, 30, 48, 60, 90, 100, 120, 144, 165, 240];

// 报告端 perf.html:2243（snapFpsTarget，决定「目标帧率」）
for (const c of [30, 45, 60, 90, 120, 144, 165]) { if (c >= p95 * 0.97) return c; }
return Math.ceil(p95 / 30) * 30;
```

**后果**（`达帧率 = 平均FPS ÷ 目标帧率`，目标由这段吸附得出）：

| 实际帧率 P95 | 报告吸附出的目标 | 应有目标 | 达帧率被算成 |
|---|---|---|---|
| 100（100Hz 屏） | **120** | 100 | 83%（假警报） |
| 48 | **60** | 48 | 80%（假警报） |
| 24（24fps 视频） | **30** | 24 | 80%（假警报） |
| 240 | 240 | 240 | ✅ |

采集端认这四档、报告端不认，是明显的漏配。**影响面**：所有 100Hz 机型、以及 24/48fps 的视频类应用，达帧率与「流畅度」评级会被系统性拉低。

**补验（2026-11-14 17:40）——根因比「漏配」更严重**：项目其实**已经采到了权威值**，只是报告端从没消费。

```
collector.js:366-375  ADB.getDeviceRefreshRate() → { refreshRateHz, source }   // dumpsys-display | settings-system
collector.js:473      displayProfile: this._displayProfile,                    // ✅ 写进 payload
perf.html             grep "displayProfile" → 0 条                             // ❌ 从没读
perf.html             grep "refreshRateHz"  → 0 条
```

`adb.js:2219-2242` 的注释把问题说得很准：「目标帧率的唯一可信来源是设备自报的峰值刷新率，而不是 FPS 序列 P95。锁 30fps 的应用会把 P95 推成 30，但屏幕其实是 120Hz —— 用推断值当目标会把『主动限帧』误判成『达标』。」**而报告端的实际行为恰好就是注释里说的那种错法。**

**行业实况**（Android 官方 + 厂商规格页）：

- Android 官方要求用 `Display.getSupportedModes()` **枚举设备实际 mode**，从未给出「常见刷新率列表」可硬编码；Android 15 起游戏还默认锁 60Hz，需应用显式请求高刷。
- 市面真实档位远超 7 个：144（红魔 10 Pro+）、165（REDMI K100 / ROG 9 系统设置）、**185**（ROG 9 Game Genie、REDMI K100 Pro Max、荣耀 WIN）、240（红魔 8S Pro 系列），以及 LTPO 的 1–120 可变。
- **`45` 不是面板刷新率**——手机屏没有 45Hz 这档，45 是常见的帧率上限，被误当成刷新率塞进了表。
- **`100` 未找到手机采用证据**（多见于显示器/电视），作为超集保留无害，但不构成「必须支持」的理由。
- `185` 既非 30 也非 60 的倍数，任何 `Math.ceil(p95/30)*30` 形式的兜底都会把它算成 210。

**建议**（按优先级）：

1. **报告端读 `displayProfile.refreshRateHz`**，有值即作目标帧率并标注来源——这一步就能消掉绝大多数误判，且不动采集逻辑。
2. 回退时**复用采集端 `REFRESH_RATES` 常量**，不要维护第二份表，`45` 自然消失。
3. 档位表补 `185`。
4. 修兜底公式：`Math.ceil(p95/30)*30` 会把 24fps 判成 30、185Hz 判成 210；改为「吸附到表中不小于 `p95×0.97` 的最小档，否则取 `p95` 向上取整」。
5. 放宽 `parsePeakRefreshRate` 的 `hz <= 240` 上界，否则 360Hz 屏会被判非法丢弃。
6. 区分「峰值刷新率」与「本场实际刷新率」：系统因省电/热节流降到 60Hz 时，用峰值当目标会把正常降频算成不达标。

改后需 `SCHEMA_VERSION` 递增。完整调研见 `docs/Perfara_P01_P04_主流做法调研_20261114.md`。

### P-05 Jank 解读的单位写成「次/s」（P2）

```js
// perf.html:3271
parts.push('Jank ' + iFmt(jankMean, 2) + ' 次/s');
```

而 `jank` 的语义在 `adb.js:1941-1946` 已明确改成「本采样周期的卡顿帧数（帧）」，口径表单位也是「帧」：

```js
{ key: 'jank', label: 'Jank', unit: '帧', ... }
```

1Hz 采样时两者数值恰好相等，所以平时看不出来；一旦 tick 被拉长（设备卡顿、看门狗恢复），这句话的单位就是错的。

**建议**：改为 `' 帧'`（或 `' 帧/拍'`）。

### P-06 `isLowActivity` 的 500ms 没有行业出处（P3）

```js
// collector.js:143-146
function isLowActivity(fps, ftP50) {
  return (typeof fps === 'number' && fps <= 2) || (typeof ftP50 === 'number' && ftP50 > 500);
}
```

- `fps <= 2`：合理，1 秒窗口内 2 帧撑不起分布统计。
- `ftP50 > 500ms`：**没有找到对应标准**。Android Vitals 的「冻结帧」门槛是 **700ms**（16ms~700ms 为慢帧，700ms~5s 为冻结帧，>5s 为 ANR）。

500ms 作为「帧分布无统计意义」的工程判据是说得通的（比 700ms 更保守），但注释里没写明这是自定阈值。**建议**：注释标注「工程约定，非行业阈值」，或直接对齐 700ms 以便与 Android Vitals 对照。

## 四、存疑项与撤销项

### 4.1 Q-01 `TinyJank` 是否属于 PerfDog 口径 —— 命名已核实，阈值自定

项目注释（`adb.js:1627`）称「卡顿分级（PerfDog 口径，逐级递进）：TinyJank / SmallJank / Jank / BigJank」。

初版验证时我据 PerfDog V7.1 发布说明（只提 SmallJank 与 Smooth）判断「TinyJank 疑似项目自造」。**补验后推翻**：PerfDog 客户端说明书（`article_detail?id=10089`）明确列有

> `SmallJank(微小卡顿，在Jank基础上对细微的卡顿进行捕捉)`
> `TinyJank(极小卡顿，在高帧率情况下对极小的卡顿进行捕捉)`

所以四档命名**全部属于 PerfDog**，项目注释在命名层面成立。

**但阈值是自定的**：PerfDog 至今未公布 SmallJank / TinyJank 的任何毫秒值（见 P-01 补验）。项目的 `tinyMs = 1.5×baseline` 是自己的选择。

**建议**：注释区分两件事——「命名沿用 PerfDog」与「阈值自定，PerfDog 未公布」。现在的写法容易被读成「连阈值也是 PerfDog 的」。

### 4.2 Q-02 / Q-03 PresentMon 两列的语义 —— 已撤销，项目正确

`collect_pc_perf.py:28-32` 的注释：

```
displayChange  = MsBetweenDisplayChange  上屏节奏           ← ✅ 与资料一致
untilDisplayed = MsUntilDisplayed        Present→上屏（P2D） ← ✅ 已核实正确
inPresentApi   = MsInPresentAPI          Present() 调用耗时  ← ✅ 一致
renderLatency  = MsRenderPresentLatency  Present→GPU 完成该帧 ← ✅ 已核实正确
appStartGap    = MsBetweenAppStart       帧起点间距         ← ✅ 语义相符
```

**一手证据**：Intel `GameTechDev/PresentMon` 的 `README-CaptureApplication.md` 列定义表（第 117–125 行），原文逐字：

| 列 | 官方英文定义 | 对应中文 |
|---|---|---|
| `MsInPresentAPI` | The time spent inside the Present() call | Present() 调用内部耗时 |
| `MsBetweenDisplayChange` | How long the previous frame was displayed before this Present() was displayed | 上一帧显示到本帧显示 |
| `MsUntilDisplayed` | The time between the Present() call and when the frame was displayed | **Present() → 上屏** |
| `MsRenderPresentLatency` | The time between the Present() call and when GPU work for this frame completed | **Present() → 本帧 GPU 完成** |
| `MsBetweenAppStart` | How long it took from the start of this frame until the CPU started working on the next frame | 本帧起点 → CPU 开始下一帧 |

**关键点**：该 README 中 `MsUntilRenderComplete` 的 grep 计数为 **0**——这一列在 CaptureApplication 文档里根本不存在。此前二手文章（presentmon.org）用「帧起点→GPU 完成」来描述它，我据此反推 `MsUntilDisplayed` 的起点应为「帧起点」，属于**基于不存在列的推断**，结论无效。

项目注释的五处标注全部与官方一致，**不需要修改**。
