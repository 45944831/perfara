## 一、本轮已完成

### FIX-11（P0）PC 采集字节码 magic 错配 → 运行期完全不可用

**现象**
`pc_realdevice_test` 从 28 PASS 掉到 **23 PASS / 3 FAIL**（失败项：采集到数据 0 条、字段齐全、
`mem.totalPss > 0`）。直接运行字节码：

```
RuntimeError: Bad magic number in .pyc file
```

即 **PC 端一个数都采不到**，但采集页仍显示「采集中」，属于静默失效。

**根因（三个条件叠加，缺一不可）**

| # | 事实 | 证据 |
|---|---|---|
| 1 | `Scripts/` 目录下**只有 `collect_pc_perf.pyc`，没有 `.py`** | `ls Scripts/` 无 `collect_pc_perf.py` |
| 2 | pyc 由 **Python 3.12** 编译 | pyc 头 4 字节 = `6f0d0d0a` |
| 3 | 运行期内置解释器是 **3.13.12** | `python.exe -V`；期望 magic `f30d0d0a` |

条件 1 使 `pickNewerScript()` 走 `pyc-only` 分支，运行期必然加载 pyc；条件 2/3 使加载即崩。
pyc mtime（12:34）又晚于源码（10:28），即使补了 `.py` 也不会回退。

**为什么既有测试没拦住**
`pc_script_source_test.js` 只断言「pyc 头记录的源大小 == 源码大小」（offset 12 的 uint32）。
那只能证明 pyc 由这份源码编译，**证明不了它能被当前解释器加载**。

**修法**
1. 用内置解释器重编，而不是系统 `python`：
   ```bash
   perfara/collector/resources/ios-tools/python/python/python.exe tools/compile_pc_collector.py
   ```
   输出 `magic ok: f30d0d0a`，体积 12383 → 23024 B。
2. `pc_script_source_test.js` 新增断言：spawn 内置解释器取
   `importlib.util.MAGIC_NUMBER`，与 pyc 前 4 字节比对。

**验收（已通过）**
- pyc magic = `f30d0d0a`，实跑输出 `[collect_pc_perf] PID=5652 采样间隔 1.0s`；
- `pc_realdevice_test` → **26 PASS / 0 FAIL**；
- `pc_script_source_test` 23 → **24 PASS**；
- **反向验证**：把 magic 改回 `6f0d0d0a` → 断言 FAIL（`pyc=6f0d0d0a interp=f30d0d0a`），
  恢复后 PASS —— 证明断言不是恒真。

### FIX-12（P1）速率类指标的 dt 用墙钟，时间回拨会把读数放大 2~10 倍

**现象**
网络 KB/s、FPS（timestats）、gfxinfo 帧增量的分母都是
`Math.max((Date.now() - prev.ts) / 1000, 0.1 | 0.5)`。
Windows 时间同步、用户改系统时间、跨时区都会让墙钟跳变；一旦**回拨**，差值为负并被
**夹到下限**，而计数器增量仍是真实增长 —— 真实 1 秒的窗口按 0.1 秒算，速率 ×10。
表现为偶发尖峰，污染峰值统计、1% Low 与报告结论。

**根因**
`dt` 用了非单调时钟，且用 `Math.max(..., 下限)` 掩盖了「间隔为负」这一异常，
把错误转成了看似合理的数值。

**修法（`_client_src/app/src/adb.js`）**
1. 新增 `monoMs()`（`:3010`，`process.hrtime.bigint() / 1000000n`）。
2. `getNetStats`（`:2231`）：`readAt = monoMs()`；新增 `dtMs = readAt - prev.ts`，
   `!(dtMs > 0)` → 写 `null` 并重建基线（不再夹下限放大）。
3. `getFps`：新增 `mono = monoMs()`；`_fpsState` 增 `mono` 字段；timestats 的
   `dtMs = prev.mono != null ? mono - prev.mono : now - prev.ts`，非正 → `method:'no-frames'`
   并重建基线。
4. `gfxTotalDelta`：调用方改传 `mono`，`dtMs <= 0` → 返回 `null`。
5. `selectFramestatsWindow`（`:1409`）：改传 `mono`，窗口过期判定与 fps 的 dt 同基准。
6. 墙钟仍保留在两处**确实需要真实日期时间**的语义：`timestamp` 展示、
   timestats 的 15s 重试节流（`skipUntil = Date.now() + …`）。
7. `__algo` 导出 `monoMs` 供离线断言。

**验收（已通过）**
新增 `perfara/tests/clock_base_test.js` **20 PASS**：
monoMs 单调性（1000 次无回退）、分辨率（5ms 忙等可分辨）、量级（毫秒而非纳秒/秒）、
代码中不存在墙钟 dt 兜底（排除注释）、四处调用点逐一断言、
墙钟仍保留在节流与时间戳、`selectFramestatsWindow` 对 `now < prev.ts` 判 `stale-window`
而非产出负 dt。
同步更新 `accuracy_fixes_test` 的 FIX-04.1/04.2（原断言写死 `readAt = Date.now()`），46 PASS。

## 二、待修复（本轮确认，尚未实施）

### FIX-13（P1）长间隔被当作「瞬时值」，曲线时间轴被压缩

**现象**
tick 因看门狗恢复、设备休眠、跳过重叠而间隔 10s+ 时，写入的 CPU%、网络速率、GPU 利用率
其实是「这 10 秒的平均」，但采样点语义是「当前值」。曲线看起来平滑，实际是把 10 秒压进 1 个点。

**根因**
- `calcCpuPct`（`:852`）只用 jiffies 差值，不看两次快照隔了多久；
  `_cpuState`（`:819`）存了 `ts` 但从未使用。
- `gpuBusyDeltaPct`（`:2841`）同理，只看 Δbusy/Δtotal。
- `getNetStats` 已用 `dt` 归一化，但未判断 dt 是否异常大。

**建议修法**
1. 状态里统一存 `mono`，计算前先判间隔：
   `if (dtMs > Math.max(3 * intervalMs, 3000)) → 返回 null 并重建基线`
   （CPU / GPU 走这条；网络已有 null 语义，只需加阈值判断）。
2. 采样点增加 `dtMs`（与上一拍 `tickStartTs` 的差），报告层可据此标注
   「本点为 N 秒窗口的平均」或直接剔除异常点。
3. 不改变正常间隔下的数值，只处理异常窗口。

**验收标准**
- 注入「上一拍 10s 前」的状态 → CPU/GPU/网络均返回 `null`，且基线已更新；
- 正常 1s 间隔数值与现在完全一致（逐点对比无差异）；
- 新断言进 `clock_base_test` 或独立用例。

### FIX-14（P2）CPU 频率读的是 governor 目标频率，不是实际运行频率

**现象**
`getCpuSnapshot`（`:878`）读 `/sys/devices/system/cpu/cpuN/cpufreq/scaling_cur_freq`
（`:889`、`:891`）。该节点是 **cpufreq governor 当前设置的目标频率**，DVFS 快速切换或
被限频时，与核心实际运行频率可能差一个档位。

**建议修法**
优先读 `cpuinfo_cur_freq`（部分设备需 root/内核支持），失败回退 `scaling_cur_freq`，
并在返回值里带 `freqSource: 'cpuinfo' | 'scaling'`，进 provenance 的 `sources`，
让报告能说明「这条频率曲线的精度等级」。

**验收标准**
- 两源都不可读 → `null`，不写 0；
- 只 `scaling_cur_freq` 可读 → 正常返回且 `freqSource='scaling'`；
- 两源可读时取 `cpuinfo`，逐核仍按 `cpuN` 名称配对（不得按下标）。

### FIX-15（P1）`Scripts/` 下没有 `.py` 兜底，pyc 一旦不可用即无路可退

**现象**
FIX-11 的根因防护。发布形态下 `Scripts/` 只有 `collect_pc_perf.pyc`，
magic 错配或字节码损坏时，`pickNewerScript` 没有任何可回退的源码。

**建议修法（二选一或都做）**
1. `tools/compile_pc_collector.py` 编译后**同时把 `.py` 复制到 `DST` 同目录**，
   使 `resolvePcScriptPy()` 有货可回退（体积 +18KB，可忽略）。
2. 运行期捕获 `Bad magic number` / `ImportError`，自动改用 `.py` 重试一次，
   并打日志提示「字节码不可用，已回退源码，请重编」。

**验收标准**
- 删除 pyc 后仍能正常采集（走 `.py`）；
- 把 pyc magic 改坏后能自动回退并给出可见提示（不是静默）；
- `pc_script_source_test` 增对应断言。

### FIX-16（P2）`isLowActivity` 把真实 2fps 重度卡顿标成「低活动」

**现象**
`collector.js:143` 的 `isLowActivity(fps, ftP50)` 在 `fps <= 2` 时清空 9 个帧分布指标。
真实的重度卡死（加载、GC 停顿）恰好也是 2fps，于是报告显示 `--`，用户容易读成「没测」。

**说明**
这是**有意设计**：1s 窗口只有 2 帧，帧分布确实没有统计意义（否则会算出
`jankyRatio=100%`、`overrunMax≈3000ms` 这类物理上不可能的值，即 FIX-01 修的问题）。
所以不建议改判定逻辑，而是改**表达**。

**建议修法**
报告层区分两种空值语义：
- `fpsMethod='low-activity'` → 文案「帧数不足，未统计分布」+ 保留 fps 实测值；
- `fpsMethod='no-frames'` → 文案「本周期无渲染帧」。
两者都不显示裸 `--`。

**验收标准**
- 构造 `fps=2` 的采样点 → 报告卡片显示「帧数不足」而不是 `--`，且 fps 仍展示；
- 构造 `fps=null` → 显示「无渲染帧」；
- 两者在 Excel 里也不为空字符串歧义。

### FIX-17（P2）framestats 窗口过期判定用配置周期，而非实际周期

**现象**
`selectFramestatsWindow`（`:1409`）的 `maxGap = max(intervalMs/1000 × 2.5, 3s)`
（`FRAMESTATS_MAX_GAP_FACTOR = 2.5`，`:1398`）。`intervalMs` 是**配置值**；
门闩跳过重叠导致实际周期 2× 时仍可容忍，3× 以上会把正常窗口判成 `stale-window`，
降级到精度更低的 gfxinfo 增量通道。

**建议修法**
`collector.js` 把「上一拍实际周期」传给 `getFps`（已有 `tickStartTs` 可直接算），
用它替代配置 `intervalMs` 参与 `maxGap` 计算；配置值仅作首拍缺省。

**验收标准**
- 实际周期 3× 配置值时，窗口仍判 `usable`；
- 真正过期（如应用后台 30s）仍判 `stale-window`；
- 离线用例覆盖 1× / 2× / 3× / 真过期四档。
