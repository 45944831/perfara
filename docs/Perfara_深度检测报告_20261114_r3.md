## 二、D-01：FIX-16 的报告文案是死代码（P1）

### 现象

`perf.html` 的解读区写了两种「帧分布为空」的说明文案，但**无论数据如何都不会出现**。

### 根因

文案读的是采样点的 `fpsMethod`：

```js
// perf.html:3485
const lowN  = pts.filter((p) => p.fpsMethod === 'low-activity').length;
const noneN = pts.filter((p) => ['none', 'no-frames', 'timestats-init', 'error']
  .includes(p.fpsMethod)).length;
```

但 `pts` 是 `perf.map(...)` 产出的**归一化对象**，其字段是白名单式的，原实现只有 `fps`、`jank`、`bigJank` … **没有 `fpsMethod`**。于是 `lowN` / `noneN` 恒为 `0`，两句话永远不渲染。

`fpsMethod` 由 `_client_src/app/src/collector.js:754/766` 写入，且在采样白名单内（`collector.js:155`），采集端没问题——**断在报告页的归一化**。

### 修复

`perf.html:4082`（Android 归一化）补一行：

```js
fpsMethod: it.fpsMethod ?? null,
```

并加注释说明**为什么只加在 Android**：

- iOS 采集端没有帧分布指标（无 `ftP50` / `jankyRatio` / `hitchMsPerSec`），不存在 `low-activity` 语义；
- PC 的 `pcExtra.fpsSource` 语义是「采集通道是否可用」（`none` = PresentMon 不可用），与「本周期没有渲染帧」不是一回事，混用会给出**错误结论**。

### 验证

新增 `[D]` 用例（`perfara/tests/e2e_metric_config/run_perf_html_test.js`）：构造 3 拍 `low-activity` + 2 拍 `no-frames` + 3 拍正常，实渲染后取 `#insight-box` 全文断言。

修复后真实渲染文案：

```
8 个采样点 · 采样间隔不恒定（含采集耗时） · 3 拍帧数不足（帧分布未统计，FPS 为实测）
· 2 拍无渲染帧 · 有效时长 4 秒 · 已排除 1 段加载 3s
```

结果：`23 passed / 0 failed`（当时），补 D-02 后为 `26 passed / 0 failed`。

## 三、D-02：ADPF「热节流」解读是死代码（P1）

### 现象

采集端确实读到了系统的热节流等级，但报告解读里**从来没有「热节流」这一条**。

### 根因

同一类缺陷。解读块读 `thermalStatus` / `coolingValue`：

```js
// perf.html:3340
const stCol = iNums(pts.map(p => p.thermalStatus)).filter(v => v != null);
// perf.html:3344
const coolVals = iNums(pts.map(p => p.coolingValue)).filter(v => v != null);
```

而 Android 归一化对象里同样没有这两个字段 → `stCol.length` 恒为 `0` → 整块跳过。

值得注意的是：**现有测试抓不到它**。`perf_source_audit_test.js:314` 只验证了「采集端写入 `data.thermalStatus`」，`metric_schema_test.js:40` 只验证了「口径表登记了 `thermalStatus`」，**没有任何用例验证报告页渲染**。

### 修复

`perf.html:4098-4099` 补两行，并注明 `null` 的语义：

```js
thermalStatus: it.thermalStatus ?? null,
coolingValue: it.coolingValue ?? null,
```

> `null` = ROM 未暴露该节点 → 报告不显示该条；**不能折成 0 级「未节流」**，那是把「没测到」说成「没问题」。

### 验证

新增 `[E]` 用例：8 拍中前 4 拍 `thermalStatus=3 / coolingValue=12`，其余为 0。

- `PASS 解读出现「热节流」条目`
- `PASS 节流等级与命中拍数正确（峰值 3 级，4/8 拍）`
- `PASS E 无 JS 报错`

**反向验证**：临时移除这两行归一化 → 用例失败 2 条（`RESULT: 24 passed, 2 failed`）；文件按 md5 原样还原（`df2fb873a4dd65ca3971dea10d79caaa`）。证明这条守卫不是空转。

## 四、D-03 / D-04：两处测试自身缺陷

### D-03 `clock_base_test` 断言过度耦合（P2）

批量里 `clock_base(exit=1)`，单独跑 `19 PASS / 1 FAIL`。

失败项：`framestats 窗口用 mono 判定`。原断言把第 4 个实参名写死：

```js
/selectFramestatsWindow\(frames, _fsState\.get\(key\), mono, intervalMs\)/
```

而外部修复（FIX-17）已把该实参改名为 `effInterval`——因为语义确实变了（改用「上一拍实际周期」，配置值仅作首拍缺省，见 `adb.js:1819`）。这是**合理的实现变更**，断言却在纯重命名时误报，反而会掩盖真正的墙钟回流。

修复：只钉住意图（第 3 个实参必须是 `mono`），不钉第 4 个实参的名字。

反向验证（对真实源码做字符串变异）：

| 变异 | 断言结果 | 期望 |
|---|---|---|
| 真实源码 | `true` | 通过 |
| `mono` → `Date.now()` | `false` | 失败 ✓ |
| `mono` → `now`（墙钟变量） | `false` | 失败 ✓ |
| `effInterval` → `intervalMs`（纯重命名） | `true` | 不误报 ✓ |

结果：`20 PASS / 0 FAIL`。

### D-04 `serialize_bench` 计时断言在批量负载下翻盘（P2）

批量里 `serialize_bench(exit=1)`，单独跑 `13 通过 / 0 失败`。

根因：对同一次 `JSON.stringify` 只测**单次**，然后断言 `tCompact < tPretty`。批量并行跑时一次 GC / 调度停顿就能让 compact 反而报「更慢」。

修复：改为**3 次取最小值**（最优值反映代码路径本身，不受单次长停顿影响）。连续 3 次实测：

```
indent=2 15.1ms → 无缩进 11.2ms  PASS
indent=2 14.6ms → 无缩进 10.0ms  PASS
indent=2 14.3ms → 无缩进 10.9ms  PASS
```

## 五、纠正一处历史误判：`perf2.html` 温度口径

`docs/交付清单-采集数据可信度与性能专项-20261105.md:199` 记为遗留问题：

> `perf2.html` 仍是旧温度回退口径（`pickTemp` 回退 `battery.temperature`），与已修的 `perf.html` 不一致。

本轮核对后确认**该记录不成立**，三条证据：

1. `perf2.html` 的 `CONFIG` 只有 `android` / `ios` / `ios_gpu`，**没有 `pc`**（`grep -c '"pc"'` = 0）。当初 `perf.html` 要禁掉回退，针对的是 **PC** 的 `battery.temperature` 曾是 CPU 结温；perf2 不存在这个路径。
2. `perf.html` 的 **Android** 分支本身就用 `pickTemp(it.temperature, bat.temperature)`，注释写明「Android 的 battery.temperature 来自 dumpsys battery，同样是机身/电池温度，可作为老报告的回退」。两者**口径一致**。
3. `perf2.html` 没有解读区（`insight-box` 出现 0 次），因此 FIX-16 文案「未同步」也不成立——它根本没有这段 UI。

> 结论：perf2 无需改动。历史记录已按此更正。
