## 三、真包采集 + 参数准确性

新增用例 `perfara/tests/realdevice/param_accuracy_pkg.js`（按 `PERFARA_PKG_ROOT` 指向解包目录）。
它做三件事：启动**包里的** collector → UI 驱动真机采集 60s（前 8s 跑重载页制造加载段）→
停采后把 `data.js` 与包里 `perf.html` 渲染出的页面数字，同 adb 独立基准逐项对齐。

### 3.1 基准怎么来的（不复用包内代码）

| 参数 | 包内来源 | 独立基准 |
|---|---|---|
| FPS | SurfaceFlinger timestats 图层帧数 | 采集前 `--timestats -clear`，跑完读该图层 `totalFrames ÷ 窗口秒数` |
| 进程 CPU | `/proc/stat` + `/proc/<pid>/stat` 差值 ÷ 单核时长 | 同一份文件，本用例自己解析、自己算 |
| 内存 PSS | `dumpsys meminfo` App Summary | 同一条命令，本用例自己解析 |
| 刷新率 | `dumpsys display` | 三路：`settings get system peak_refresh_rate`、支持模式最大 fps、`timestats` 的 `displayRefreshRate` |

> 为什么不用 `gfxinfo framestats`：Chrome 的网页内容帧不在被测进程的 UI 线程里，实测包内 111fps 时
> gfxinfo 只有 19fps，差 5 倍。第一版用例踩过这个坑，已换成 SurfaceFlinger 呈现帧。

## 四、两个缺陷

### D-19 刷新率取错字段：120Hz 面板报成 90

`src/adb.js` 的 `parsePeakRefreshRate()` 正则：

```js
/(?:mPeakRefreshRate|peakRefreshRate|peak_refresh_rate|mPeakRefreshRateHz)\s*[=:]\s*([0-9]+(?:\.[0-9]+)?)/i
```

`i` 标志下 `peakRefreshRate` 会命中 `mDefaultPeakRefreshRate: 90.0` —— 那是 **DisplayManagerService
的框架默认常量**，与面板能力无关。本机实测四路取值：

| 来源 | 值 |
|---|---|
| 当前正则（命中 `mDefaultPeakRefreshRate`） | **90.0** ← 实际采用 |
| `PRIORITY_USER_SETTING_PEAK_REFRESH_RATE … maxRefreshRate=` | 120.0 |
| `settings get system peak_refresh_rate` | 120.0 |
| `supportedModes` 最大 fps | 120.00001 |
| `SurfaceFlinger --timestats` 的 `displayRefreshRate` | 120 |

**影响**：`displayProfile.refreshRateHz=90`，目标帧率按 90 算时「达帧率」= 110/90 = **122%**（超过 100%），
低帧阈值也会从 96 掉到 72。这不是本机个例 —— 只要 ROM 的 `mDefaultPeakRefreshRate` 与面板峰值不同就会错。

### D-20 `data.js` 从未写入加载段，报告侧「设备自报刷新率优先」整条链失效

`perf.html` 的 `deviceTargetHz()` 读的是 `data.loading.targetHz`：

```js
const L = (typeof data !== 'undefined' && data && data.loading) || null;
if (!L) return null;          // ← 实际永远走这里
```

而 `main.js` 组装 payload 时只有 `displayProfile`，没有 `loading`；`writeDataJs()` 也不会补。
查历史 4 份报告，**全部 `loading=no`**。于是目标帧率永远退回「FPS 序列 P95 吸附」，
v1.5 的 P-04「设备自报优先」在报告侧是死代码。

**两个缺陷互相掩盖**：D-20 让报告不用 `displayProfile`，所以 D-19 的 90 没有暴露到页面上；
本轮报告页显示「目标 120」是 P95 推断的巧合。**只修 D-20 会更糟**（目标变 90、达帧率 122%），
必须两个一起修。

## 五、修法（已按此实施，见第八节）

1. `parsePeakRefreshRate()` 加负向断言排除 `mDefault*`，并优先取
   `PRIORITY_USER_SETTING_PEAK_REFRESH_RATE … maxRefreshRate=`；`getDeviceRefreshRate()`
   把 `settings get system peak_refresh_rate` 提到 `dumpsys display` 之前；两者都没有时用
   `supportedModes` 的最大 fps 兜底。
2. `preparePayload()` 里补 `loading` 段（`analyseLoading(fps, undefined, displayProfile.refreshRateHz)`），
   让 `data.js` 带上 `target / targetSource / targetHz / excludedSamples / segments`。

两项都改会改变目标帧率与「达帧率 / 低帧占比 / FPS≥目标」的数值，按项目规矩要决定是否递增
`SCHEMA_VERSION`（6 → 7）。若同时做「非标档位 200→240」的上界修正，可合并成一次跳版。

### 8.7 口径变更影响面：同一份真机样本跑两版实现

只跑「改后全绿」不足以说明改对了 —— 还得证明**改到的就是该改的那几项**。
做法：取 v1.7 采集到的 70 点原始样本（`data.js` 里的 `perf` 数组，不做任何加工），

| KPI | v1.6（出厂） | v1.7 | 说明 |

`fps` / `fps1Low` / `fpsStd` / `fpsFrameTime` / `ftP50~P99` / `jankyRatio` / `hitchMsPerSec` /
