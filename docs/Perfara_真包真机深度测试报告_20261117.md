## 三、真缺陷 D-21：60Hz 面板机被 framework vote 误报成 120Hz

### 3.1 根因

`_client_src/app/src/adb.js` 的 `parsePeakRefreshRate()`（D-19 于 2026-11-15 修复版）按可信度依次取：

```js
const patterns = [
  /PRIORITY_USER_SETTING_PEAK_REFRESH_RATE[^\n]*?maxRefreshRate\s*=\s*([0-9]+(?:\.[0-9]+)?)/,  // ①
  /(?<!Default)\bmPeakRefreshRate(?:Hz)?\s*[=:]\s*([0-9]+(?:\.[0-9]+)?)/,
  ...
];
```

**本机 `dumpsys display` 实测**：

| 字段 | 值 | 语义 |
|---|---|---|
| `PRIORITY_USER_SETTING_PEAK_REFRESH_RATE -> Vote{maxRefreshRate=120.0}` | 120 | framework 的**范围上限 vote**，非面板能力 |
| `mDefaultPeakRefreshRate: 120.0` | 120 | framework 默认常量（已被 D-19 负向断言排除） |
| `mDisplayModeSpecs primaryRefreshRateRange=[0 120]` | 120 | 允许的刷新率区间上界 |
| `supportedModes[]` 三档 `fps=60.000004` | **60** | **面板物理能力**（唯一可信） |
| `SurfaceFlinger displayRefreshRate` | 60 | 当前实际刷新率 |
| `settings get system peak_refresh_rate` | null | 用户未设置 |

D-19 当初针对的 120Hz 设备，`supportedModes` 含 120 档，取 ① 恰好正确；但这台 60Hz 面板机的 `PRIORITY_USER_SETTING_PEAK_REFRESH_RATE` vote 是 framework 写入的**默认上限 120**（`settings` 为 null 证明用户未主动设置），面板根本不支持 120Hz。于是 ① 命中 120，被 `getDeviceRefreshRate()` 作为 `dumpsys-display` 来源采信。

### 3.2 影响面

- `displayProfile.refreshRateHz=120` → 报告 `loading.targetHz=120` → 目标帧率、达帧率、低帧占比、FPS≥目标占比全部按 120 算；
- 60Hz 屏理论上限 60，按 120 算让"达帧率"凭空腰斩（实测 48%），是**可自证的缺陷信号**（与 v1.7 报告里"达帧率>100% 一定取错"对称：这里是"60Hz 屏达帧率长期<50%"）；
- 不改变原始采样（FPS/CPU/PSS/卡顿均准确），只改变目标帧率派生项。

### 3.3 建议修法（未实施）

以 `supportedModes` 最大 fps（面板物理能力）作为**硬上界**约束 vote：

1. `getDeviceRefreshRate()` 读到 `PRIORITY_USER_SETTING_PEAK_REFRESH_RATE` / `mPeakRefreshRate` 的 hz 后，再解析同一次 `dumpsys display` 的 `supportedModes` 最大 fps（`panelCap`，已有 `parseMaxSupportedFps()`）；
2. 若 `hz > panelCap × 1.1`（容浮点噪声，如 120.00001），判定为 framework vote 虚高，**回退到 panelCap**、source 标 `display-supported-modes`；
3. `settings get system peak_refresh_rate` 有明确值时仍优先（用户真实的档位选择），但同样受 panelCap 上界约束；
4. 补离线守卫：构造"60Hz modes + 120Hz vote"的 dump 文本，断言 `parsePeakRefreshRate` 结果被 panelCap 钳到 60；保留 120Hz 设备（modes 含 120）不被误钳；
5. 因改变目标帧率派生口径，按项目铁律 `SCHEMA_VERSION` 7→8，更新 `tests` 中的版本守卫与 `tools/inject_metric_info.py`。

## 四、5 个环境性 FAIL 的逐项归因（均非 v1.9 包缺陷）

| 套件 | 批跑结果 | 归因 | 证据 |
|---|---|---|---|
| `fps_render` | 10/4 | 采样瞬间 Chrome 无可见渲染层（`timestats 未匹配层`） | **受控重跑**：先把 Chrome 拉到前台（`mCurrentFocus=...Chrome.Main`）后 14/0；同机同包 `param_accuracy` 能取到 3691 帧 |
| `tinyjank` | 7/2 | 目标是 `com.android.settings`，framestats 只解析到 2 帧（<20），采样时该页无持续渲染 | 同机 Chrome 走 timestats 通道正常出帧；属被测页当时无渲染层 |
| `preflight_real` | 19/1 | 断言写成 `gpu===null \|\| typeof gpu==='object'`，但测试名是"为数值或 null"；实测 `gpu=15`（数值）被误判 | 断言与测试意图自相矛盾，与包无关；跑的是源码 |
| `net_scope` | 18/1 | 断言假设"默认视图解析不出 per-UID 计数"，但该 ROM 默认视图有 1MB 输出含 UID 行 | ROM 行为差异使测试假设不成立；带 `--uid` 的正式通道正常 |
| `trough_shot` | 11/17 | 本轮未形成低谷（帧率稳定 60），故无截图可生成，连锁 17 项 | `trough_overrun` 26/0 证明截图/落盘逻辑正常；`param_accuracy` 里 adb screencap 成功出合法 PNG |

以上套件跑的都是仓库源码（非包内 asar）。唯一真正用 v1.9 包的 `param_accuracy_pkg` 已单列 D-21。
