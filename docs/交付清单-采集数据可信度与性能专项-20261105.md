## 3. 修复明细与证据

### 专项 A：温度采集口径

**现象**：客户端「温度」显示 60 多度，但机身摸着不热。

**真机证据**（MTK 平台，`dumpsys thermalservice`）：CPU/GPU/NPU 结温 61~66.5°C，BATTERY 36~39°C，SKIN 外壳估算 49.5~52.4°C。旧 `parseThermalService` 优先级是 CPU → SKIN → BATTERY，把**芯片结温**当机身温度展示。结温比外壳高 20~30°C 属物理常态，不是设备过热。

**修复**（`adb.js:1658-1863`）：
- 主温度改为 `BATTERY > SKIN > bodyRows > nonDieRows`，纯结温场景 `main = null` 且 `source = 'die'`，不拿结温顶替机身温度；
- CPU/GPU 结温、SKIN 估算单独返回 `cpuTemp / gpuTemp / skinTemp / tempSource`；
- 采集顺序改为 `dumpsys thermalservice` → 具名 sysfs 机身/电池热区 → `dumpsys battery` → `null`；
- 匿名 `thermal_zoneN/temp` 不再无差别求平均（多为 CPU 各核结温，会系统性抬高机身温度）；
- `normalizeThermalSysfsTemp()` 兼容毫度(36500)/十分度(340)/度(36)，旧版只认毫度。

**顺带修**：`getBatteryInfo` 的取值正则未锚定行首，命中 `Max charging voltage: 5000000` 导致电压/功耗荒谬，改为 `^\s*key:`。

**展示层同步**：客户端温度卡片改为主数值 + 单位来源 + 「外壳 xx° · 结温 xx°」小字；告警阈值 50/65 → 45/50；报告页温度图新增橙色「CPU 结温」序列与机身温度红色序列并列；PC 端明确标注「CPU 结温」、阈值 75/90，不再回退 `battery.temperature`。

**验证**：`thermal_source_test.js` 52 PASS（含 die-only `main === null`、sysfs 单位三态、CSV 空值语义）；真机 3 次采样主温度 39°C = 电池温度，结温差 27.5°C；`voltage 4000 mV / power 2156 mW` 恢复合理。

### 专项 B：采集数据可信度（单位 / 假 0 / 语义错配）

**真机单位证据**（Android 13 中端机型）：`dumpsys battery` 无 `current now`，`voltage: 4`(V)、`temperature: 340`(十分度)；sysfs `current_now=-227`、`current_max=2000`、`voltage_now=4281` → 该机是 **mA / mV 量级**，而 AOSP 标准机型同名字段是 µA / µV。结论：不能只看数值猜单位，改以设备自报 `current_max` 量级为主判据，数值阈值仅兜底。

**确认并修复的 6 类误导项**：

1. `perf.html` 的 `a_ua_to_ma` 无条件 `/1000`，而采集端 `currentNow` 已是 mA（CSV 列名即 `currentNow_mA`）→ 报告电流整整小 1000 倍。改为按量级自适应 `a_cur_to_ma()`。
2. `getCpuStats` 读不到进程 stat 时写 0 → 下一帧 `(current - 0)/totalDelta` 被 clamp 成假 100% CPU。首帧 / 读失败 / 计数器回绕一律 `null`。
3. `getMemInfo` / `getBatteryInfo` / `getNetStats` / `collector.js` 把「未测量」写成 0 → 全改 `null`；网络首帧与回绕不再报 `0 KB/s`。
4. 电压补 µV 兼容；电流保留充放电负号（`power` 用 `Math.abs`）；抽成纯函数 `normalizeBatteryVoltageMv` / `normalizeCurrentMa` 放入 `ADB.__algo` 供离线单测。
5. 网络接口白名单扩展，补齐 MTK `ccmni*`、老高通 `rmnet0`、USB 共享 `rndis*` / `eth*`，修「用蜂窝数据时流量一直 0 KB/s」。
6. `Total frames rendered` 正则加行首锚定；CPU 各核心频率按 `cpuN` 名称配对（glob 字典序与 `/proc/stat` 顺序不一定一致，10 核以上尤其明显）；`gfxinfo-delta` 只数帧、测不到卡顿，jank 族改 `null`；报告页电流/功耗图表 `?? 0` → `?? null`（不画假的 0 线）。

**数据通道**：`collector.js` 的 `ANDROID_METRIC_KEYS.temp` 扩展为 6 个字段；`exporter.js` CSV 新增 `deviceTempSource`、`skinTemp_est`、`cpuTemp_die`、`gpuTemp_die` 四列；`pc-collector.js` 无电池时整组置 `null`。

**验证**：`thermal_source_test.js` 52 PASS、`jank_algo_test.js` 41 PASS、`pc_realdevice_test.js` 28 PASS。真机复验：`battery {level:100, voltage:4000, temperature:34, currentNow:-36, power:144}`、网络首帧 `null` 次帧 3 KB/s、CPU 首帧 `null` 次帧 3%、`cores.usage` 首帧 `null` 次帧 `[6,8,6,6,4,0,1,3]`、`freq` 逐核不同、`thermal {temperature:34, source:battery, cpuTemp:38}`。

### 专项 C：采集期曲线图上下滑动卡顿

**根因**（读本机 ECharts 6 `lib/component/helper/RoamController.js` 确认）：每张图 `dataZoom inside` 配了 `moveOnMouseWheel: true`，`_mousewheelHandler` 对**每个**滚轮事件都置 `shouldMove=true` → `_checkTriggerMoveZoom` → `eventTool.stop(e.event)` 吞掉页面滚动并触发整张图（数千点）重排重绘；11 张图叠加即严重卡顿。次要原因：每秒给全部 11 张图回传全量数组做 `setOption`；`ResizeObserver` 一回调就给全部图 `resize()`；`MAX_RENDER_POINTS=2000`（可到 4000 点）。

**修复**（`charts.js`，关键锚点见括号）：

1. 两个 option builder 的 `dataZoom inside` 改 `moveOnMouseWheel:false` / `moveOnMouseMove:false` / `zoomOnMouseWheel:'shift'`（`:707`、`:762`），普通滚轮与触摸拖动交还页面，缩放改 Shift+滚轮或底部 slider。
2. `update()`（`:364`）拆成 `_appendPoint`（只写内部 state）+ `_scheduleFlush`（`:338`）；`IntersectionObserver`（`:304`，root=`.charts-grid`，rootMargin 160px）只对视口内图表 `setOption`，滚入视口时一次性补齐历史并 resize。
3. 滚动空闲窗口 `RENDER_IDLE_MS=120`、最小刷新间隔 `RENDER_MIN_GAP_MS=200`、持续滚动 `RENDER_MAX_DEFER_MS=1000` 兜底补画（`:57-61`、`:283`）。
4. `ResizeObserver` 改 debounce + 容器宽高未变则整批跳过。
5. `MAX_RENDER_POINTS` 2000 → 900（`:48`，上限 1800 点）；`LAZY_OPT = {lazyUpdate:true, silent:true}`（`:54`）。
6. `toNumOrNull()`（`:67`）让未测量值写 `null`，tooltip 显示 `--`，曲线断线，不再折成 0。
7. **顺带修旧 bug**：`_decimateIfNeeded` 原先把 tag 下标减半放在逐图调用里，一次采样 11 张图会连除 11 次把场景标记塌成 0；改为 `update()` 内 `_halveTags()` 只做一次。
8. 动态核心图 option 重建改 `notMerge:true`，延后到可见时执行。

**交互变化（需告知使用者）**：不能在图上按住鼠标拖动平移 dataZoom；改用底部 slider / 手柄，或 Shift+滚轮缩放。已在操作手册 FAQ 补 2 条说明。

**验证**：新增 `chart_scroll_perf_test.js` 34 PASS，覆盖「`update()` 同步阶段零 `setOption`」「9 张不可见图完全不 `setOption`」「滚动活跃期不重绘」「停止后补画」「持续滚动超 1s 兜底」「抽稀上限 ≤1800」「一次采样 tag 只减半一次」「`reset()` 不残留脏状态」。

### 专项 D：性能参数「错误采集」复查（8 类）

这一轮查的是**参数本身算错**，不是「未测量写 0」。完整读 `adb.js`(约 2050 行) / `collector.js` / `pc-collector.js` / 两个报告页 / 采集页卡片与图表。

| # | 问题 | 根因 | 修复（源码锚点） |
|---|---|---|---|
| 1 | 进程 CPU 偶发假 100% | `/proc/<pid>/stat` 的 `comm` 可含空格/右括号，旧 `split(/\s+/)` 固定取 `p[13]/p[14]` 会错位到 ppid / 缺页计数 | `parsePidStat()`（`:733`）用 `lastIndexOf(')')` 后重新编号，utime=rest[11]、stime=rest[12] |

## 9. 第二阶段：采集源审计（错采 / 漏采 / 重复采集）

> 第一节至第八节是「指标口径」专项；本节是随后按用户要求做的「采集源本身是否正确」审计——
> 不只看算得对不对，还要看**有没有同一条命令在一个采样周期里跑两遍**、**有没有该读的源没读**。

### 9.1 三类问题与修复

| 类型 | 问题 | 修复 |
|---|---|---|
| 重复采集 | `getCpuStats` + `getCpuCoreStats` 各读一次 `/proc/stat`，两次读数不同刻 | 合并 `getCpuSnapshot`（一次 shell：整机 + 进程 + 逐核频率） |
| 重复采集 | 温度兜底再跑一遍 `dumpsys battery`，与 `getBatteryInfo` 重复 | `getThermalInfo(deviceId, { noBatteryRead })`，采集器用同 tick 电池读数兜底 |
| 重复采集 | `getBatteryInfo` 最多 4 条 shell | 合并 1 条（`---CMAX---` / `---CUA---` / `---CNOW---` 段标记） |
| 重复采集 | `getMemInfo` 2 条 shell（`dumpsys meminfo` + `cat /proc/meminfo`） | 合并 1 条（`---PROCMEM---`） |
| 重复采集 | FPS framestats 不可用时再跑 `dumpsys gfxinfo`（超集） | `gfxTotalDelta()` 复用同一份输出里的 `Total frames rendered` |
| 错采 | `procCpu` 分母用整机总时间片 → 8 核偏低 8 倍 | `calcCpuPct()` 除「单核平均时间片」，上限 N×100% |
| 错采 | `nativeHeap` 走明细表、其余分项走 App Summary | `parseMemInfoSections()` 统一 App Summary，取不到回退明细 |
| 漏采 | 网络白名单缺 `clat*` / `v4-*`（464xlat 承载的 IPv4 流量） | `METERED_IFACE_RE` 补齐；回环/隧道仍排除 |

### 9.2 真机实测（Android 13 中端机型，同一采样周期）


- 温度来源核对：本机 MTK 平台 `/sys/class/thermal/thermal_zone*/{type,temp}` 对 shell 全部 `Permission denied`，

- `dumpsys battery` 的 `voltage 4(V)` / `temperature 290`（十分之一度）已按单位归一为 4000 mV / 29°C。

### 9.3 顺带修复：长跑抽稀后低谷截图标记消失
