# Perfara 体积与性能优化方案

> 本文所有数字均为**本机实测**（2026-10-20，Windows 10，`perfara/` 完整便携包 + r6 发布包），
> 不含任何推测值。文中「预计收益」按实测基线推算，实施后需按第 6 节复测。
>
> **本文只做分析与设计，不包含任何打包动作**（未跑 PyInstaller、未生成 zip、未改发布资产）。

---

## 1. 结论速览

| 维度 | 现状（实测） | 目标 | 主要手段 |
| --- | --- | --- | --- |
| 发布 zip | 223.1 MB | ~188 MB（-16%） | 删示例数据、精简内置 Python、asar 瘦身 |
| 解压后 | 464 MB | ~392 MB | 同上 |
| 轻量包（Android/PC 专用） | 无此形态 | ~95 MB | 拆 full / lite 双包 |
| 冷启动到可访问 | 2.34 s（源码）/ ~3 s（exe） | < 1.6 s | 延迟导入、精简 uvicorn 组件 |
| 单个采样周期（Android） | 290–450 ms | < 100 ms | adb 调用合并 + PID 缓存 |
| 首屏 JS | 1.35 MB（未压缩） | ~200 KB（gzip + 拆包） | GZip 中间件 + 路由分包 |
| 看板接口 | 25 ms / 6.9 KB | 持平 | 已足够，无需改动 |

**最高性价比的三件事**：`lowgpu.json`（-27.7 MB）、内置 Python 裁剪（-42 MB）、服务端 GZip（首屏 JS 少传 66%）。

| 指标 | 实测值 | 测量方式 |
| --- | --- | --- |

| `GET /api/tests?page_size=100`（13 条） | **25 ms / 6.9 KB** | curl 计时 |

| DB 体积 | 540 KB / 13 条 | `PRAGMA` |
| 报告页 | `perf.html` 174 KB + `echarts.min.js` 1.03 MB（外部引用） | `stat` |
| 历史归档 | 每次 2 份（`.js` + `.json`，各 ~45 KB） | `reports/history/` |

### 已经做对的地方（不需要再优化）

- 前端图表：`MAX_RENDER_POINTS = 2000` 隔点抽稀 + `lazyUpdate` 合并重绘，已解决 O(n²) 累积卡顿。
- 前端路由：`Compare` / `Trend` 已独立 chunk，不是全量打进主包。
- DB 索引：`test_runs(started_at / project_id / share_md5 / owner_uid)` 齐备，列表查询 25 ms 无压力。
- 采集参数开关：`metricConfig` 关闭的指标完全不发起 adb 调用。
- 报告页 echarts：本地优先 + CDN 兜底，离线可用。

## 4. 体积优化方案

> 收益均为「解压后」体积，zip 按 50% 压缩率折算。

### S1 · 删除 `ios-tools/bin/lowgpu.json` —— 收益 **-27.7 MB**（最高性价比）

- **现状**：27.7 MB 的 JSON，内容是一段带 `timestamp` 的 GPU 采样序列（`texture/bandwidth/compute` 分组）。
- **证据**：全仓检索 `lowgpu.json` 只命中一处**注释**（`ios-gpu-collector.js:20` 的说明文字），无任何读取代码；
  `ios_gpulow.exe` 是通过 stdout 输出 JSON，不读这个文件。
- **做法**：移出发布包（保留在 `docs/samples/` 或 git LFS 作为样例）。
- **风险**：低。若 `ios_gpulow.exe` 内部硬编码了默认路径，需一次 iOS <17 真机采集验证；建议验证后再删。
- **验证**：iOS 16 设备跑一次 GPU 专项采集，确认数据非空。

### S2 · 精简内置 Python —— 收益 **-40 ~ -42 MB**（104 MB → ~62 MB）

分三组，建议用白名单方式在构建脚本里生成裁剪副本，而不是手改发布目录：

| 组 | 内容 | 预计 |
| --- | --- | ---: |
| ① 纯运行期无用 | `tcl/`、`DLLs/tcl86t.dll`、`include/`、`libs/`、`Lib/idlelib`、`Lib/ensurepip`、`Lib/pydoc_data`、`Lib/venv`、10 个 WinPython 启动器 exe（`Lib/test` 本包内不存在，无需处理） | ~18 MB |
| ② 包管理残留 | `site-packages/pip`、`setuptools`、`_distutils_hack`、`pkg_resources` | ~10 MB |
| ③ 反编译工具 | `site-packages/uncompyle6`、`xdis`、`spark_parser` | ~2.5 MB |
| ④ `Scripts/` 中非必需入口 | 保留 `pymobiledevice3.exe` 等实际调用的入口，其余（jupyter / pip / 各类辅助）删除 | ~3 MB |

- **风险**：中。删错会直接导致 iOS 采集失败（`ios.exe` 依赖这个解释器）。
- **验证**：裁剪后在干净环境跑 iOS 采集全链路（设备识别 → 启动 → 采集 → 停止 → 生成报告）。
- **附加收益**：`site-packages` 文件数减少后，首次调用 `ios.exe` 的冷启动也会更快（Windows 上大量小文件扫描是主要成本）。

### S3 · app.asar 瘦身 —— 收益 **-2.7 MB**（4.05 MB → ~1.3 MB）

- **现状**：`node_modules/zrender` 2.42 MB（255 文件）打进 asar，运行期零引用；`echarts` 只用到 `dist/echarts.min.js`。
- **做法**：`tools/build_app.py` 的瘦身规则里补两条（该脚本已有剔除 echarts 冗余的先例）：

```python
# 渲染页只用 echarts/dist/echarts.min.js（自包含 zrender），
# 且全仓无 require('zrender')，整包剔除
DROP_PREFIXES += ('node_modules/zrender/',)
# echarts 只保留 UMD 构建产物
KEEP_ONLY = {'node_modules/echarts/dist/echarts.min.js'}
```

- **风险**：低。改完必须验证 4 个渲染页（`index / iphone / iphone_gpu / pc`）图表正常。
- **验证**：`tools/asar_tool.py list` 确认体积；打开客户端看 11 张图是否正常绘制。

### S4 · Electron 运行时裁剪 —— 收益 **-7.8 MB**，**默认不建议做**

`vk_swiftshader.dll`（5.0 MB）+ `ffmpeg.dll`（2.8 MB）理论上可在「确定有 GPU、不播视频」时移除，
但会导致无 GPU 机器白屏（本机 CI 环境就复现过 `GPU process isn't usable`）。**保持现状**。

> `LICENSES.chromium.html` 8.8 MB 是 Chromium 许可证合规要求，**不可删**。

### S5 · 报告页瘦身 —— 收益 **-1 MB 以内**，价值在加载速度

`perf.html` 174 KB 是「结构 + 样式 + 逻辑」全内联，配合外部 `echarts.min.js` 1.03 MB。
可做：把 echarts 改为**首次绘图时才注入**（当前是 `<script>` 同步加载，会阻塞首屏），
并把 `history/*.json`（与 `.js` 内容重复）改为只存一份。详见 P7 / P10。

### S6 · 发布形态拆分：full / lite —— 收益 **lite 包 -199 MB**

| 形态 | 内容 | 解压后 | zip 估算 |
| --- | --- | ---: | ---: |
| **full**（现状） | Android + iOS + iOS GPU + PC | 464 MB | 223 MB |
| **full（做完 S1–S3）** | 同上 | ~392 MB | ~188 MB |
| **lite** | 不含 `resources/ios-tools/`（仅 Android + PC） | ~193 MB | ~95 MB |

lite 包与「完全离线」定位不冲突：它只是不提供 iOS 能力，README 里明确标注即可。
若担心用户误下，可在启动器里检测 `ios-tools` 缺失时禁用 iOS 选项并提示「请下载完整版」。

### 体积小结

| 阶段 | 解压后 | zip |
| --- | ---: | ---: |
| 现状 | 464 MB | 223 MB |
| S1 + S2 + S3 后 | ~392 MB（-15.5%） | ~188 MB（-16%） |
| 另加 lite 形态 | 193 MB | ~95 MB |

## 5. 性能优化方案

### P1 · adb 调用合并 + PID 缓存 —— **收益最大**（290–450 ms → < 100 ms）

- **现状**（`collector.js:_tick`）：每个 tick 先 `getPid`，再并发发起最多 8 个采集调用，
  每个调用都是一次独立的 `execFile(adb.exe, ...)` 进程创建。实测单次 50 ms、9 次并发 290 ms 以上。
- **做法 A（合并命令）**：把同一 tick 的多项读取拼成**一次** `adb shell`，用分隔符切分结果：

```js
// 一次 shell 读回 4 项，替代 4 次进程创建
const script = [
  'cat /proc/meminfo | head -3',
  'cat /proc/stat | head -1',
  'dumpsys SurfaceFlinger --timestats -dump',
  'cat /sys/class/thermal/thermal_zone0/temp',
].join('; echo __SEP__;');
const out = await ADB.shell(deviceId, script);
const parts = out.split('__SEP__');
```

- **做法 B（PID 缓存）**：`getPid` 从「每 tick 必调」改为「每 5 tick 刷新一次」，
  并在 `dumpsys activity` 返回异常时立即重查；配合 `_processGoneGraceUntil` 现有机制，误停风险可控。
- **预计**：tick 内 adb 进程创建从 9 次降到 1–2 次，单周期 290–450 ms → 60–100 ms；
  1 Hz 采样的抖动明显减小，PC 侧 CPU 占用下降。
- **风险**：中。命令拼接要注意设备端 shell 差异（`/system/bin/sh` 不支持某些语法）与输出解析容错。
- **验证**：同一台 Android 设备，改前/改后各采 5 分钟，对比 `history` 里的样本数、FPS 曲线缺帧率、PC CPU 占用。

### P2 · 采样间隔自适应 —— 收益：长时采集更省资源

前台 1 s、切后台（`topResumedActivity` 变化）降到 2 s；「应用不在前台」本来就要靠这条信息判断。
风险低，可与 P1 一起做。

### P3 · 服务端开启 GZip —— 收益：首屏 JS **-66%**、JSON **-80%**

- **现状**：无任何压缩。`index-CX8C-b2E.js` 1,345,571 B 原样传输；实测带 `Accept-Encoding: gzip` 仍返回 1,345,571 B。
- **做法**：`backend/app.py` 加一行中间件（Starlette 自带，无需新依赖）：

```python
from fastapi.middleware.gzip import GZipMiddleware
app.add_middleware(GZipMiddleware, minimum_size=1024)
```

- **预计**：JS 1.35 MB → 451 KB；`/api/tests` 6.9 KB → ~1.5 KB。
  本机访问收益有限，但 `--host 0.0.0.0` 局域网部署时差别明显（这也是项目支持的模式）。
- **风险**：极低。唯一注意点是别对已压缩资源（`.png/.zip`）重复压缩，`minimum_size` 已可过滤小响应。

### P4 · 启动加速 —— 收益：2.34 s → 约 1.6 s

- **现状**：import 1.47 s（fastapi 0.5 s + uvicorn 0.5 s + asyncio 0.3 s），剩余 ~0.9 s 是 DB 迁移与 uvicorn 启动。
- **做法**：
  1. `launcher.py` 里把 `from backend.app import app` 延后到端口选好之后（现在是先 import 再选端口）；
  2. uvicorn 只保留 `h11` 协议与 `asyncio` loop，关掉 `auto` 探测：

```python
config = uvicorn.Config(app, host=..., port=..., http="h11", loop="asyncio",
                        ws="none", lifespan="off", log_config=None, access_log=False)
```

  3. `ensure_sqlite_migrations()` 的 `PRAGMA table_info` 探测改为一次性版本号判断（读 `PRAGMA user_version`）。
- **预计**：省 0.5–0.7 s。启动器「双击 → 浏览器打开」的体感改善主要来自这里。

### P5 · SQLite 写优化 —— 收益：上传/解析吞吐提升，锁冲突消失

- **现状**：`create_engine(..., connect_args={"check_same_thread": False})`，无 WAL、无 `busy_timeout`。
  默认 `journal_mode=DELETE` + `synchronous=FULL`，每次上传要等 fsync；并发请求（采集端上传 + 看板轮询）容易 `database is locked`。
- **做法**：连接建立时下发 PRAGMA：

```python
from sqlalchemy import event

@event.listens_for(engine, "connect")
def _sqlite_pragma(dbapi_conn, _):
    cur = dbapi_conn.cursor()
    cur.execute("PRAGMA journal_mode=WAL")
    cur.execute("PRAGMA synchronous=NORMAL")
    cur.execute("PRAGMA busy_timeout=5000")
    cur.execute("PRAGMA temp_store=MEMORY")
    cur.close()
```

- **预计**：单次上传写入从「等磁盘」变为「写 WAL」，1 h 采集（~1.2 MB）的上传耗时下降明显；
  看板与采集端并发时不再互相阻塞。
- **风险**：低。WAL 会额外产生 `-wal`/`-shm` 文件，需确认发布包清理逻辑不会误删/误打包（`.gitignore` 已忽略 `*.db`，但打包脚本要注意排除 `*.db-wal`）。

### P6 · 前端首屏拆包 —— 收益：首屏 JS 1.35 MB → ~200 KB

- **现状**：`index-CX8C-b2E.js` 1.35 MB（gzip 451 KB）单文件；`Compare`/`Trend` 已独立。
- **做法**：
  1. `manualChunks` 把 `vue` + 框架层拆成 `vendor`（可长期缓存）；
  2. 看板首页与测试详情页拆成独立 chunk，详情页（含图表逻辑）按需加载；
  3. 配合 P3 的 gzip，首屏实际下载 ~200 KB。
- **风险**：中低。前端源码**不在本仓库**（`perfara/frontend/` 只有 `dist`），改分包需要在源码仓库做，
  然后重新构建 `dist` 并同步到 `backend` 打包（`perfara_server.spec` 的 datas）。
- **备注**：如果短期拿不到前端源码，P3 的 gzip 是唯一能立刻拿到的收益（1.35 MB → 451 KB）。

### P7 · 报告页加载优化 —— 收益：首屏可交互提前 0.3–0.6 s

- **现状**：`perf.html` 用 `<script src="echarts.min.js">` 同步加载 1.03 MB，阻塞首屏渲染；
  数据走同目录 `data.js`（`var data = {...}`）。
- **做法**：echarts 改为 `defer` 或「首次绘图前动态注入」；`data.js` 改为 `fetch` + `JSON.parse`
  （`data.js` 走 JS 解析器比 `JSON.parse` 慢，且无法流式处理）。
- **顺带修文档**：README 写「echarts 与数据全部内联，单文件 HTML」，实际是 `perf.html + echarts.min.js + data.js` 三件套。
  要么改文档措辞，要么真做「导出单文件」（把两者内联进 HTML，体积约 1.2 MB，适合微信/邮件转发）。

### P8 · 渲染进程 echarts 懒加载 —— 收益：客户端首屏 ~0.2–0.4 s

4 个渲染页都在 `<head>` 里同步加载 1.07 MB 的 `echarts.min.js`，但只有「采集开始后」才画图。
改为首次 `emit('data')` 时注入 `<script>`，窗口先出来、图表后补。
风险低，与 S3（asar 瘦身）一起改最省事。

### P9 · 数据冗余 —— 收益：DB 体积约 -25%，上传解析更快

- **现状**：同一次采集同时写 `test_runs.raw_json`（179 KB / 13 条）、`metric_blobs.content`（56 KB）、`parsed_info.summary_json`。
- **做法**：`metric_blobs` 改为「按需从 `raw_json` 解析」或仅在详情页首次访问时生成（惰性物化）；
  `parsed_info` 只保留聚合摘要。
- **风险**：中。`/api/tests/{id}` 与趋势接口都读 blobs，需要改查询路径并补回归。
- **优先级**：低（当前 540 KB 的库不构成压力，但 1000 条记录后会放大到 40 MB 级）。

### P10 · 历史归档策略 —— 收益：磁盘增长可控

- **现状**：每次停止采集在 `reports/history/` 落 `.js` + `.json` 两份（内容重复），无自动清理。
- **做法**：只保留 `.js`（报告直接可用）；加「保留最近 N 次 / 总量上限」策略（如 200 次或 500 MB），
  在 `library.html` 里显示占用并支持一键清理。
- **风险**：低。注意别删用户手动归档的文件。
