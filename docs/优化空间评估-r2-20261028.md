## 1. 结论速览

| 级别 | 项 | 实测依据 | 收益 | 风险 |
| --- | --- | --- | --- | --- |
| **P0** | full / lite 双包：lite 不含 `ios-tools/bin` | 仅 Android + PC 的用户不需要 49.03 MB 的 iOS 采集器 | lite 201.1 MB → **152.1 MB（−24.3%）** | 低（无 iOS 依赖） |
| **P1** | `ios_gpulow.exe` 可由 18 KB 内置脚本替代（离线等价已验证，缺一次真机验收） | 抽出 exe 内 `ios_lowgpucounters`，用内置 Python 跑错误路径：JSON 报文/流/退出码与 exe 完全一致，耗时 9.2 s → 3.1 s；decoder `gpu_decode.py` 与内置版 **md5 相同** | full 201.1 MB → **158.4 MB（−21.2%）** | 中（成功路径需 1 台 iOS ≤16） |
| **P1** | 启动器强制结束服务端，PyInstaller onefile 的 `_MEI` 目录留在 `%TEMP%` | 实测单次启动在 TEMP 生成 **32 MB** 目录；`taskkill /F /T` 后目录保留 | 停止每次 32 MB 泄漏；冷启 −0.5~1 s（onedir） | 中 |
| **P1** | ~~adb 采样每 tick 8 个进程~~ **已实测否决** | 8 并发 506 ms，合并 5 项 474 ms；瓶颈是 `dumpsys meminfo` 单项 445 ms | 合并仅 −6%，不值得引入 ROM 兼容风险 | —（不做） |
| **P1** | 打包态 `ios.log` 写在 asar 内，静默失败 | `LOG_DIR = path.join(__dirname,'..','log')`，asar 只读 | iOS 采集问题可诊断 | 低 |
| **P2** | 数据生命周期无保留策略、无 checkpoint/VACUUM | 1 h 采集 ≈ 3 MB；`raw_json` gzip 后仅 14.7% | 库增长 −85%（可选）、磁盘可控 | 中 |
| **P2** | 静态资源无 `Cache-Control` | `FileResponse` / `StaticFiles` 均未设置 | 二次访问免重复下载 1.35 MB | 低 |
| **P2** | 上传接口无鉴权、不限 content-type | `upload_json` 对任意 JSON body 直接落库 | 本机数据污染面收窄 | 低 |
| **P2** | 无 CI，回归靠手工跑 16+10 套脚本 | 仓库无 `.github/` | 防止构建链/种子库回退 | 低 |
| **P3** | `app.py` 44 KB / 18 路由单文件、模型声明了库里不存在的索引、试用逻辑已死、主窗口未开 sandbox | 见 §7 | 可维护性 | 低 |

**边界说明**：本轮确认**没有 iOS 真机可用于验收**，因此所有 iOS 相关项拆成两级——
「离线可验证」（今天就做）与「真机验收待补」（不阻塞其它项、也不作为删包前提）。
Android / PC / 服务端相关的优化不受影响。

**一句话**：体积上现在有一条**不依赖 iOS 真机**的稳妥路径——full / lite 双包（lite −49 MB）；
`ios_gpulow.exe` 的替代方案也已用离线方式做到「行为同构」，只差一台 iOS ≤16 跑通成功路径。
运行期最该修的是 onefile 的 `_MEI` 泄漏和 iOS 日志写不进去。

## 3. 无 iOS 真机条件下的体积方案

> 原计划「默认切 Python 脚本 + 删 exe」依赖 iOS 16 真机验收。本轮确认没有该条件，
> 因此把方案改成「**不依赖真机也能落地**」与「**离线已验证、只差一次真机**」两类。

### 3.1 本轮新增的离线等价性证据

| 证据 | 结果 |
| --- | --- |
| exe 内嵌主脚本 | `ios_lowgpucounters`（18 KB pyc），调用 `ios_device.cli.base.InstrumentsBase.gpu_counters(callback, stopSignal)` |
| 解码器是否同一份 | exe 内 `ios_device/util/gpu_decode.py` 的 md5 = `e03c971de793ed0f1eef140c518f1a3a`，与包内 `Scripts/psets/pdm/ios_device/util/gpu_decode.py` **完全相同**（exe 侧 ios_device 2.4.22，包内 2.4.23） |
| 内置库是否有该 API | 有。用内置 Python 导入成功，签名 `(self, callback, stopSignal)` 与 exe 脚本调用一致 |
| 错误路径实跑 | 抽出 exe 脚本 + 内置 Python + 伪 UDID：rc=1、stdout 空、stderr 同一份 224 B JSON、耗时 **3.1 s**；exe 原样：rc=1、stderr 同报文、耗时 **9.2 s** |
| 传输形态 | exe 是一次性输出数组；`gpu_counters_pre_ios17.pyc` 是长驻 NDJSON。采集器**两条解析分支都已存在** |
| 未验证项 | 成功路径（真机上的 configureCounters / flush / 采样率）——没有设备无法覆盖 |

结论：**exe 与内置 Python 环境在「同一服务、同一解码器、同一输出字段」这一层是等价的**，
差异只在启动方式与输出信封；而信封差异代码里已经处理。

### 3.2 方案 A（推荐，立即可做）：full / lite 双包

- lite 只删 `ios-tools/bin/`（`ios.exe` 6.32 MB + `ios_gpulow.exe` 42.71 MB），**保留 `python/`**（PC 采集要用）。
- 201.1 MB → **152.1 MB（−24.3%）**，不需要任何 iOS 设备即可完整验收。
- 采集端在 `ios-tools/bin` 缺失时隐藏 iOS / iOS GPU 入口（现在是运行到一半才报错），
  README 标注「lite 版不含 iOS 能力」。
- 验收：Android + PC 全链路回归（现有 16+10 套离线用例可直接复用）。

### 3.3 方案 B（已准备就绪，待一次真机验收）：用 18 KB 脚本替代 exe

1. 把 exe 内的 `ios_lowgpucounters`（18 KB）随包放到 `python/Scripts/`，并加路径 shim（内置 Python 需要 `psets/pdm` 在 `sys.path`）。
2. 采集器改成**回退链**：`ios_gpulow.exe` 存在 → 用 exe（行为不变）；不存在 → `python.exe ios_lowgpucounters.pyc <udid>`。
   输出仍是同一份 JSON 数组，`_startLowGpuLoop` 的解析逻辑不用改。
3. 等有一台 iOS ≤16 时，按下面清单验收后，再从 full 包移除 exe → **158.4 MB**。

**真机验收清单（一次，5–10 min）**：

- 同一游戏同一场景各采 5 min（exe 路径 vs 脚本路径）：
  - 图表分组与指标名逐项一致（解码器同源，预期一致）；
  - 单轮样本数、采样间隔抖动不明显回退；
  - 停止后无残留 `ios_gpulow.exe` / python 子进程，`%TEMP%` 无新增 `_MEI`。
- 顺带确认「停止采集」能终止脚本（脚本常驻 vs exe 一次性，停止路径不同）。

**不做真机也能拿到的收益**：单轮失败重试从 9.2 s 降到 3.1 s，且不再有 53 MB/次 的临时解压。

### 3.4 方案 C（可选）：重建 slim exe

`ios_gpulow.exe` 的 PYZ 里与采集无关的依赖很大：pygments 1.72 MB、xonsh 0.94、setuptools 0.83、
IPython 0.82、pydantic 0.78、prompt_toolkit 0.64、jedi 0.48、rich 0.43，外加 PIL 系列 pyd 约 13 MB、
pydantic_core 5.4 MB。剔除后 42.71 MB（zip）预计可降到 ~20 MB，**行为不变**，但仍保留一次性解压结构。
需要能复现 PyInstaller 构建的环境，优先级低于 A/B。

### 3.5 方案 D：lite-android（仅当确定不做 PC 采集）

再删内置 Python（23.66 MB）→ **128.4 MB**。PC 采集依赖 `collect_pc_perf.pyc` + `PresentMon.exe`，
删了会直接失去 PC 能力，默认不建议。

### 3.6 形态与体积对照

| 形态 | 内容 | 估算 zip | 需要 iOS 真机 |
| --- | --- | ---: | --- |
| full（现状） | 全部 | 201.1 MB | — |
| **lite（推荐先发）** | 无 iOS 采集器，保留 PC | **152.1 MB** | 否 |
| full - exe（方案 B 验收后） | 全部，GPU 走内置脚本 | 158.4 MB | 是（一次） |
| lite-android | 无 iOS、无 PC | 128.4 MB | 否 |

风险：iOS<17 是低频场景，但失败表现是「GPU 页空白」。因此**没有真机就不删 full 包里的 exe**；
lite 与方案 B 的回退链互不影响，可以并行推进。

## 4. P1 · 启动与运行期

### 4.1 onefile 的 `_MEI` 泄漏与冷启动（R3）

**现状**：服务端、启动器都是 onefile；启动器退出时用 `TerminateProcess` / `taskkill /F /T`，
bootloader 没有机会清理，32 MB 目录留在 `%TEMP%`。

**设计（二选一）**：

1. **保留 onefile，收敛临时目录**：构建时加 `runtime_tmpdir` 指向包内 `.run`（如 `<pkg>/.run`），
   启动器每次启动先清空 `.run`，退出时再清一次。改动小，仍保留单文件分发形态。
   注意：多开时要用 PID 子目录，避免互删。
2. **服务端改 onedir**：`perfara_server.spec` 的 `EXE(...)` 拆成 `COLLECT` + `EXE(exclude_binaries=True)` + `COLLECT`。
   启动省掉每次 32 MB 解压，估计冷启 −0.5~1 s；代价是包内文件数从 1 个变数百个、zip 条目增加。
   启动器需要从 `server/PerfaraServer.exe` 改为 `server/PerfaraServer/PerfaraServer.exe`，并同步 `find_processes_by_exe`。

**建议**：先做 1（不改变分发形态、立即止血），把 2 留作下一轮性能项。

**验收**：连续启动/退出 10 次，`%TEMP%\_MEI*` 增量为 0；`.run` 为空；启动到 health ≤2.5 s。

### 4.2 adb 采样合并（R4）——**实测否决，不做**

原设计：一个 tick 内把 meminfo/stat/thermal/battery 等可同 shell 的读取拼成 1 次 `adb shell`，
预期 8 进程 → 1~2 进程、450–480 ms → 210–260 ms。

复测（同机同设备，逐项计时）：

| 方案 | tick 耗时 |
| --- | ---: |
| 当前 8 路并发（`Promise.allSettled`） | 506 ms |
| 合并 5 项到 1 次 `adb shell` | 474 ms |
| 仅 `dumpsys meminfo` 单项 | 445 ms |

瓶颈是 `dumpsys meminfo`（445 ms，设备端执行时间），不是进程启动开销；合并只省 32 ms（−6%），
却要引入 shell 拼接、分隔符解析与 ROM 兼容风险。**结论：不改**，此项从实施清单移除。

### 4.3 iOS<17 采集循环（R5）

若不采纳 §3 方案 A，至少把 `_startLowGpuLoop` 改为常驻进程（若 exe 支持持续输出），
否则每轮解压 53 MB 的成本无法消除。**与 R1 合并实施最省事**。

## 5. P1 · 可诊断性（R6）

**问题**：发布版 iOS 日志写在 asar 内，静默失败；用户报「iOS 采不到数」时没有现场。

**设计**：

- 路径改为 `app.getPath('userData')/logs/ios.log`（Electron 已有多处同类回退写法可复用），
  或由启动器在 `configout/config.js` 下发 `logdir`，与报告目录保持一致。
- 轮转：单文件 5 MB × 3（与服务端 `logging_setup.py` 同口径）。
- 脱敏：日志里出现的 UDID/序列号截断为前 4 位 + `***`（本项目已有敏感串规则，可复用）。

**验收**：打包态跑一次 iOS 采集，文件存在且包含设备识别、tunnel、脚本退出码；停止后文件可读。

## 6. P2 · 数据生命周期与传输

### 6.1 raw_json 压缩 + 保留策略（R7）

- 现状：3 MB/h 全量入库，`raw_json` 与 `metric_blobs` 各存一份解析前后数据；无上限。
- 设计：
  1. `raw_json` 写入前 `zlib.compress(level=6)` 存 BLOB（或在 `metric_blobs` 之外新增 `raw_z` 列，保留兼容读）；
     读取路径统一解压。实测压缩率 **14.7%**，1 h 记录 2.35 MB → ~0.35 MB。
  2. 保留策略：按「最近 N 天 / 总量上限」清理（默认 90 天或 2 GB），管理页显示占用并支持一键清理。
  3. 关停 checkpoint：服务端收到 `SIGTERM`/正常退出时执行 `PRAGMA wal_checkpoint(TRUNCATE)`；
     因为启动器是强杀，另加「每 N 次上传后 checkpoint 一次」兜底。
  4. 可选：`PRAGMA auto_vacuum=INCREMENTAL` 需重建库，收益有限，**暂不做**。
- 风险：中。所有读 `raw_json` 的路径（详情、reparse、分享）都要改，需补回归。
- 验收：同样 1 h 数据入库后 `length(raw_json)` 下降 ≥80%，详情页字段与改前逐项一致；
  清理任务跑完后 `PRAGMA page_count` 下降。

### 6.2 静态资源缓存头（R8）

- `/assets/*`：文件名带 hash，可 `Cache-Control: public, max-age=31536000, immutable`。
- `index.html`：`Cache-Control: no-cache`，避免升级后仍加载旧入口。
- 实现：给 `/assets` 加自定义 `StaticFiles` 子类或中间件；SPA fallback 的 `FileResponse` 显式带头。
- 验收：二次访问 DevTools 显示 from disk cache；升级包后首访拿到新 hash。

### 6.3 上传面收敛（R9）

- 现状：无鉴权、JSON body 不限 content-type；跨站 `text/plain` POST 可绕过预检写入数据。
- 设计：启动器把随机 `upload_token` 写入 `configout/config.js`，采集端带上；服务端校验。
  同时校验 `Origin`（缺省允许本机/无 Origin 的采集端），content-type 仅接受 `application/json` 与 multipart。
- 风险：低，但要保证旧版采集端兼容（一个版本内 token 可选）。

### 12.2 新增功能：性能低谷自动截图

**判定口径**（与报告「低帧占比」同源）：FPS < 本轮 P95 目标 × 0.8，连续 2 拍才算低谷；
两次截图冷却 10 s；单轮上限 30 张；无帧数据（fps=null/0）不参与判定并打断连击；
样本少于 8 拍不判定（避免开头几拍把目标拉低）。实现 `src/trough-detector.js`。

**截图通道**：主进程在采样回调里同步判定、异步入队截图，不阻塞采样。
Android 走 `adb exec-out screencap -p`（校验 PNG 魔数，避免 Windows CRLF 破坏二进制）；
iOS 走 `ios screenshot --output=<png> --udid=<udid>`（go-ios 无 `-u` 短选项，实测确认）。
PNG 经 `nativeImage` 缩到宽 900（超过才缩）并压成 JPEG q82，单张 30–120 KB。

**落盘与数据**：`reports/shots/<包名>/<YYYYMMDD-HHMMSS>/trough_HHMMSS_NN.jpg`；
每张另存 140 宽 q76 的 `thumb_trough_HHMMSS_NN.jpg`（曲线标记/缩略条用小图，避免按 900 宽原图解码）；
停止采集写 `data.js` 时附带 `shots: [{id,t,time,fps,target,file,url,thumb,thumbUrl,bytes}]`。

**展示面**：
- 采集窗口底部缩略图条（横向滚动、最多 60 张、点击全屏、Esc 关闭、切换应用/清空报告时清空）；
- 采集窗口 FPS 曲线与本地报告 FPS 曲线都钉上「低谷截图」缩略图（36×80，悬在低谷点上方，点击全屏）；
  截图时间会投影到当前 x 轴最近类目（≤20 s），长跑抽稀删掉原始时间类目后仍能显示，抽稀后会重投影；
- 本地报告 `perf.html` 末尾「性能低谷截图（N）」画廊（点击全屏；坏图自动剔除，全部坏图时整段移除，不白屏）。

**安全**：CSP 增加 `img-src ... file: data:`；截图仅在本机 `reports/` 下，不上传。
