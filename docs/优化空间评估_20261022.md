# Perfara 优化空间评估（2026-10-22）

> 基于 2026-10-22 全量测试（26 套件 / 695 断言全通过）之后的代码审查。
> 本文只做**评估与建议**，不含任何改动。已确认当前无功能性缺陷。

## 结论先说

项目**功能健康、测试充分**（695 断言零失败），但存在 4 处**架构债而非功能缺陷**的优化空间，
主要集中在「已废弃功能未彻底清除」和「复制粘贴式重复」两类：

| # | 优化项 | 类型 | 收益 | 风险 | 建议优先级 |
| --- | --- | --- | --- | --- | --- |
| 1 | 激活/试用死链路 | 死代码 + 健壮性 | 每页省 342 行、移除全局点击拦截 | 低 | **高**（建议做） |
| 2 | 外部 loginurl 残留 | 隐私 / 定位一致性 | 消除外发与「离线」定位的冲突 | 低 | **高**（建议做） |
| 3 | echarts 按需构建 | 体积 / 体验 | 单文件报告 ~1218KB → ~600KB | 中 | 中（值得做） |
| 4 | renderer 复制粘贴重复 | 可维护性 | 4 个文件 2575 行，去重可观 | 中 | 中（可分批） |

---

## 1. 激活/试用死链路（建议优先处理）

### 现状

激活功能**业务上已废弃**（`src/activation.js` 注释明确：「激活校验已移除」，
`getActivationState` 恒定返回 `activated: true`），但整条调用链**完整保留并在运行**：

```
4 个 HTML 页面 → activation-ui.js (342 行)
   → preload.js: activationGetState / trialBudgetGet
   → main.js: ipcMain.handle('activation-get-state' / 'activation-submit' / 'activation-open-fetch-url')
   → src/activation.js + src/trial-session.js
```

### 具体问题

**(a) 全局捕获级点击拦截**——`activation-ui.js:324`：

```js
document.addEventListener('click', blockIfNeeded, true);   // 捕获级，全页面
```

`blockIfNeeded` 只在 `_activated` 为真时放行，否则对**所有点击**执行
`preventDefault + stopPropagation + stopImmediatePropagation`。

> 生产环境当前**不会**锁死——因为 `getActivationState` 恒定返回 `activated: true`。
> 但这是**单点依赖**：一旦该接口异常或后续被改动，整个 UI 会静默失效（按钮点了没反应，
> 且无错误提示）。这属于设计脆弱性，不是当前 bug。

**(b) 每次点击的额外开销**：捕获级监听器会在页面上**每一次点击**都执行 `blockIfNeeded`
+ `clickAllowed`（含 5 次 `closest`）。虽然现在第一行就 return，但监听器本身常驻。

**(c) 加载开销**：`activation-ui.js` 被 `index/iphone/iphone_gpu/pc.html` **4 个页面**各加载一次
（342 行 + 内部构建的模态框 DOM）。

**(d) 硬编码密钥残留**：`src/activation.js:18` 仍保留 `SECRET_KEY = 'PERFXD_SECRET_KEY_2024'`
并对外导出。虽注释说明「不再参与任何校验」，但属于安全卫生问题，也易被误解为仍在生效。

**(e) 测试被迫 mock**：`run_collector_pages_test.js:20` 注释写明
「activationGetState 返回『已激活』——否则 activation-ui 的 document 捕获级点击拦截」，
测试必须打桩才能跑通。这是死代码增加测试负担的直接证据。

### 建议

彻底移除该链路：`activation-ui.js`、4 处 `<script>` 引用、preload 的 2 个接口、main.js 的 3 个
IPC handler、`src/activation.js`、`src/trial-session.js`、`reports-config.js` 的
`unactivatedTrialSec`，并同步简化测试 mock。

- **风险**：低。功能恒定通过，移除后行为不变。
- **回归验证**：`run_collector_pages_test.js`（36）、`run_metric_info_test.js`（37）、
  `run_open_location_test.js`（23）等依赖点击的用例可完整覆盖。

## 2. 外部 loginurl 残留（与「完全离线」定位冲突）

### 现状

`src/reports-config.js:15` 硬编码：

```js
loginurl: 'https://www.appstoreflow.com/api/auth/licence',
```

`main.js:1205` 的 `activation-open-fetch-url` IPC 会读取该 URL 并用**系统浏览器打开**，
同时带上本机 uid 作为查询参数。

### 问题

项目 README 的核心定位是「**完全离线**：不登录账号、不上传数据、不依赖任何云服务，
断网也能跑」。但代码里保留了一个第三方域名，且存在可触发打开该域名的 IPC 通道
（携带本机 uid）。

即使激活已废弃、当前 UI 隐藏了入口，这仍是：
- **定位不一致**：离线工具里留着外部授权域名
- **隐私面**：uid 会被拼进 URL 发给第三方域名
- **维护困惑**：`main.js:1209` 的错误分支「未配置 loginurl」暗示它仍可能被使用

### 建议

移除 `loginurl` 默认值与 `activation-open-fetch-url` IPC（与优化项 1 同批做，成本几乎为零）。
若确实保留服务端上报能力，应改为**显式可配置**（默认留空）、并在 README 中说明。

- **风险**：低。

## 3. echarts 按需构建（体积优化）

### 现状

`reports/echarts.min.js` **1,029,203 字节（约 1MB）**，是单文件离线报告体积的绝对主因：
分享报告实测 **1218 KB**。

### 实际用到的 echarts 能力（扫描 perf.html + library.html）

| 类别 | 实际使用 |
| --- | --- |
| 图表类型 | **仅 `line`（折线）与 `bar`（柱状）** |
| 组件 | `grid`、`title`、`legend`、`tooltip`、`dataZoom`（slider+inside）、`markLine`、`markArea`、`axisPointer`、`dataset` |
| 渲染器 | canvas |

完整包中的饼图、散点、地图、雷达、树图、3D、SVG 渲染器等**全部未使用**。

### 预期收益

按需构建（line + bar + 上述组件 + canvas 渲染器）通常可将 echarts 从 ~1MB 降到
**约 300–450 KB**，单文件报告相应从 ~1218KB 降到 **约 550–700KB**。

这直接强化核心卖点——README 强调「单文件 HTML，微信/邮件直接转发」，
体积减半对转发体验、打开速度、存储都有实质改善。

### 风险与注意事项

- **中等风险**：需重新构建并**完整回归**图表类用例（`chart_perf_bench`、`fps_legend_overlap`、
  `compare_lanes`、`report_edge`、`dedupe_metrics`、`shared_report`、`compare_report` 等）
- ⚠️ **已知坑**：当前这份 echarts 5.5 构建**不含 ResizeObserver**，所以图表不会自动跟随容器，
  代码里必须显式 `requestAnimationFrame(() => charts.forEach(c => c.resize()))`。
  若新构建**引入**了 ResizeObserver，行为会变化——这是好事（可去掉手动 resize），
  但必须验证，否则对比页等 CSS grid 场景可能出现「只画左边一条」的老问题复现。
- 建议保留旧构建以便回滚，并做逐图视觉核对。

## 4. renderer 复制粘贴重复（可维护性）

### 现状

4 个平台 renderer 共 **2575 行**，函数名高度重合：

| 重复次数 | 函数 |
| --- | --- |
| ×4 | `showStartHint`、`hideStartHint`、`showPrepHint`、`hidePrepHint`、`log`、`_getCurXIndex` |
| ×3 | `scheduleDeviceInfoBar`、`refreshDevices`、`refreshDeviceInfoBar`、`initMetricSettingsUI`、`_flagOn` |
| ×2 | `updateElapsed`、`updateCards`、`resetCards`、`stopUI`、`setCollecting`、`renderAppList`、`loadApps`、`haltCollectOnSwitch` |

| 文件 | 行数 |
| --- | --- |
| `renderer/iphone_gpu.js` | 780 |
| `renderer/iphone.js` | 689 |
| `renderer/renderer.js` | 645 |
| `renderer/pc.js` | 461 |

### 问题

明显的**复制粘贴式多平台开发**：同一份采集页交互逻辑（开始/停止、提示显隐、设备刷新、
应用列表、卡片更新、耗时计时）在 4 个文件里各写一遍。

后果：修一个 bug 要改 4 处、易漏；新增平台成本高；行为容易悄悄分叉。

### 建议

抽取公共模块（如 `renderer/collect-page-common.js`）承载上述同构逻辑，各平台只保留差异
（指标组、采集器选择、平台特有字段）。

- **风险**：中等。涉及 4 个页面的交互，**必须依赖现有测试回归**
  （`run_collector_pages_test.js` 36 项正好覆盖四平台设置持久化，是天然防线）。
- 建议**分批改**：先抽 `log` / 提示显隐 / 计时这类纯同构函数，再处理 `refreshDevices` 等
  带平台差异的部分。

## 已经做过、本次不建议重复的优化

来自 `全面测试与优化报告.md`（2026-10-20）与 `报告模板热更新与 echarts 图表坑` 记录，
以下均已落地且经测试覆盖，无需再做：

- `data.js` **无缩进序列化**（体积 -42%）
- `summarizePerf` **单趟热路径**（不再对同一份 rows 跑 11 遍 `_pick`）
- 拉起应用 **am start 优先 / monkey 兜底**
- 图表 **抽稀 + 单次采样成本**（500 点 5.9ms/次，较旧行为快 13.3×）
- 对比图 **分段并列泳道**（各运行 x 区间不重叠、段间留间隙）
- 指标表 **去重**（Jank/10min 并入主行副标注）
- 报告 **离线零依赖**（echarts 与数据全内联）
- 全历史脱敏重写（2026-10-21~22）
