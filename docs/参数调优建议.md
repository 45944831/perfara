# Perfara 参数调优建议（总结报告）

> 承接 `docs/优化方案-体积与性能.md`，本篇只谈**可调参数**：现状值 → 建议值 → 依据。
> 所有「当前值」均从源码/构建产物中核对过位置，不是推测。
>
> **本文不含任何打包动作**（未跑 PyInstaller、未生成 zip、未改发布资产）。

## 1. 明确建议：先改这 5 个参数

| # | 参数 / 位置 | 现在 | 建议 | 为什么（有证据） |
| --- | --- | --- | --- | --- |
| 1 | `collector.js:104` tick 重入 + `adb.js:30` 超时 | `setInterval` 不等待上一次完成；单次 adb 超时 **10 s** | 加 `_inflight` 门闩（上一 tick 未完成则跳过）；单指标超时 **4 s** | 采样间隔 1 s，但 adb 超时 10 s。设备一卡（`dumpsys` 慢）就有 **最多 10 个 tick 叠加**，每 tick 9 个 adb 进程 → 瞬间 90 个进程，越卡越卡。这是当前最容易踩的性能悬崖 |
| 2 | `collector.js:129` PID 刷新 | **每 tick 都调** `getPid` | 每 **5 tick**（5 s）刷新一次，异常时立即重查 | 实测 adb 单次 50 ms；9 次/tick → 290–450 ms。PID 占其中 1 次，且它变化极慢 |
| 3 | `app.py:638` 公开接口兜底查询 | `limit(5000)` 拉**全字段**（含 `raw_json`） | `limit(200)`，且只 `select(TestRun.id)` | 任何无效 testid 都会触发这次扫描；按单条 raw_json 14 KB 估算，最坏 **70 MB 级内存尖峰 + 全表读盘**，一次请求就能拖慢整个看板 |
| 4 | `perf.html` 报告图表 | **无抽稀**：32 条 series × 全部采样点 | 每 series 上限 **2000 点**，超 4000 隔点抽稀（与客户端 `MAX_RENDER_POINTS` 同策略） | 1 h 采集 = 3600 点 × 32 series ≈ 11.5 万点。客户端图表早就抽稀了，报告页漏了 —— 长报告打开会明显卡 |
| 5 | `database.py` / `app.py` | 无 PRAGMA；无 GZip | `journal_mode=WAL` + `synchronous=NORMAL` + `busy_timeout=5000`；`GZipMiddleware(minimum_size=1024)` | 上传写入要等 fsync；采集端上传与看板轮询并发时易 `database is locked`。首屏 JS 1.35 MB 未压缩，实测带 `Accept-Encoding: gzip` 仍返回原大小 |

## 3. 三个必须知道的参数陷阱

### 3.1 tick 叠加（最危险）

```
间隔 1000 ms  ──▶  每次 tick 起 9 个 adb 进程（实测 290–450 ms）
adb 超时 10000 ms ──▶  设备一慢，单个调用可挂 10 s
setInterval 不等待 ──▶  10 s 内可叠加 10 个 tick = 90 个 adb 进程
```

后果：越卡越慢、日志刷屏、CPU 飙高，看起来像「采集把机器拖死了」。
**改法**：一个布尔门闩 + 超时降到 4 s，两行代码的量级，但能根除雪崩。

### 3.2 无效 testid 触发全表扫描

`/api/public/test` 在 `share_md5` 未命中时，会 `limit(5000)` 拉全字段做 md5 反查。
这是历史兼容逻辑（`share_md5` 未回填的老数据），但**任何打错的 token 都会走这条路**。
建议缩到 200 条并只取 `id` 列，最坏内存从 ~70 MB 降到 ~3 KB。

### 3.3 报告页没有抽稀

客户端图表有 `MAX_RENDER_POINTS = 2000` + 隔点抽稀，**报告页 `perf.html` 没有**：
32 条 series 全量渲染，1 h 采集约 11.5 万点。`dataZoom` 有 7 处，但缩放前已经付了全量渲染成本。
建议与客户端同策略：>4000 点时隔点抽稀到 2000。

```python
# database.py
@event.listens_for(engine, "connect")
def _pragmas(dbapi_conn, _):
    cur = dbapi_conn.cursor()
    cur.execute("PRAGMA journal_mode=WAL")
    cur.execute("PRAGMA synchronous=NORMAL")
    cur.execute("PRAGMA busy_timeout=5000")
    cur.execute("PRAGMA temp_store=MEMORY")
    cur.close()

# app.py
from fastapi.middleware.gzip import GZipMiddleware
app.add_middleware(GZipMiddleware, minimum_size=1024)
```

```js
// perf.html（报告页）
const MAX_POINTS = 2000;
function decimate(arr) {
  if (arr.length <= MAX_POINTS * 2) return arr;
  const step = Math.ceil(arr.length / MAX_POINTS);
  return arr.filter((_, i) => i % step === 0);
}
```

## 5. 预期效果对照

| 场景 | 现在 | 改后 | 依据 |
| --- | ---: | ---: | --- |
| 正常设备单 tick | 290–450 ms | **< 100 ms** | adb 调用 9→1~2 次 |
| 卡顿设备单 tick（最坏） | 叠加 10 个 tick / 90 进程 | **跳过重叠 tick，最多 9 进程** | 门闩 + 4 s 超时 |

## 7. 建议的实施顺序（仍不打包）

| 顺序 | 改动 | 是否需要真机 | 风险 |
| --- | --- | --- | --- |
| 1 | GZip + SQLite PRAGMA | 否 | 极低 |
| 2 | 公开接口兜底 5000→200 | 否 | 低（老数据反查仍可用） |
| 3 | 分页/趋势上限收紧 | 否 | 低（前端传参会自动被 clamp） |
| 4 | 报告页抽稀 + echarts defer | 否（用现有 `data.json` 即可验证） | 低 |
| 5 | tick 门闩 + adb 超时 4 s | **是**（Android 11+ 与低版本各一台） | 中 |
| 6 | PID 每 5 tick + adb 命令合并 | **是** | 中 |
| 7 | MAX_HISTORY 14400 | **是**（跑 2 h 验证） | 低 |

前 4 项都不需要设备，改完起服务 + 打开看板 + 跑 `perfara/tests` 回归即可验收；
5–7 项需要真机，建议同一台设备改前/改后各采 5 分钟，对比样本数、FPS 曲线完整性与 PC 侧 CPU 占用。
