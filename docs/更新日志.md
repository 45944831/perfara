### 未发布 · 采集结束自动生成 Excel（按性能标签页 + 标记区间）

  `Perfara_<应用>_<时间>.xlsx`；Android / PC / iOS / iOS GPU 四个采集入口统一生效，
  无需再手动导出。生成结果会写入采集日志一行（含路径与标签页数）。
- **标签页**：`汇总`（基本信息 + 各指标均值/最小/最大）、`FPS与卡顿` / `CPU` / `内存` /
  `网络` / `GPU` / `温度` / `电池`（按本轮指标顺序，每组独占一页）、`其他指标`（iOS 等平台专属字段）、
  `标记区间`（每段标记的逐项统计）、`原始采样`（全字段平铺）。
  每张明细表都有「标记区间」列，可直接按标记筛选；表头冻结并开启自动筛选。
  未采到的分组不生成空表，未测到的单元格留空（与 CSV 一致，不补 0）；逐核使用率 / 频率自动展开成列。
  `pid` 属标识字段而非性能指标，只留在`原始采样`，不会让`其他指标`页退化成只有一列的空壳表。
  文件名精确到秒，同一秒内再停一次会自动加 `_2` / `_3`，不会静默覆盖上一次的数据。

### 未发布 · 低谷截图不再把静置 / 加载限帧误判成卡顿

- **现象**：真机截图里「低谷截图 24 张」大多是 29~31fps 的正常游戏画面，Jank / BigJank 都是 0；
  用户没有操作、或停在加载界面时，游戏主动把帧率限到 30fps，旧判定只看「FPS < 本轮 P95×80%」，
  冷却 10 秒一到就再截一张，一轮刷出几十张几乎一样的图。
- **判定改造**（`src/trough-detector.js`）：
  1. **跌落武装**：必须先连续 2 拍处于正常帧率（≥ 目标 85%）才允许截图，一上来就在加载不会截；
  2. **一次跌落一张**：截图后立即解除武装，回到正常帧率才重新允许，冷却到期不再重复截；
  3. **稳态抑制**：连续低帧 ≥ 6 拍判为加载 / 静置 / 限帧平台，停止截图直到帧率恢复；
  4. **卡顿佐证**：`main.js` 把每拍 jank / bigJank / jankRate 传给判定器；半帧平台（≥ 目标 45%）
     且明确测得零卡顿 → 判为主动限帧，不截图。深谷即使零卡顿也保留，避免漏报；
     jank 为 `null`（无权限 / iOS / gfxinfo 增量通道）时按「未测量」处理，不因缺证据而拒绝截图。
- **文案同步**：采集窗口缩略图条、报告画廊、`使用说明.txt`、操作手册第四章与 FAQ。
- **回归**：`trough_shots_test.js` 39 → **56 项全过**（新增静置/加载半帧平台、伴随卡顿仍截图、
  深谷零卡顿保留、长时间低帧不刷屏、jank 未测量不误杀、稳态后恢复等场景）。
- 改动落在 `main.js` / `src/trough-detector.js` / `src/trough-shots.js` / `renderer/trough-shots.js`，
  **需重新打包 asar 才会生效**；`perf.html` 与 `使用说明.txt` 在 asar 之外，改完即时生效。

### v1.1（2026-11-05）· 采集源审计（错采 / 漏采 / 重复采集）

- **修复：进程 CPU 口径偏低（错采）**。`getCpuStats` 拿 `/proc/stat` 的 `cpu ` 汇总行
  （所有核的时间片之和）当分母，得到的是「占整机百分比」——8 核机型上单核跑满只有 12.5%，
  而文档与 PerfDog / 任务管理器用的是「占单核百分比」（单核跑满 100%，多线程可超 100%）。
  改为除以「单核平均时间片」= 整机增量 ÷ 在线核数，上限放宽到 N×100%。**旧报告的该指标不可直接对比**。
- **修复：内存分项口径混用（错采）**。`nativeHeap` 的正则会先命中明细表（`Native Heap  1901`），
  其余分项命中 App Summary（`Native Heap:  1360`），同一张表两种 Pss 口径、差值可达数 MB。
  统一为 App Summary，取不到再回退明细表。
- **修复：同一周期重复执行同一采集源（重复采集）**：
  - `getCpuStats` 与 `getCpuCoreStats` 各读一次 `/proc/stat`，两次读数不同刻、整机使用率与逐核均值对不上；
    合并为一次 `getCpuSnapshot`（一次 shell 同时取整机 + 进程 + 逐核频率）。
  - 温度兜底会再跑一遍 `dumpsys battery`，与 `getBatteryInfo` 重复，且两个字段可能差 0.1°C；
    改为 `getThermalInfo({ noBatteryRead: true })`，由采集器用同一 tick 的电池读数兜底。
  - `getBatteryInfo` 最多下发 4 条 shell（dumpsys + current_max + batt_current_ua_now + current_now），
    合并为 1 条，四个值同一时刻。
  - `getMemInfo` 两条 shell（`dumpsys meminfo` + `cat /proc/meminfo`）合并为 1 条。
  - FPS 的 framestats 不可用时又跑一遍 `dumpsys gfxinfo`（framestats 是其超集），改为复用同一份输出里的
    `Total frames rendered` 做增量，仅在 framestats 本身抛异常时兜底。
- **修复：网络接口漏采**。白名单补 `clat*` / `v4-*`：464xlat 机型把 IPv4 流量转成 IPv6 走这两个接口，
  只认 `wlan*` 会整段丢失。回环与隧道（`lo` / `ifb` / `sit0` / `tunl0` / `ip6tnl0`）仍排除。
- **效果（真机实测，同一 tick）**：shell 命令数 10 → **5**，重复命令 **0**；
  温度 29°C（电池源）/ 结温 34.5°C 分层正确；`meminfo` 分项同口径；进程 CPU 与逐核均值同源。
- **顺带修复：长跑抽稀后低谷截图标记消失**。`update()` 抽稀分支只打了 `_fpsMarksDirty` 脏标记，
  而真正重画要等滚动空闲后的批量 flush；一旦用户此时正在滚动/缩放曲线，标记会长时间不出现。
  改为抽稀后直接走 `_renderTroughMarks()`；`clearTroughShots()` 由「只打脏标记」改为同步
  `_applyTroughMarksNow()`——清空是用户显式动作，晚一帧看起来就像「点了没反应」。
- **回归**：新增 `perf_source_audit_test.js`（42 项）；`thermal_source`(52) / `perf_param_audit`(49) /
  `preflight_breaker`(58) 全过；这 4 个套件此前**未接入 `run_offline_batch.sh`**，本轮已补入。
  全量结果：离线 **27/27** 套 `exit=0`、深度 **22/22** 套 `exit=0`。

### v1.0（2026-11-04）· 退出清理 adb 服务

- **修复：关闭采集端后 adb.exe 孤儿进程常驻**。adb 客户端执行任意命令都会 fork 一个常驻的
  `fork-server server`，它不随客户端退出；旧版关掉程序后它就留在系统里，占着 5037 端口，
  并把便携包里的 `adb.exe` 文件锁住（整个目录移不走、删不掉）。
  - `src/adb.js`：首个 adb 命令之前先探测 server 端口（默认 5037，跟随 `ANDROID_ADB_SERVER_PORT`）；
    **探测到端口空闲才判定「server 是本进程拉起的」**，新增 `killServerIfOwned()` 只收自己拉起的那个。
    探测不到 / 报错时保守判定为「不是我们的」，绝不动 Escrcpy、Android Studio 等外部 server。
  - `main.js`：`window-all-closed` 的退出链在 `app.quit()` 之前先 `cancelAllInflight()` 再收 server；
    并新增 8 s 强制退出兜底（`app.exit(0)`），避免任何一步 await 卡死时留下「没有窗口却常驻」的僵尸进程。
  - 回归：新增 `perfara/tests/adb_server_cleanup_test.js`（29 项，含探测顺序、外部 server 不误杀、
    kill 失败/挂起不拖住退出、退出链接线），已接入离线批量套件。

### 本次新增（v2026.10.21）· 体积与性能专项

按 `docs/优化方案-体积与性能.md` 与 `docs/参数调优建议.md` 落地，全部改动均已实测。

**性能**

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 首屏 JS 传输（`index-*.js`） | 1,345,571 B | **449,936 B**（gzip，-66%） |
| 服务冷启动 → `/api/health` 200 | 2.34 s | **2.13 s**（uvicorn 固定 h11 + asyncio，跳过 auto 探测） |

| PID 查询 | 每 tick 一次 | **每 5 tick 一次**，进程消失仍在 5 s 内发现 |
| 无效分享 token 兜底扫描 | `limit(5000)` 拉全字段（最坏 ~70 MB 内存） | **`limit(200)` 且只取 `id`**（实测 5 ms 返回 404） |

| 报告页数据灌入 | 每点 × 12 张图各 setOption 一次 | **批量追加，每图只重绘一次** |
| SQLite | 无 PRAGMA（写等 fsync，易 `database is locked`） | **WAL + synchronous=NORMAL + busy_timeout=5000** |
| 历史归档 | 每次 `.js` + `.json` 两份 | **只留 `.js`**（内容一致，省一半磁盘） |

| 日志面板 | DOM 无上限 | **上限 500 行** |
| echarts 加载 | 4 个采集页 + 报告页均同步加载 1.07 MB | **异步注入**，窗口先出来、图表后补 |

#### 真机验证（Android 13 中端机型）

用真机跑了采集 → 上传 → 报告全链路，**发现并修掉 4 个只在真机/游戏场景暴露的问题**：

| 问题 | 表现 | 原因 | 修复 |
| --- | --- | --- | --- |
| framestats 解析在 Android 10+ 全失效 | `gfxinfo framestats` 通道解析出 0 帧，静默降级到「Total frames 增量」，丢掉了 Jank 明细 | 写死 `cols[1]=vsync`、`cols[13]=completed`；Android 10 起 `Flags` 后插入 `FrameTimelineVsyncId` 等列（18→22 列），`cols[1]` 变成小整数，被 `vsync > 1e9` 全部丢弃 | 改为**按表头名**取列（`Vsync` / `FrameCompleted`），自动兼容 18/22 列 |
| 游戏无法从界面启动 | 选游戏点「开始」直接报「该应用没有可启动入口」 | 部分厂商定制 ROM 上 `am start -a MAIN -c LAUNCHER -p <pkg>` 返回 `unable to resolve Intent`，代码一见该报错就提前放弃，连 monkey 都不试 | 先用 `cmd package resolve-activity` 解析组件，再 `am start -n <pkg/cls>`；失败依次降级，**不再提前 return** |
| 后台应用采不到 FPS | 目标应用进程活着但在后台时，整段 FPS 全是 null | `ensureAppRunning` 只看 PID 存在就返回「无需启动」，而取帧依赖**可见图层** | 新增 `isAppForeground()`；在后台时用 `am start -n` 把任务切到前台 |
| 陈旧帧缓冲导致假 0 | 静态画面下 `fps` 恒为 0，曲线贴底并被当成真实掉帧 | framestats 是「最近 N 帧」滚动窗口，N 用满后跨度可达 190s，`frames/dur` 算的是几分钟前的平均值 | 窗口跨度 > 30s 或帧缓冲未前进时**不再用它算 fps**，交给 Total frames 增量；仍无变化则报无数据（写 null） |

另外修掉一个**数据归属**问题：`ensure_project_for_payload` 里用
`(Project.package_name == pkg) | (Project.app_name == app_name)` 查项目，
当 `pkg` 为 `None` 时 SQLAlchemy 会生成 `package_name IS NULL`，
**匹配到任意一个包名为空的项目** —— 不同应用的上传会被并进同一个项目。
改为「值为空就不参与匹配」。

真机回归结果：一款真机游戏端到端 **39/39**、
浏览器 `com.example.browser` **39/39**、报告页渲染 **11/11**；
`test_api_full.py` 64 PASS、`test_metric_config_upload.py` 25/25、
`run_perf_html_test.js` 19/19、`run_collector_pages_test.js` 36/36、`jank_algo_test.js` 30/30。

> 已知未修：framestats 的 `tinyJank` 用 `FrameCompleted - Vsync` 作帧耗时，
> 60Hz 下该值恒为 2 个 vsync（≈33.6ms），会让 TinyJank 计数偏高（timestats 通道为 0）。

### 本次新增（v2026.10.21 · 采集前健康检查 + 超时熔断）

设备卡顿曾经会一路传导到 PC 界面：点「开始」之后 `ensureAppRunning` 逐条尝试启动命令、
每种方式再轮询 5 秒 PID，最坏 20 多秒才给结论；采集中一旦 adb 通道卡死，
门闩又被永不 resolve 的 promise 焊死，界面停在「采集中」再也不动。
这一版把「设备不健康」和「设备卡死」都在有限时间内变成**可操作的结论**。

#### 采集前健康检查（`ADB.preflightCheck`，动应用之前执行）

四项并行探测、各自有硬超时，总耗时有界（真机实测 0.7 s）：

| 检查 | 通过 | 警告（放行） | 失败（直接拦下） |
| --- | --- | --- | --- |
| 设备响应 | `echo` 2.5 s 内返回 | — | 超时/报错，附 adb 原文（`device not found` / `offline`） |
| 整机内存 | 可用 ≥ 600 MB | 可用 < 600 MB | 可用 < 200 MB（LMK 随时杀目标进程，数据不可用） |
| GPU 负载 | < 95% | ≥ 95%（有别的应用占着 GPU，结果会偏高） | — |
| 屏幕状态 | 已点亮 | 锁屏（应用被 keyguard 挡着） | 熄灭且唤不醒（**没有可见渲染层，三条取帧通道全废**） |

读不到的一律降级成「未知」并记一条说明，**不**因此判失败——机型/权限差异太大，
误判失败比漏判更糟。熄屏时会自动替用户点亮（`KEYCODE_WAKEUP`），点亮不了才报错。

#### 采集超时熔断（`Collector`，两级防线）

| 防线 | 触发条件 | 动作 |
| --- | --- | --- |
| 单轮看门狗 | 某一轮采样超过 16 s 未完成 | 中止本轮、清掉 inflight adb 进程、把门闩交还下一轮（否则 `_tickBody` 里永不 resolve 的 promise 会把门闩焊死，后面再也采不动）；连续 2 轮即熔断 |
| 无数据巡检 | 连续 20 s 没有任何采样点产出（含 `fps=null` 的无帧点） | 熔断：自动停止 + 说明原因 |

另有 `start()` 全流程 30 s 硬超时（含拉起应用与稳定期等待）——健康检查、安装检查、
无入口快速失败已把常见卡点砍掉，超过 30 s 只能说明设备迟迟不就绪。

熔断时停止原因 `device_stall` 会直接显示在主界面（不只写进可能被隐藏的日志面板），
采集准备期间提示条还会跟随日志实时更新（`[adb] …` / `[健康检查] …`），
用户能看见「在等什么」而不是对着一句「准备中」猜。

#### 顺带修掉的一处回归

「假 0 修复」把无帧数据点改写成 `null` 之后，`updateFpsWarn` 仍写着
`if (fps === null) return`，导致灭屏/应用退后台时**告警条再也不亮**——
用户对着一片空白曲线没有任何提示。现已把 `null` 与 `0` 一视同仁
（都表示「这一秒没有帧数据」），并补上屏幕熄灭这一可能原因。

真机实测：游戏登录页是静态界面时 FPS 全程 `null`，现在第 5 秒起主界面即提示
「已连续 N 秒未取到帧数据：被测应用可能不在前台、屏幕熄灭或没有渲染层」。
