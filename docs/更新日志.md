### v1.7：真包真机参数准确性专项（2026-11-15）

第一次用**解包后的发布包**（而不是仓库源码）跑真机：解包 v1.6 → 跑包里的 `collector/Perfara.exe`
→ adb 独立基准核对参数 → 再用包里的 `perf.html` 渲染真数据读页面数字。查出**两个产品缺陷**，
修复后口径 6 → 7 重打包，复测全绿。

**D-19 刷新率取错字段**：`parsePeakRefreshRate()` 的正则在 `i` 标志下命中
`mDefaultPeakRefreshRate: 90.0`（DisplayManagerService 的框架默认常量），120Hz 面板报成 90。
四路证据：`settings=120` / `supportedModes=120` / SF `displayRefreshRate=120` / 当前正则 90。
修法：模式收紧到 `PRIORITY_USER_SETTING_PEAK_REFRESH_RATE` 与 `mPeakRefreshRate`，并加
`(?<!Default)` 负向断言；来源顺序改为 settings → `dumpsys display` → `supportedModes` 兜底，
`source` 分别 `settings-system` / `dumpsys-display` / `display-supported-modes`；
上界 240 → 480（240Hz 面板本身合法，旧上界会把真值判成非法而回退）。

**D-20 `data.js` 从不写 `loading` 段**：`perf.html` 的 `deviceTargetHz()` 读
`data.loading.targetHz`，取不到就退回 P95 推断 —— v1.5 的「设备自报刷新率优先」在报告侧是死代码，
历史 4 份报告全部 `loading=no`。修法：`preparePayload()` 补 `loading`（`target` / `targetSource` /
`targetHz` / `inferredTarget` / `segments` / `excludedSamples` / `excludedRatio`）；分析失败**不静默**，
写 `targetSource: 'unavailable'` + `error`，报告侧照旧退回 P95 吸附，但降级有迹可循。

**两者互相掩盖**：D-20 让报告不用 `displayProfile`，D-19 的 90 才没暴露；只修 D-20 会让目标变 90、
达帧率变 122%，**必须一起修**。

**非标档位吸附上界**（同批修）：`snapFpsTarget` 加 `c <= p95 × 1.10`，200Hz 面板不再被抬到 240
（达帧率凭空少 17%）。四处实现同步：`fps-loading.js` / `perf.html` / `library.html` / `backend/utils.py`。
三项都改变目标帧率与达帧率，故 `SCHEMA_VERSION` 6 → 7 一次跳版。

### 未发布 · r7 收尾：报告目录改白名单、空 catch 加预算、4 个测试归队、批处理环境统一

这一轮把 r5 报告里剩下的 P3/P4 工程债收掉，全部是**工程侧改动，不动任何指标口径**
（`SCHEMA_VERSION` 仍是 6，历史报告不受影响）。

**S-04 报告目录从「扩展名黑名单」反转成「文件名白名单」**（`tools/make_release_zip.py`）

`collector/resources/reports/` 同时是交付资源目录和运行期输出目录。原来靠三条排除规则
（`data.js` / `history/` / `*.xlsx`）挡住，方向是黑名单——**将来多出一种产物就漏**：
`.csv` 导出、`.png` 低谷截图、`.json` 诊断包都不会被拦住，会直接跟着发包出去。

现在改成 `REPORTS_ALLOW = {perf.html, library.html, echarts.min.js}`，只放行这三个，
其余一律剔除，并在打包日志里打一行 `⚠ 报告目录剔除（不在白名单）: <文件>`——
让「多出来的文件」当场显形，而不是悄悄进包。配套加了 `check_reports_assets()`：
白名单里的文件少一个就中止打包，避免「名字写错把交付资源一起挡掉、页面 404」。

**S-03 `perf2.html` 标注停用并从包里剔除**

源码保留（`schema_version_test.js` 还在用它做「页面内置口径版本 == `SCHEMA_VERSION`」的守卫），
文件头加了醒目的停用说明；白名单里没有它，所以不再随包分发（38 KB 死重消失）。
没有删文件——删它必须同步删那个用例，否则守卫会静默消失，这个决定留给后续。

**S-05 空 catch：先纠正数字，再用「约定 + 棘轮」收口**

原报告写「150 处 / 5 处带注释」，是手工 `grep` 的漏计。新增 `tools/scan_empty_catch.py`
重扫（先把注释置空再匹配，否则说明文字里写的 `` `catch (_) {}` `` 会被算成代码；
同时修掉 `main.js` 因分隔符不同被重复计数的问题），实测 **203 处 / 20 处带说明 / 29 个文件**。

不给 183 处各写一句「忽略」——那只会制造噪音。改成两件事：

1. **约定**：`main.js`、`adb.js`、`phone-proxy.js`、`weaknet-host.js`、`renderer.js`、
   `weaknet-page.js` 六个高频文件各写一段「本文件的空 catch 属于哪一类、由谁兜底」；
   写盘（`reports-data-js.js`）与网络（`sysproxy.js`、`update-check.js`）关键路径逐条补了原因。
2. **棘轮**：`perfara/tests/deep/empty_catch_budget_test.py` 按文件锁数量，只许减不许增。
   新增空 catch 必须显式改预算——「这里吞了个错误」就会出现在 review 里。

**测试脚手架：两处「无 JS 报错」断言过严**

后续测试清掉了，页面加载时留下 3 条 `Failed to load resource: net::ERR_FILE_NOT_FOUND`。
这是测试数据漂移，不是代码缺陷——截图是可选产物，用户清掉 `shots/` 之后报告仍要能看。

资源失败单独断言「除 `shots/` 之外不得缺失」。这样既不误报，也仍然能抓住 echarts / data.js 缺失。

### 未发布 · 根治 PerfaraServer.exe 进程残留（祖先进程存活守卫）

**现象**：本机同时挂着 4 个 `PerfaraServer.exe`，占着 8000 和 8001 两个端口，前端早已关闭。

**取证**（`perfara/server/logs/app.log` + `netstat` + 进程树）：

```
10:48:36  Started server process [45100]  →  :8000     父进程 30148（bootloader，仍活）
10:48:55  Started server process [16712]  →  :8001     父进程 2936（bootloader，仍活）
两次启动的上一级（25536 / 23032）都已消失，日志里没有任何 shutdown 记录
```

4 个进程 = **2 次启动 × 2 层**（PyInstaller onefile 的 bootloader + 真正的 Python 服务）。

**根因**：`PerfaraServer.exe` 自身没有任何生命周期绑定 —— `launcher.py` 就是
`uvicorn.Server.run()` 阻塞（`:361`），没有 `atexit`、没有信号处理器、没有父进程存活检测、
没有 `/api/shutdown`（`backend/` 全目录零匹配），且 `perfara_server.spec:141` 是
`console=False` —— 没有控制台窗口，也就没有「关闭窗口」这个动作可触发。
所以**谁拉起它，谁就必须负责收尾**；拉起者异常退出，服务就成了永久孤儿。
`v2026.10.20.1` 修过启动器侧（Job Object + `taskkill /T`），但那只覆盖「走便携启动器」这一条路，
直接跑 exe 仍然复现。

**修复（子进程侧兜底，`perfara/launcher.py` 新增「祖先进程存活守卫」）**：

- 启动时用 `CreateToolhelp32Snapshot` 取进程表，从自身往上走出一条祖先链，
  对每个祖先 `OpenProcess(SYNCHRONIZE)`，再用 `WaitForMultipleObjects` 一起等；
  任一祖先退出即收尾退出。
- **为什么是整条祖先链，不是直接父进程**：onefile 是两层，
  `启动器 → bootloader → python 子进程`。python 子进程的直接父进程是 bootloader，
  而先死的往往是启动器 —— 只盯直接父进程在这种形态下完全失效，而这正是本次 4 个残留的
  实际结构（45100 的父进程 30148 仍在，30148 的父进程 25536 已消失）。
- **上溯到桌面会话根就停**（`explorer.exe` / `services.exe` / `svchost.exe` 等
  `ROOT_PROCESS_NAMES`）：双击启动时它们的父进程就是它们自己，监视它们只会让
  「资源管理器重启」误杀正在用的服务。
- 句柄在 `main()` 一开始就开（`_setup_console` 之后立即），避免晚一步父进程已死、
  PID 被复用导致守卫失效。
- 退出走优雅路径：`_WATCHDOG_HOOK` 置 `server.should_exit = True`，给 uvicorn 3 秒收尾，
  超时才 `os._exit(0)`。
- 新增 `--no-exit-with-parent` 显式退出该行为（默认开启）；POSIX 下退化为
  `os.getppid()` 轮询，保证源码方式在 macOS / Linux 上也能跑。

**顺带修掉的同类隐患**：`tools/audit-probes/probe_r12_upload_guard.py`（及
`release/_audit/` 下同名副本）用 `proc.kill()` 收尾 —— 那只会杀掉 onefile 的 bootloader，
真正的服务子进程留成孤儿。改为 `taskkill /F /T /PID`。

**验证**：

- 新增 `perfara/tests/deep/launcher_parent_watch_test.py`（**12 PASS / 0 FAIL**）：
  用三层替身精确复现「启动器死、bootloader 活、叶子被留下」——
  杀最上层后断言中间层**仍然活着**且带守卫的叶子已退出；
  并跑反例（关掉守卫时叶子确实残留），证明修复非空转。
- 端到端（真实 `launcher.py` + uvicorn，`--port 8199` 隔离数据目录）：
  起 `top → mid → boot → launcher` 三层，只杀 `mid`（祖父层）、不杀树，
  `boot` 存活，`launcher` 在 10 秒内退出，8199 不再 LISTENING。
- 既有启动器测试无回归：`launcher_process_test` 32/0、`launcher_port_test` 14/0。
- 报告页脚本语法：`perf.html` 8 块 / `library.html` 4 块，0 错（与本改动无关，一并复核）。

**注意**：该改动落地时只改了源码；**已在 v1.6 重打 `PerfaraServer.exe` 并验证**
（强杀拉起者后 0.5s 内退出、端口释放；`--no-exit-with-parent` 反例存活；
整包冒烟的「启动器退出后无遗留进程 / 端口已释放」两项同批通过）。

发现 2 个**真实缺陷**，其中 1 个让「网络按应用统计」在 Android 10+ 上**从未真正生效过**：

1. **`parseNetstatsUid` 对真机输出完全失效**（严重）
   - 真机 `dumpsys netstats` 用的是**缩写字段** `rb=` / `tb=`，不是 `rxBytes=` / `txBytes=`；
     而且 `uid=` 头行与计数行是**分离的两行**。旧解析器要求「同一行同时出现
     `uid=` + `rxBytes=` + `txBytes=`」，在真机上一条都命中不了。
   - 命令也必须带 `--uid`：默认视图只有汇总段（目录 / 接口 / openSession callers），
     **不含** per-UID 计数行；`--uid` 视图 1187 行 / 74 KB / ≈190 ms。
   - **set 语义搞错了**：真机实测 `DEFAULT` 是「非前台流量」、`FOREGROUND` 是「前台流量」，
     两者**互斥**而非包含。旧口径「只取 DEFAULT」会漏掉前台大头 ——
     实测某前台应用 `DEFAULT` 仅 18 KB、`FOREGROUND` 却有 22 MB，相差三个数量级。
   - 修复后真机 `netScope` 由 `device`（整机流量）变为 **`app`（按 UID 的应用流量）**，
     `meta.quality` 回到 `ok`；同时给 netstats 通道补了分桶粒度说明
     （ROM 按 1~2 小时分桶存储，短周期突发流量可能被抹平）。
2. **`trough-detector` 在只有 `overrunP99` 时丢失证据**：命中回传
   `overrunMax: Number(ctx.overrunMax)`，旧数据上得到 `NaN`（JSON 序列化后成 `null`），
   截图依据凭空消失。改为与判定使用同一套回退口径。

#### 真机端到端再暴露 4 处（trace-capture 3 处 + netstats 口径 1 处，全部修复）

1. **perfetto 命令 `-c` 与 `-t` 同用被设备拒绝**（Android 12+ 全量命中，perfetto_cmd.cc:587）：
   时长参数改写进 config 文本的 `duration_ms`，CLI 只留 `-c -`。
2. **perfetto 输出路径被 SELinux 拒绝**（errno 13）：shell 用户 touch 得了

   产物改落官方目录 `/data/misc/perfetto-traces/`。
3. **simpleperf 的 mkdir 目录残留**：`rm -f` 删不掉目录，反复取证会在设备端堆空目录；
   清理目标改为 mkdir 的目录、命令改 `rm -rf`。真机 e2e 断言成功 / 取消两条路径都零残留。

#### 采集编排性能优化：adb 命令 TCP 直连 adb server（观测者效应 59% → 25%）

外部复核指出「采集编排一行没改，单拍 761ms」后实测定位（同一台 Android 13 真机，
Chrome 前台渲染）：

- 采集编排结构本身已是局部最优：v1.1 已把组内命令合并（CPU 一条 shell 读全核），
  7 组任务 `Promise.allSettled` 真并发；组间合并只会把设备端执行串行化，反而更慢。
- 真正的瓶颈在 **host 侧每条命令 spawn 一个 adb.exe**：单条 ~180ms（Windows 进程
  创建 + adb 握手），7 条并发竞争拉到 ~400ms；而设备端命令只跑 20~50ms，
  全部命令串行也只有 344ms。
- 解法：`adbShell` 优先走 **TCP 直连 adb server**（127.0.0.1:5037，标准 adb 协议
  `host:transport:<serial>` → `shell:<cmd>`，零进程创建），任何失败自动回退
  子进程路径，36 处调用点零改动；pull/push/exec-out/设备管理仍走子进程。
  直连 socket 纳入 `cancelAllInflight` 同一套取消通道。

**真机实测**：整拍 P50 **589ms → 250ms（-58%）**、max 665 → 419；采集开销
（观测者效应）从占采样周期 59% 降到 ~25%，回到 30% 告警线以内。
回归：离线 31/31、深度 25/25 全绿（注入式测试不受影响）；真机 12 套见真机测试记录。

### 本次新增（v2026.10.21 · 采集前健康检查 + 超时熔断）

设备卡顿曾经会一路传导到 PC 界面：点「开始」之后 `ensureAppRunning` 逐条尝试启动命令、
每种方式再轮询 5 秒 PID，最坏 20 多秒才给结论；采集中一旦 adb 通道卡死，
门闩又被永不 resolve 的 promise 焊死，界面停在「采集中」再也不动。
这一版把「设备不健康」和「设备卡死」都在有限时间内变成**可操作的结论**。

#### 采集前健康检查（`ADB.preflightCheck`，动应用之前执行）

四项并行探测、各自有硬超时，总耗时有界（真机实测 0.7 s）：

| 检查 | 通过 | 警告（放行） | 失败（直接拦下） |
| --- | --- | --- | --- |
| 设备响应 | `echo` 2.5 s 内返回 | — | 超时/报错，附 adb 原文（`device not found` / `offline`） |
| 整机内存 | 可用 ≥ 600 MB | 可用 < 600 MB | 可用 < 200 MB（LMK 随时杀目标进程，数据不可用） |
| GPU 负载 | < 95% | ≥ 95%（有别的应用占着 GPU，结果会偏高） | — |
| 屏幕状态 | 已点亮 | 锁屏（应用被 keyguard 挡着） | 熄灭且唤不醒（**没有可见渲染层，三条取帧通道全废**） |

读不到的一律降级成「未知」并记一条说明，**不**因此判失败——机型/权限差异太大，
误判失败比漏判更糟。熄屏时会自动替用户点亮（`KEYCODE_WAKEUP`），点亮不了才报错。

#### 采集超时熔断（`Collector`，两级防线）

| 防线 | 触发条件 | 动作 |
| --- | --- | --- |
| 单轮看门狗 | 某一轮采样超过 16 s 未完成 | 中止本轮、清掉 inflight adb 进程、把门闩交还下一轮（否则 `_tickBody` 里永不 resolve 的 promise 会把门闩焊死，后面再也采不动）；连续 2 轮即熔断 |
| 无数据巡检 | 连续 20 s 没有任何采样点产出（含 `fps=null` 的无帧点） | 熔断：自动停止 + 说明原因 |

另有 `start()` 全流程 30 s 硬超时（含拉起应用与稳定期等待）——健康检查、安装检查、
无入口快速失败已把常见卡点砍掉，超过 30 s 只能说明设备迟迟不就绪。

熔断时停止原因 `device_stall` 会直接显示在主界面（不只写进可能被隐藏的日志面板），
采集准备期间提示条还会跟随日志实时更新（`[adb] …` / `[健康检查] …`），
用户能看见「在等什么」而不是对着一句「准备中」猜。

#### 顺带修掉的一处回归

「假 0 修复」把无帧数据点改写成 `null` 之后，`updateFpsWarn` 仍写着
`if (fps === null) return`，导致灭屏/应用退后台时**告警条再也不亮**——
用户对着一片空白曲线没有任何提示。现已把 `null` 与 `0` 一视同仁
（都表示「这一秒没有帧数据」），并补上屏幕熄灭这一可能原因。

真机实测：游戏登录页是静态界面时 FPS 全程 `null`，现在第 5 秒起主界面即提示
「已连续 N 秒未取到帧数据：被测应用可能不在前台、屏幕熄灭或没有渲染层」。
