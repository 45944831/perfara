### 1. `launcher_process_test.py` — 30 项全绿

启动器此前零覆盖，而它正是「进程残留 / 端口漂移」历史大坑的所在。
用真实进程 + 真实端口验证：端口管理（`port_free`/`pick_port`/`wait_port_free`）、
进程管理（`find_processes_by_exe` 按完整路径匹配、不误杀同名不同目录进程、
`kill_server_processes`、`kill_tree`）、Job Object（`KILL_ON_JOB_CLOSE` 生效）、

> 测试方法坑：假服务 exe 必须用**系统 python**（`D:\python\python.exe`）的副本。
> venv 的解释器复制出去后找不到 `pyvenv.cfg`，会以退出码 106 静默死掉。

### 2. `loading_algo_consistency.py` — 29 项全绿

`detect_loading_segments` 在客户端（`fps-loading.js`）、服务端（`utils.py`）、
报告页（`perf.html`）**三处各有一份实现**，注释要求「保持完全一致」。
任何一处漂移都会导致「服务端算的均值 ≠ 报告页画的底纹 ≠ 客户端剔除的段」。

用 25 个构造 / 随机序列逐字段比对三处输出 —— **确认无漂移**；
另覆盖 warm-up、minRun 边界、null 桥接上限（2 允许 / 3 断开）、40% 作废、
结尾 null 收缩、mask 越界保护。

15 种畸形 payload（空数组 / 键缺失 / null / 单点 / 全 0 / 全 null / 1e9 / 负值 /

## 四、修复的缺陷（3 处，均未打包）

### 缺陷 1：上传接口对非标量字段崩成 500（`perfara/backend/utils.py`）

`/api/upload` 是开放入口，`device`/`app`/`bundleId`/`appName`/`label`/`platform`/`category`
**没有任何 schema 约束**。

- 若调用方把 `app` 传成 dict，`ensure_project_for_payload` 会把它整个塞进 SQL 条件
  （`Project.app_name == {...}`），SQLite 抛
  `ProgrammingError: type 'dict' is not supported` → 上传 **500**
- payload 顶层是数组时 `payload.get(...)` 直接 `AttributeError` → **500**
- `label` 为 dict 时同样崩（`parsers.py`）

**修复**：新增 `as_text()` 规范化 —— `str` 原样 / `int`·`float` 转字符串 /
`bool`·`dict`·`list` 一律 `None`（不猜），并把 `payload` / `device` 非 dict 的情况前置兜住。
`label` 在 `parsers.py` 走同一规范。

**效果**：10 种字段类型错乱 + 顶层数组 + label 畸形，全部从 500 变为优雅处理
（400 拒绝或 200 正常入库）。

### 缺陷 2：启动器端口检测存在误判隐患（`tools/launcher_portable.py`）

`port_free()` 原先设 `SO_REUSEADDR` 再 bind。Windows 上该选项的语义是
「**双方都设**才允许重复 bind」—— 一旦对端也设了它，这里 bind 会成功，
把「已被占用」误判成「空闲」。启动器会直接起服务，然后服务 bind 失败、30s 后 fatal。

**修复**：改为不设 `REUSEADDR`。无论对端设不设，端口上真有 socket 占着，bind 就会失败。
代价只是 `TIME_WAIT` 时更保守地顺延到下一个端口，方向是安全的。

> 实测确认：对真实 uvicorn 服务，原实现也能正确判定（uvicorn 没设 REUSEADDR），
> 所以这是**潜在**而非当前触发的缺陷；但去掉后检测覆盖所有情况。

### 缺陷 3：测试资产缺口（本次补齐）

启动器、三处算法一致性、畸形输入此前的零覆盖，已由上述 4 套 106 项断言补上。
