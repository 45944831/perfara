## 三、新缺陷清单

### N1 · 高 · 带 `metricConfig` 的上传去重失效  〔已修 2026-10-28〕

**现象**

同一份 payload（含关闭了部分指标的 `metricConfig`）连续上传两次，得到两条记录：

```
第一次 id=8，第二次 id=9
```

8 路并发上传同一份 payload，得到 8 条记录：

```
ids = [10, 11, 12, 13, 14, 15, 16, 17]
```

不带 `metricConfig` 的普通上传不会复现：32 路并发仍只落一条，说明去重主体逻辑没坏，
坏在「参与哈希的 payload」不是同一份。

**根因**

上传入口用**原始 payload** 算哈希：

```python
# perfara/backend/app.py:241
content_hash = compute_content_hash(payload)
```

解析器在 `metricConfig` 存在时，会先按配置剔除被隐藏的 `perf` 项，再用**过滤后的 payload** 算哈希：

```python
# perfara/backend/parsers.py:262-272
raw_payload = json.loads(json.dumps(payload))
...
raw_payload["perf"] = filter_perf_items_for_raw(items, category, mc)
raw_payload["metricConfig"] = mc
...
content_hash=compute_content_hash(raw_payload)
```

于是入口拿 A 去查重，库里存的是 hash(B)，永远查不到。
`database.py:105` 每次启动还主动 `DROP INDEX IF EXISTS uq_project_content_hash`，
库层没有唯一约束兜底，并发下更没有第二道闸。

**影响**

同一份采集数据在列表、趋势、对比里重复出现；导出与分享也会重复。
不会丢数据，但会破坏「同内容只留一条」这一核心行为。

**修复建议**

1. 哈希只算一次：在入口把 payload 规范化（含 metricConfig 过滤）后算 hash，
   通过参数传给解析器，禁止两处各算一次；
2. 恢复库层唯一约束，例如 `UNIQUE(project_id, owner_uid, content_hash)`，
   `IntegrityError` 转成「已存在」响应；
3. 增加「带 metricConfig 的重复上传」回归用例（现有 `dedupe_metrics` 只覆盖无配置场景）。

**复现**

```bash
PYTHONIOENCODING=utf-8 tools/.venv/Scripts/python.exe perfara/tests/deep/adversarial_deep_test.py
# 修复后预期 100 PASS / 0 FAIL（本节相关断言）
```

### N2 · 高 · 跨租户泄漏：`/api/projects/with-info` 返回他人的最新解析结果  〔已修 2026-10-28〕

**现象**

alice 与 bob 先后上传同一包名的数据后，alice 请求自己的项目概览，
返回的 `latest_info` 是 bob 的记录：

```json
{
  "project": {"id": 1, "package_name": "com.tenant.shared", "app_name": "TenantApp"},
  "latest_info": {
    "id": 2,
    "test_run_id": 2,
    "device": "DeviceOf-bob",
    "summary": {"fpsAvg": 102.5, "fpsAvgRaw": 102.5}
  }
}
```

alice 自己的记录是 `id=1`，bob 的是 `id=2`；项目列表本身按 uid 过滤是对的，
但「最新解析结果」没有按 uid 过滤。

**根因**

项目按包名 / 应用名**全局复用**（`ensure_project_for_payload`），
而 `with-info` 只按 `project_id` 取最新 `ParsedInfo`：

```python
# perfara/backend/app.py:961-968
latest = (
    db.query(ParsedInfo)
    .filter(ParsedInfo.project_id == p.id)
    .order_by(ParsedInfo.created_at.desc(), ParsedInfo.id.desc())
    .first()
)
```

同一文件里的 `/api/projects/{project_id}/infos` 反而做了 uid 过滤
（`app.py:1005-1013` 先 join `TestRun` 再 `_match_uid_to_testrun_sql`），
说明这是 `with-info` 单点的遗漏，不是模型层无解。

**影响**

设备名、机型、FPS/CPU/内存均值、`test_run_id` 等元数据跨用户可见。
再叠加 N3 的可预测令牌，元数据泄漏会升级为完整原始数据泄漏。

**修复建议**

- `latest_info` 查询 join `TestRun` 并加 `_match_uid_to_testrun_sql(uid)`；
- 或者在项目层引入真正的成员关系（owner / shared_with），不要用「包名相同」当共享依据；
- 为 `with-info` 增加双用户交叉断言（本轮取证脚本可直接接入）。

**复现**

```bash
PYTHONIOENCODING=utf-8 tools/.venv/Scripts/python.exe perfara/tests/deep/tenant_isolation_repro.py
# 修复后预期 6 PASS / 0 FAIL；退出码 0 表示越权已被拦住
```

### N3 · 高（局域网）/ 中（默认本机）· 分享令牌可预测，公开接口返回完整数据  〔已修 2026-10-28〕

**现象**

1. 令牌就是 `md5(str(id))`。拿到任意记录 id，不用登录即可读取：

```bash
curl "http://<host>:8000/api/public/test?testid=$(printf 2 | md5sum | cut -d' ' -f1)"
# 200，返回 test.owner_uid=bob、完整 test_raw
```

2. 返回值远多于「分享报告」所需：`test.owner_uid`、`para1/para2`、
   完整 `test_raw`（含全部 perf 点）、项目信息；
3. 演示账号 `perfara123` 本应只能读快照 id，但公开令牌对**任意**记录都返回 200，
   快照隔离形同虚设；
4. `share_md5` 缺失时还会回退扫描最近 200 个 id 并逐个比 `md5(id)`（`app.py:680-690`），
   等于把「令牌可猜」写进了兜底逻辑。

**根因**

- `database.py:97-100` 启动时把空 `share_md5` 回填为 `md5(str(id))`；
- `app.py:670-700` 的 `/api/public/test` 无鉴权，直接 `TestRunDetailOut` 全量序列化；
- 分享令牌没有随机性，也没有有效期 / 撤销机制。

**影响**

默认便携版只监听 `127.0.0.1`，风险限于本机其他进程 / 其他本地用户；
一旦按 README 用 `serve.py`（默认 `0.0.0.0`）或 `--host 0.0.0.0` 开放局域网，
同网段任何人可枚举 id 读取全部原始采集数据。实测 `192.168.1.49:8153/api/health` 返回 200。

**修复建议**

1. 新记录用 `secrets.token_urlsafe(32)` 生成分享令牌，绝不由 id 派生；
2. 删除 `md5(id)` 回填与兜底扫描；旧链接显式迁移或失效；
3. 公开接口使用独立 DTO：只暴露报告所需字段，隐藏 `owner_uid`、`para1/para2`
   与非必要的 `test_raw`；
4. 增加令牌撤销 / 过期；分享默认关闭，显式开启才生成。

**复现**

```bash

# N3 / N3b 两项预期 REPRO
```

### N4 · 中 · 项目别名全局共享，可被任意 uid 覆盖  〔已修 2026-10-28〕

**现象**

alice 写入别名后，bob 能读到；bob 再写一次，alice 看到的是 bob 的值：

```
alice PUT  com.tenant.shared -> AliasByAlice
bob   GET  -> AliasByAlice
bob   PUT  -> OverwrittenByBob
alice GET  -> OverwrittenByBob
```

**根因**

别名表没有 `owner_uid`，读写都不按 uid 过滤：

```python
def list_aliases(db: Session = Depends(get_db)):

alias = db.query(ProjectAlias).filter(
```

别名是展示层数据，但跨用户覆盖会造成「我起的名字被别人改掉」，

**修复建议**

- `ProjectAlias` 增加 `owner_uid`，唯一键改为 `(owner_uid, package_name, app_name)`；
- 列表与 upsert 全部按 uid 过滤；

### N5 · 中低 · `Infinity` / `NaN` 被写入 summary，严格 JSON 解析失败  〔已修 2026-10-28〕

**现象**

上传含 `Infinity` 字面量的 JSON，接口返回 200，summary 里原样保留：

```
{"fpsAvg": null, "fpsAvgRaw": Infinity, "cpuProcAvg": 21.5, ...}
```

Python 的 `json.loads` 默认接受 `Infinity` / `NaN`，`json.dumps` 也默认写出；
但 ECMAScript 的 `JSON.parse` 会直接抛错，其他语言的严格解析器同样失败。

**根因**

- 上传解析没有 `parse_constant` 拒绝非有限值；
- 落库序列化没有 `allow_nan=False`：

```python
# perfara/backend/parsers.py:280 / :485 / :487
raw_json=json.dumps(raw_payload, ensure_ascii=False)
...
content=json.dumps(...)
summary=json.dumps(...)
```

**影响**

单文件报告 / 前端若用严格 JSON 解析，会遇到整条记录解析失败；
当前前端多数路径能容错，所以表现为「个别图表空」，不易察觉。

**修复建议**

入口 `json.loads(..., parse_constant=...)` 直接拒绝，或统一把非有限值归一为 `null`；
落库统一 `allow_nan=False`，把问题挡在写入前。

### N6 · 中 · 上传无体积 / 点数 / 字段长度上限  〔已修 2026-10-28〕

**现象**

- 6.8 MB、2 万点的 payload：1.0 s 处理完，落库后 DB 17.1 MB；
- 4 KB 的 uid：接受；
- 256 KB 的 label：接受并完整回显；
- 代码里没有请求体大小、点数、单字段长度的上限。

**根因**

```python
# perfara/backend/app.py:176
raw = await up.read()
# perfara/backend/app.py:200
body = await request.body()
```

两处都把请求体一次性读入内存；后续也没有点数 / 长度校验。
原始 JSON 与 `MetricBlob` 双份存储，进一步放大磁盘占用。

**影响**

局域网模式下，未鉴权的大请求可造成内存与磁盘压力；单条 6.8 MB 放大到 17.1 MB，
反复上传即可快速堆库（叠加 N1 的去重失效更明显）。

**修复建议**

- 反向代理 / 中间件限制 `Content-Length`（例如 10 MB），超限 413；
- 限制 `perf` 点数与单字段长度，超限 400；
- 评估是否必须同时保存 `raw_json` 与 blob，或对原始数据做压缩 / 截断。

### N7 · 中 · `serve.py` 默认监听 `0.0.0.0`，与便携启动器不一致  〔已修 2026-10-28〕

**现象**

```python
# perfara/serve.py:36
```

### N8 · 低 · `library.html` 的 `createdAtLocal` 未转义；报告库窗口权限偏大  〔已修 2026-10-28〕

**现象**

报告库卡片直接拼接时间字段：

```js
// perfara/collector/resources/reports/library.html:1270
'    <div class="card-time">' + (rep.createdAtLocal || rep.createdAt || '') + '</div>',
```

同文件的 `deviceName` / `app` 都走了 `escapeHtml`，唯独这里没有。
若本地索引被篡改（或未来某条链路让该字段来自外部），脚本会在报告库窗口执行。

窗口本身还关闭了沙箱：

```js
// _client_src/app/main.js:1311
sandbox: false,
```

preload 暴露了 `deleteReports`、`openReport`、`openReportLocation`、`exportSharedReport` 等文件操作。
两个条件叠加，才构成「脚本 → 文件操作」的完整链路。

**影响**

本轮浏览器测试没有从服务端数据触发该字段（`createdAtLocal` 由本地采集器生成），
所以定为低危「本地索引可信边界」问题，而不是远程 XSS。
但 `library.html` 是可单独打开的本地文件，索引可被其他程序修改，纵深防御上应修。

**修复建议**

- `escapeHtml(rep.createdAtLocal || rep.createdAt || '')`；
- 报告库窗口能开 `sandbox: true` 就开；不能则收紧 preload，只暴露必要 IPC 并校验参数；
- 给索引文件加简单完整性校验（或至少校验字段类型）。

### N9 · 低 · 测试基建三处「假绿 / 残留」（本轮已修）

   留下半截目录；`seed_integrity_test.py --src` 则因 SQLAlchemy 连接池持有 `t.db` 句柄永远删不掉。

   `perfara_adv_*` / `seedint_*` 均无残留。

**建议**
