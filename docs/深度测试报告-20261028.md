## 三、缺陷清单

### D2 · 严重 · 便携包首启用到的演示数据是坏的  〔已修 2026-10-28 · 见第八节〕

**现象**（真跑 `perfara/dist/PerfaraServer.exe` 首次启动生成的库，非源码推断）

- `metric_blobs.content` 13 行中 **10 行不是合法 JSON**
- `test_runs.summary` 13 行中 **12 行不是合法 JSON**
- `test_runs.raw_json` 13 行中 **10 行非法**；`parsed_info.summary_json` **12 行非法**
- 合计 **44 处损坏**（`_seed/webperf.db` 与 exe 首启库逐字节一致）
- `GET /api/tests` → 200 但每条 `summary=None`（`parse_summary_dict` 静默吞异常）→ **看板列表 FPS/CPU/内存均值整列空白**
- `GET /api/tests/{id}` → **500**，12 条演示记录里 10 条打不开
- 浏览器实测：详情页只有「加载失败，请返回重试。」，`canvas=0`

**根因**：`tools/make_seed_db.py:61` 的兜底正则

```python
(re.compile(r"\b[A-Z0-9]{14,}\b"), "DEMO-SERIAL"),
```

`\b` 在 `.` 后成立，于是**浮点字面量的尾数被当成设备序列号**：

```
"cpuUsage": [null, 24.218338859221145, ...]   →   "cpuUsage": [null, 24.DEMO-SERIAL, ...]
```

已验证该结果是**确定性复现**：用这条正则单独处理开发库的 blob，输出与 `_seed/webperf.db` 逐字节相同
（id=19/20/27 三条全部相等）。也就是说只要跑 `make_seed_db.py`，损坏必然发生。

**为什么发布自查没拦住**：`tools/scan_seed_db.py` 只做敏感词模式匹配（`scan_db`），
命中 0 就退出 0；它启动 exe、拿到库，却从不 `json.loads` 任何一列。
`scan_package.py` 同样只看文本条目。**两道门都在查「有没有泄漏」，没人查「还能不能用」。**

**修复**（按性价比排序）

1. `make_seed_db.py` 的序列号正则要求同时含字母与数字，且排除纯数字：
   `r"\b(?=[A-Z0-9]*[A-Z])(?=[A-Z0-9]*[0-9])[A-Z0-9]{14,}\b"`
   **该写法已实测**：真序列号形态 `HT8A1234567890AB` 仍被命中，`24.218338859221145` 不再被命中；
   用它对开发库整库（52 个 JSON 列值）重跑一遍脱敏，**0 处 JSON 损坏**（现网正则同法跑出 44 处）。
2. 脱敏**不要对整段 JSON 文本做正则替换**。按列 `json.loads` → 只替换字符串叶子 → `json.dumps` 回写，
   数字与结构天然不会被碰到。第 1 条是止血，这条才是根治——否则将来加任何「数字形态」兜底规则都会再踩一次。
3. `scan_seed_db.py` 增加一道 `json.loads` 完整性断言 + 「逐条演示记录 GET /api/tests/{id} 必须 200」
   （`seed_integrity_test.py` 已经写好，接入即可）。
4. `schemas.py:112 from_orm_with_json` 加容错：坏 blob 跳过或降级为空 content，
   不要让一条脏数据把整个详情页打成 500。

**复现**

```bash
python perfara/tests/deep/seed_integrity_test.py --src     # 仓库内种子库
python perfara/tests/deep/seed_integrity_test.py           # 真跑打包 exe（推荐，最接近用户现场）
```

### D18 · 高 · 「入库的种子库」其实只是一个 Git LFS 指针  〔已修 2026-10-28 · 见第八节〕

`perfara/.gitattributes:2`（文件头写着 `# auto generated by UGit`）：

```
*.db   filter=lfs diff=lfs merge=binary -text
*.pyc  filter=lfs diff=lfs merge=binary -text
```

于是 `git cat-file -s HEAD:perfara/_seed/webperf.db` 得到 **131 字节**——那是
`version https://git-lfs.github.com/spec/v1 / oid sha256:... / size 552960` 的指针文本，
真库躺在本地 `.git/lfs/` 里。三条后果：

1. **克隆即坏**：`git clone` 后拿不到 LFS 对象（配额、登录、或 `git lfs pull` 没跑）时，
   spec 里 `_seed/webperf.db` 就是 131 B 文本，`make_release_zip.py` 照样把它塞进 exe，
   服务首启直接起不来——门禁扫到的是指针，不是数据。
2. **推送即上传**：`git push` 的 pre-push 钩子会把 LFS 对象传到 GitHub 的 LFS 存储。
   叠上 D17，等于把带真机残留字节的库发到公网，而 git 层的任何审计都看不见它。
3. 仓库根 `.gitattributes:2` 明明写着「历史遗留的 Git LFS 追踪规则已移除（2026-10-21）」，
   但同一批规则在 `perfara/` 子目录里还活着——这类「同一约定散在两个文件、只改了一个」的坑，
   和 D10 的「`.gitignore` 有两条规则」是同一个病。

**修复**（已做）：`perfara/.gitattributes` 改为 `*.db binary` / `*.pyc binary`
（保留「不当文本做行尾转换、不做 diff」的语义），种子库 389 KB 用普通 blob 存，
克隆即得、也才谈得上被 `scan_seed_db.py` 审计；顺手用 `git lfs ls-files` 验证 HEAD 树里
已无任何 LFS 条目。历史里 2026-10-21 之前那批 `data/webperf.db` / `*.pyc` 指针仍留在旧提交中
（对象不在本地 LFS 存储里，未见对应数据被上传），是否与 D11 一起重写历史属同一类决策。

### D5 · 中低 · SPA 兜底前缀守卫可被同层目录绕过  〔已修 2026-10-28 · 见第八节〕

`app.py:1039-1050` 用 `cand.startswith(FRONTEND_DIST)` 判断候选文件是否落在 dist 内。
`FRONTEND_DIST = <repo>/perfara/frontend/dist`，而 `perfara/frontend/dist_backup/` 同样满足前缀。
实测：在 `frontend/` 下放置 `dist_probe/`（名字以 `dist` 开头）并请求相应路径，
返回 200 且读出预埋标记 `PERFARA-PREFIX-GUARD-PROBE`。

不是穿越到任意目录（那部分守住了），但**同层/子层的非发布目录会被当静态资源发出去**——
本地开发时 `dist-old/`、`dist_bak/` 很常见，可能读掉不该读的文件。

**修复**：`os.path.commonpath([FRONTEND_DIST, cand]) == FRONTEND_DIST`，
并要求路径段完整匹配（`dist` 与 `dist_probe` 是两个段）。

### D16 · 低中 · PC 采集「启动目标程序」经 `cmd start`，文件名含 `^&` 可在本机执行任意命令  〔已修 2026-10-28 · 见第八节〕


上游 `main.js:457-461` 只做 `path.normalize + fs.existsSync`。分两段实测（不启动任何 GUI 程序）：

1. **闸门放行**：Windows 文件名允许 `^` 与 `&`，预埋 `perfara_probe.exe^&notepad.exe` 后
   `existsSync` 返回 True，归一化不剥离元字符，字符串原样传到 sink。
2. **sink 生效**：同一数组形态交给 cmd，6 组探针里只有 `^&` 那组把 proof 文件写了出来
   （`&`、`|`、`"`、含空格的 `&` 都没触发）——即 `^&` 经 Node/libuv 转义后仍被 cmd 反转义成命令分隔符。
   两段合起来构成可利用链。

触发条件苛刻：需要用户主动选中一个**名字里带 `^&` 的预埋文件**，且路径不含空格（有空格时会被整体加引号而失效）。
所以定为低中，但它是本项目唯一能被本机 shell 解析的地方，值得一次改掉。

**修复**：`spawn(exePath, [], { detached: true, windowsHide: true })` 直接拉起，不经 `cmd start`；
或在闸门里拒绝文件名含 `^ & " | > <` 的路径。

顺带查出一个次生现象：`cmd /d /c start "" <名字解析不了的程序>` 每次都会留下一个**空闲的
`cmd.exe`** 不退出（探针跑了 23 次，`Get-CimInstance Win32_Process` 就数到 23 个，已确认全部
出自探针命令并逐个回收）。也就是说这条链路除了注入面，还有进程泄漏面——`_winCmdStartExe` 的
`detached + stdio:'ignore'` 让它没有退出回调可依赖。同一处改成直接 `spawn(exePath)` 一并解决。

**复现**：`node perfara/tests/deep/pc_launch_injection_test.js`（5 PASS / 2 FAIL）

### D14 · 低 · 服务 exe 被直接 terminate 会留孤儿监听  〔本轮未修 · 见第八节〕

`Perfara.exe` / `PerfaraServer.exe` 是 `.gitignore` 排除的二进制（不入库）。本轮已在本地按
`perfara.spec` / `perfara_server.spec` 重打并把产物部署到 `perfara/Perfara.exe`、
`perfara/server/PerfaraServer.exe`，但**发布 zip 尚未重出**——
`release/交付_20261027/*.zip` 里那份种子库仍是坏的。对外发版前需要：

```bash
python tools/make_release_zip.py           # 重出便携包
python tools/scan_package.py <新 zip>      # 第一道
python tools/scan_seed_db.py  <包内 exe>   # 第二道（四判据：泄漏 / 字节层 / JSON / 详情）
```

> **推送到 GitHub 之前**还有一件与 D18 有关的事：`*.db` 一旦被 `filter=lfs` 捕获，
> `git push` 的 pre-push 钩子会把库文件本身作为 LFS 对象上传，git 层的任何审计都看不见。
> 本轮的 5 个待推提交已整体重写（`perfara/.gitattributes` 改 `binary`、种子库换成 VACUUM 后的
> 那份），`git lfs ls-files` 在新 HEAD 树里为 0 条，因此不会有对象被带走。
> 若以后有人用图形客户端（UGit 之类）重新勾选 LFS 追踪，这条会原地复发——
> 所以 `scan_seed_db.py` 的字节判据顺带也会把「扫到的是指针而不是数据」暴露出来
> （指针文本的 `PRAGMA` 会直接报 `DatabaseError`，退出码非 0）。
