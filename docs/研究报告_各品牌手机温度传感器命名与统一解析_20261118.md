# 研究报告：各品牌手机温度传感器命名与统一解析（2026-11-18）

## 一、结论（一句话）

**传感器名称（`mName`）各厂商随意命名、永远追不完；跨品牌统一的正解是按 AOSP 强制枚举 `mType` 归类。`mName` 别名表只作老格式兜底。**

据此改造 `parseThermalService()` 后，用户截图「外壳 -- · 结温 --」的根治在真包真机上得到确认：副标题从 `--` 变为 **外壳 27.9° · 结温 36.1°**。

### 2.1 关键洞察：为什么不能只做「名字别名表」

- AOSP 接口注释白纸黑字写 `mName` **不标准化**，别名表是追不完的（小米/OPPO/vivo 各有私有名，且随 ROM 版本变化）。
- 而 `mType` 是 **HAL 认证强制枚举**，厂商可以改名字，但类型值必须合规——这才是跨品牌稳定的分类依据。
- 本机取证是决定性证据：`AP`（应用处理器）用别名很难猜，但 `mType=0` 直接就是 AOSP 的 `CPU`。

### 2.2 顺带发现的两个旧正则硬缺口

1. 旧正则 `mName=([A-Z_]+)` 只认大写下划线 → 小写 `battery`、带空格 `test temperature sensor` **整行被丢弃**。
2. `mType=6/7/8` 是 BCL 电池充电限流虚拟量，单位分别是 mV/mA/% —— 旧实现只按 `0<v<150` 过滤，`BCL_PERCENTAGE=80` 会被当成 **80°C** 冒充机身温度。

## 三、集成方案

### 3.1 三处改造（`_client_src/app/src/adb.js`）

1. **`THERMAL_TYPE_CATEGORY`**：`mType` → 语义类别的权威映射（0=cpu, 1=gpu, 2=battery, 3=skin, 4/5=peripheral, 6/7/8=nonTemp, 9=die）。
2. **`THERMAL_NAME_ALIAS`**：兜底别名表，覆盖本次取证的全部厂商命名（`BAT/AP/LRB/LRF/LRP/SUBBAT/PA` 等）+ 标准名 + 常见国产 ROM 写法。
3. **`classifyThermalRow(name, type)`**：`mType` 优先、名字兜底；`nonTemp` 类型下只有名字明确命中真实传感器才救回（兼容非标准 ROM 的 `mType=8 + BOARD`）。
4. **正则放宽**：`mName` 放行大小写/数字/空格，`mType`/`mStatus` 改为可选（覆盖老 ROM 精简格式），`mStatus` 缺省视为 0（保持旧行为）。
5. **多颗外壳取平均**：Samsung `LRB/LRF/LRP` 三颗外壳传感器平均，比只取第一颗更接近整机手感；`mStatus!=0` 的异常颗先滤除（本机 `LRP mStatus=3` 被正确排除）。

### 3.2 语义不变量（严格保留）

- 主温度仍按 **电池 > 外壳 > 机身 > 结温** 优先级，只有结温时主值写 `null`（不编造机身温度）。
- 结温（`cpuTemp/gpuTemp`）与机身温度互不混用；外围器件（PA/USB）与 BCL 非温度量不进主值。
- `mStatus` 过滤语义不变。

### 3.3 口径版本：8 → 9（按项目铁律）

主温度来源由 `board`（多传感器平均）变为 `battery`（BAT 实测），`skinTemp/cpuTemp` 由空变有值 —— 已发布指标数值与含义发生变化，**必须升版**。

同步清单：`sample-meta.js`、`inject_metric_info.py`、`perf.html`/`perf2.html`/`library.html` 的 `CUR`、`compareSchemaRisk().current`，以及全部 8 处硬编码口径断言。
