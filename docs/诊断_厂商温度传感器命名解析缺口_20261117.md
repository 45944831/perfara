# 诊断报告：厂商温度传感器命名与解析器口径缺口（2026-11-17）

## 一、现象

用户截图（采集窗口「机身温度」指标卡）：

- 主数值：**33.9°C · 板载**（有数据）
- 副标题：**外壳 -- · 结温 --**（空）

用户反馈「没数据」。主数值正常，问题在副标题的两路分项读数。

## 二、结论（一句话）

**真机有数据，是采集端解析器不认这台机的厂商传感器命名，导致外壳/结温两项留空。**
这是**兼容性缺口**，不是传感器缺失、也不是数据算错。**按用户决策，本轮只出报告、不改代码。**

## 三、取证

### 3.1 真机传感器实际输出（`dumpsys thermalservice`）

```
Current temperatures from HAL:
  Temperature{mValue=51.6, mType=0, mName=AP,  mStatus=0}   ← SoC 应用处理器结温
  Temperature{mValue=34.5, mType=2, mName=BAT, mStatus=0}   ← 电池热敏电阻
Cached temperatures:
  Temperature{mValue=34.5, mName=BAT}
  Temperature{mValue=35.2, mName=LRB}   ← 左后壳估算
  Temperature{mValue=35.6, mName=LRF}   ← 左前壳估算
  Temperature{mValue=35.6, mName=LRP}   ← 左后近电池壳估算
  Temperature{mValue=40.5, mName=PA}    ← 功放
  Temperature{mValue=32.8, mName=USB}
  Temperature{mValue=0.0,  mName=SUBBAT}
```

物理关系自洽：`AP≈51.6`（芯片结温）> 外壳 `LRB/LRF/LRP≈35` > 电池 `BAT≈34.5`，
符合「结温比外壳高 20~30°C、外壳接近手感」的已知规律。设备温度数据完整可用。

### 3.2 采集端解析器的名称白名单（`_client_src/app/src/adb.js`）

```js
// 芯片结温类传感器：不得作为主温度来源
const DIE_TEMP_NAMES = new Set([
  'CPU', 'GPU', 'NPU', 'MODEM', 'DSP', 'BSP', 'CHARGER', 'WIFI', 'WLAN',
  'CAMERA', 'POWER_AMPLIFIER', 'USB', 'DDR', 'PMIC', 'SOC',
]);
// 机身 / 电池类传感器：主温度只从这里取
const BODY_TEMP_NAMES = new Set([
  'SKIN', 'BATTERY', 'BOARD', 'SHELL', 'CASE', 'BACK', 'PANEL', 'SURFACE', 'AMBIENT',
]);
```

解析函数 `parseThermalService()` 用精确名匹配：
- 电池：`pick('BATTERY')`
- 外壳：`pick('SKIN')`
- 结温：`pick('CPU')` / `pick('GPU')`

### 3.3 名称对不上 → 全落空

| 传感器语义 | 这台机的名字 | 解析器认的名字 | 结果 |
| --- | --- | --- | --- |
| 电池 | `BAT` | `BATTERY` | ❌ 不匹配 → battery 字段空 |
| 外壳 | `LRB`/`LRF`/`LRP` | `SKIN` | ❌ 不匹配 → skinTemp 空 |
| 结温 | `AP` | `CPU`/`GPU` | ❌ 不匹配 → cpuTemp 空 |

四路全不匹配，`main` 只能走到 `nonDieRows` 平均（把 BAT/LRB/LRF/LRP/PA/USB 一起平均）
→ `source='board'`、主值 33.9。这就是截图里「板载」的由来。

### 3.4 落地数据佐证（工作区 data.js）

```
样本数 54
temperature=32.5  tempSource=board
skinTemp=None  cpuTemp=None  gpuTemp=None
batteryTemp=31.3   ← 这个由 dumpsys battery 兜底拿到，不是 thermalservice
```

副标题渲染逻辑（`_client_src/app/renderer/renderer.js:791-796`）：

```js
const shell = typeof d.skinTemp === 'number' ? d.skinTemp + '°' : '--';
const die   = dieTemp != null ? dieTemp + '°' : '--';
tempExtra.textContent = '外壳 ' + shell + ' · 结温 ' + die;
```

`skinTemp`/`cpuTemp` 为 null → 显示 `--`。渲染没错，是上游数据没填。

## 四、影响范围

- **视觉**：副标题两路显示 `--`，用户以为「没数据」
- **主数值**：33.9 本身合理（多传感器平均），不算错
- **报告/分析**：`cpuTemp`（结温）缺失会影响「结温 vs 外壳」对比与热节流归因的旁证；
  但项目已有 ADPF `thermalStatus` 作为降频的直接铁证，结温缺失不结果的准确性
- **机型**：影响所有 thermalservice 用非标准传感器名的 ROM（此机为其中一例）

## 五、若后续决定修复（供参考，本轮不实施）

修复并非简单加几个名字，需兼顾口径版本（项目铁律）：

1. **名称别名映射**（保守做法）：
   - `BAT` → 电池（等价于 `BATTERY`），可进主值优先级与 `battery` 字段
   - `LRB`/`LRF`/`LRP` → 外壳估算，填 `skinTemp`
   - `AP` → SoC 结温，填 `cpuTemp`
2. **口径影响**：主值来源会从 `board`（多传感器平均）变成 `battery`（BAT=34.5），
   数值与 source 都变 → 按 `SCHEMA_VERSION` 铁律需升版（当前 8→9）并重打包
3. **更保守的替代**：只把 `LRB→skinTemp`、`AP→cpuTemp` 填进副标题，
   **主值仍保持 board 不变** → 不改口径、不升版、影响面最小
4. **测试守卫**：在 `accuracy_fixes_test.js` 增加厂商命名的解析用例，
   锁定 `BAT/LRB/AP` 的归类与 `mStatus` 过滤行为
